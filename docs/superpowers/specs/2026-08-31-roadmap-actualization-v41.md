## 1. Что дала разведка

Разведка пошла по заделу, который карта v39 оставила поиску, и первым же
замером опровергла собственную запись прошлой карты.

### Находка 1 (главная). Соединения есть — им мешал порядок

Карта v39 записала: «Механизм поиска умеет только колонки своей таблицы:
соединений с другими таблицами в `DynamicListing` нет вовсе — нужна новая
машинерия». **Это неверно.** Машинерия есть и написана давно:

- поле модели с `fieldType: 'relation'` объявляет связь (`relationKey`,
  `relationEntityKey`);
- `getFieldComparatorRelationColumn` превращает такое поле в колонку
  соседней таблицы (`contacts.display_name`);
- `buildFieldsJoinQueries` добавляет к запросу соединение.

Не работало другое — **порядок инициализации** в `DynamicFilterSearch`:

```ts
public onInitialize() {
  super.onInitialize();   // ← родитель считает, к чему нужны соединения
  this.filterRoles = this.getModelSearchFilterRoles(this.searchKeyword);
}
```

Родитель по ролям поиска решает, к каким таблицам заказать соединение, а
роли назначались строкой НИЖЕ. Родитель видел пустой список и соединений
не заказывал.

Живой замер (SQL, построенный настоящим механизмом):

```sql
select * from `sales_invoices`
where ... or (`contacts`.`display_name` like '%Ромашка%')
```

Условие по чужой таблице есть, а соединения нет — такой запрос база
отвергает. Отсюда и вывод прошлой карты, будто соединений не существует:
их не было видно, потому что механизм лишили работы.

### Находка 2. Внутреннее соединение теряет документы без контрагента

Механизм соединял таблицы через `builder.join` — то есть ВНУТРЕННИМ
соединением. Колонка контрагента в базе объявлена **без `notNullable`**
(миграции `create_sale_invoices_table`, `create_bills_table` и соседние):
пустое значение допустимо.

Внутреннее соединение выкинуло бы такой документ из выдачи **даже при
поиске по его собственному номеру**: человек ищет «СЧ-001» и не находит
свой же счёт. Дефект пришёл бы вместе с починкой находки 1 — поэтому
закрыт в том же срезе.

### Находка 3. Расходы — единственный висячий вид записей

Замер по реестру: видов записей четырнадцать, поиск умеет искать
**тринадцать**. Четырнадцатый — «расход»:

- сервер искать расходы **умеет** (модель `Expense` ищет по ссылке и сумме);
- на витрине у вида нет ни адреса запроса, ни разбора ответа, ни привязки
  к окну поиска;
- ни один из 117 маршрутов его не объявляет.

Итог для человека: на экране расходов поиск ищет «Клиентов».

## 2. Фаза «Счета Ромашки» — срезы

1. **К1 — документы ищутся по имени контрагента.** Починить порядок
   инициализации, перевести соединение в левое, добавить восьми документам
   служебное поле поиска по имени контрагента. Сторож: у каждого документа
   запрос содержит и условие, и соединение.
2. **К2 — расходы ищутся среди расходов.** Закрыть висячий вид: адрес,
   разбор ответа, привязка, объявление на маршруте.

Порядок: К1 → К2.
Каждый срез: красный тест → правка → полные прогоны → живая проба → PR.

## 3. Что сделано

### К1 — документы ищутся по имени контрагента

Порядок в `DynamicFilterSearch.onInitialize` исправлен: роли поиска
задаются ДО того, как родитель считает соединения.

Соединение полей-связей переведено с внутреннего на левое
(`builder.leftJoin`). Левое соединение строку сохраняет, а условие по
чужой колонке для неё просто не выполнится — документ без контрагента
по-прежнему находится по своему номеру.

Восьми документам (счёт покупателю, смета, чек, счёт поставщика,
кредит-нота, возврат поставщику, оплата от клиента, оплата поставщику)
добавлено служебное поле поиска `customer_name` / `vendor_name`: связь на
контрагента с ключом `display_name`. Поле помечено `filterable: false` —
в выпадашке фильтров оно не появится, по контрагенту там уже фильтруют
полем-списком.

**Почему тест написан на SQL, а не на исходнике.** Первая редакция
проверки смотрела только условие поиска — и зеленела на запросе, который
база отвергнет: соединение добавляет ДРУГОЙ метод, чем условие. Проверка
строит запрос полным путём (`DynamicFilter` + `DynamicFilterSearch`) и
требует и условие, и соединение, и его левый вид.

### К2 — расходы ищутся среди расходов

Виду «расход» добавлены адрес запроса (`/expenses`), разбор ответа
(сервер отдаёт поле `expenses`) и привязка к окну поиска. Маршрут расходов
объявляет вид записей — теперь на экране расходов поиск ищет расходы, а
подпись (карта v39) говорит об этом честно.

Строка расхода в результатах: у расхода нет номера, поэтому показываем
ссылку, а если её нет — дату; справа сумма.

**Урок про сторожа.** Проверка «окно поиска предлагает вид расходы»
сначала импортировала реестр привязок целиком — он тянет половину
приложения и упирался в таймаут. Переписана на чтение исходника, но
проверяет ОБЕ половины: привязку можно объявить и забыть включить в
список. Проверено на исходном грехе — краснеет, если строку из списка
убрать.

### Живая проба

Стенд для пробы не годится: тенантные базы там пустые — приложение
создаёт их при первом обращении, а учётных данных пользователя стенда у
меня нет. Стенд не тронут ни одной командой записи.

Вместо этого поднята **своя временная база** (контейнер `mysql:8.0`, порт
3399, удалён после пробы): таблицы `sales_invoices` и `contacts`, клиент
«Ромашка» с тремя счетами и один счёт без контрагента. На них выполнены
запросы, которые строит настоящий механизм — до правки и после.

| Запрос на экране счетов | До правки | После правки |
|---|---|---|
| «Ромашка» (имя клиента) | **0** | **3** — СЧ-001, СЧ-002, СЧ-003 |
| «Ромашка», условие без соединения (как строил механизм) | `ERROR 1054: Unknown column 'contacts.display_name'` | — |
| «СЧ-001» (номер счёта) | 1 | 1 |
| «СЧ-004» (счёт без контрагента) по своему номеру | 1 | **1** — не потерялся |
| он же при внутреннем соединении (как было бы без второй правки) | — | **0** — потерялся бы |
