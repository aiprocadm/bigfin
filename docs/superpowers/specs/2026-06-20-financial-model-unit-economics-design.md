**Зависимости (всё уже в коде):** ④ Статьи (`ManagementArticles`), ⑦ Сделки (`Deals`), ⑧b KPI менеджеров, склад/себестоимость (`InventoryCost`), сотрудники (`Payroll.Employee`).

---

## 1. Цель и объём

Новая страница «Финмодель» — дашборд юнит-экономики для управленца без бухгалтерского образования. Показывает 6 ключевых метрик и рентабельность по сегментам за выбранный период, с графиками.

**Критерий завершения (из роадмапа):** на странице виден дашборд с 6 ключевыми метриками, можно отфильтровать по периоду/сегменту.

### В объёме (решения брейншторма 2026-06-20)

- **6 метрик:** маржинальность, LTV, CAC, ROMI, точка безубыточности, выручка на сотрудника.
- **4 сегмента рентабельности:** по сделке/проекту, по менеджеру, по направлению (branch), по продукту (валовая маржа).
- **Новый ручной ввод:** маркетинговые каналы (помесячно расход + новые клиенты); пометка статей «постоянная/переменная» для безубыточности; настройка «средний срок жизни клиента (мес.)».
- **Графики:** библиотека `recharts` (новая зависимость, чистый JS → требует одного `pnpm install` с подтверждения основателя).
- **Раскладка:** единый экран с прокруткой (вариант A): фильтры → 6 карточек-метрик → графики → таблицы сегментов.

### НЕ в объёме (anti-scope)

- Машинное обучение, предсказательная аналитика.
- Пользовательские (кастомные) метрики — только preset.
- Разнесение накладных на товар — «маржа по продукту» = **валовая** (выручка − себестоимость COGS), без распределения SG&A на единицу.
- Когортный/оттоковый LTV — используем упрощённую формулу с допущением срока жизни.
- Импорт CAC из CRM ⑯ (CRM ещё не построена) — только ручной ввод.

## 2. Данные и новые вводы

Принцип: **новые структуры только там, где данных физически нет.** Всё остальное переиспользуется.

### Новые тенантные таблицы (`packages/server/src/database/tenant/migrations/`)

| Таблица | Поля | Назначение |
|---|---|---|
| `marketing_channels` | `id`, `name`, `active` (bool, default true), `created_at`, `updated_at` | Справочник каналов привлечения (Яндекс, Google, соцсети…) |
| `marketing_monthly` | `id`, `channel_id` (FK → marketing_channels), `month` (varchar `'YYYY-MM'`), `spend` (decimal), `new_customers` (int), `created_at`, `updated_at`; **unique(`channel_id`, `month`)** | Помесячный ввод расхода и числа новых клиентов по каналу |

Обе миграции — аддитивные, с рабочим `down()`. Имена таблиц/колонок физически в ВЕРХНЕМ регистре из-за `knexSnakeCaseMappers({upperCase:true})` (см. память проекта про tenant tables UPPERCASE) — учитывать в raw-SQL, если понадобится.

### Пометка статей для безубыточности

- В существующую таблицу `management_articles` добавляется **nullable** колонка `cost_behavior` (`'fixed'` | `'variable'` | `null`).
- Помечается один раз вручную (UI на странице статей или на вкладке настройки безубыточности). Пустое значение = статья не учитывается как постоянная.
- Аддитивно: на существующие отчёты (ОПиУ, Сделки, KPI) не влияет.

### Допущение для LTV

- Настройка в существующем механизме Settings: группа `financial_model`, ключ `customer_lifetime_months` (число). Паттерн — как ставки налогов в ФОТ (`payroll`).

## 3. Метрики: формулы и источники

Все суммы — за выбранный период. В скобках — переиспользуемый источник.

### Авто-метрики

- **Маржинальность** = Прибыль ÷ Выручка × 100% _(ArticlesPlRollupService: Σ доходных статей − Σ расходных)_
- **Выручка на сотрудника** = Выручка ÷ число активных сотрудников _(`Employee` where active=true)_

### Сегменты рентабельности (выручка / затраты / маржа по каждому элементу)

- **по сделке/проекту** — `GetDealsSummary` (готов)
- **по менеджеру** — агрегация сделок по `Deal.managerId` (паттерн `GetPayrollKpiSummary`)
- **по направлению** — `ArticlesPlRollupService` с фильтром `branchesIds`, по каждому branch
- **по продукту** — **новый запрос** `GetProductMargin`:
  - Выручка по товару: Σ(`quantity` × `rate`) из `items_entries` где `reference_type='SaleInvoice'`, группировка по `item_id`.
  - Себестоимость по товару: Σ(`cost`) из `inventory_cost_lot_tracker` где `transaction_type='SaleInvoice'` и `direction='OUT'`, группировка по `item_id`.
  - Валовая маржа = выручка − себестоимость; маржа% = валовая_маржа ÷ выручка.

### Маркетинговые (новый ввод + данные)

- **CAC** (на канал и итого) = Расход ÷ Новые клиенты
- **ROMI** = Выручка ÷ Расход на маркетинг — «рублей выручки на рубль маркетинга» (решение основателя; строго это ROAS, в коде/спеке фиксируем формулу Выручка÷Расход; подпись в UI: «Выручка на ₽ маркетинга»)
- **LTV** = Средний чек × Маржинальность% × Срок жизни клиента
  - Средний чек = Выручка ÷ число клиентов с продажами за период
  - Срок жизни — из настройки `customer_lifetime_months`

### Точка безубыточности

- **Выручка безубыточности** = Постоянные затраты ÷ Маржинальность (как доля, 0..1)
  - Постоянные затраты = Σ расходных статей с `cost_behavior='fixed'`

### Допущения (зафиксированы явно)

1. **«Прибыль» = валовая** (доходы − прямые расходы по статьям), не чистая после налогов.
2. **LTV упрощённый** — чек × маржа × срок жизни; срок жизни задаётся вручную (оттока в данных нет).
3. **ROMI = ROAS** по формуле Выручка÷Расход (по выбору основателя).

## 4. Архитектура (подход A — слой композиции)

### Backend: модуль `packages/server/src/modules/FinancialModel/`

- **Чистые функции** (`utils/`, без БД, легко тестируются): `computeMargin`, `computeCac`, `computeRomi`, `computeLtv`, `computeBreakEven`, `computeRevenuePerEmployee`. Каждая принимает уже агрегированные числа и возвращает результат + флаг «неприменимо» (деление на ноль/нет данных).
- **Запросы-композиторы** (`queries/`): `GetFinancialOverview` (6 метрик), `GetSegmentProfitability` (4 разреза), `GetProductMargin` (новый COGS-запрос). Тянут данные через существующие сервисы + новые таблицы, прогоняют через чистые функции.
- **Команды маркетинга** (`commands/`): CRUD каналов; upsert помесячных цифр.
- **Контроллер**: `GET /financial-model/overview`, `GET /financial-model/segments`, `GET /financial-model/marketing`, мутации маркетинга (`@RequirePermission('manage','all')`), пометка `cost_behavior` статьи.
- Флаг `financial_model` гейтит UI; на сервере — мягкий гейт (как `credits`/`notifications`).

### Frontend: `packages/webapp/src/containers/FinancialModel/`

- Страница `/financial-model` (единый экран): тулбар фильтров (период, направление) → грид 6 карточек → блок графиков (recharts: линия «маржа во времени», бары «CAC по каналам») → таблицы сегментов.
- Отдельные под-разделы на той же странице: ввод маркетинга по каналам; пометка постоянных статей.
- Хуки `hooks/query/financialModel.tsx` (React Query v3, как `credits`).
- Гейт `useFeatureCan('financial_model')`; роут + пункт меню.
- Все строки — через `intl.get(...)`; ключи парно EN+RU.

### Период/фильтры

- DTO с `fromDate`/`toDate` + группировка (месяц по умолчанию) — паттерн `ArticlesRollupQueryDto`/`ProfitLossSheet`.

## 6. Обработка ошибок (краевые случаи)

- Нет выручки → маржа/ROMI/средний чек = «—», без падения.
- Нет новых клиентов по каналу → CAC = «—».
- Маржа ≤ 0 → безубыточность «недостижима при текущей марже».
- Нет маркетинговых данных за период → блок CAC/ROMI/LTV: «Заполните маркетинг».
- Нет помеченных постоянных статей → безубыточность: «Отметьте постоянные статьи».
- Денежная математика — через утилиты проекта (как `payrollMath`/Кредиты), без float-дрейфа.
