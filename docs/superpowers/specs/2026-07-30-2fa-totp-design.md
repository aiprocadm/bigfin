# ㉚ Двухфакторная аутентификация (2FA): TOTP + резервные коды — дизайн

Дата: 2026-07-30. Пункт дорожной карты v5 §5 п. 2 (после ②c печатных форм).

## 1. Цель и рамки

Дать пользователю Bigfin возможность защитить вход вторым фактором:
одноразовым кодом из приложения-аутентификатора (Google Authenticator,
Яндекс Ключ, 1Password и т.п.) по стандарту **TOTP (RFC 6238)** плюс
**резервные коды** на случай потери телефона.

**В объёме:**
- Включение/выключение 2FA самим пользователем (настройки → «Безопасность»).
- Второй шаг при входе: ввод 6-значного кода или резервного кода.
- 10 одноразовых резервных кодов, перегенерация.
- Троттлинг попыток ввода кода (защита от перебора).

**Вне объёма (backlog):** SMS/e-mail-коды, WebAuthn/passkeys, «доверенные
устройства» (не спрашивать 30 дней), принудительное 2FA для всех
пользователей организации со стороны админа, 2FA для API-ключей.

## 2. Ограничения окружения → ключевые решения

1. **Новые npm-зависимости не добавляем.** `pnpm-lock.yaml` защищён хуком,
   `pnpm install` запрещён правилами проекта. Поэтому:
   - TOTP реализуем сами на `node:crypto` (HMAC-SHA1, RFC 6238 — это
     ~40 строк + base32-кодек). Корректность доказываем тестами на
     эталонных векторах из RFC 4226/6238.
   - QR-код рисуем вендорённым однофайловым генератором
     [qrcodegen (Project Nayuki), MIT] в `packages/webapp/src/lib/qrcodegen.ts`
     с сохранением лицензионной шапки. QR кодирует стандартный
     `otpauth://totp/...` URI; рядом всегда показываем секрет текстом для
     ручного ввода.
2. **Пользователи глобальные** (`system.users`), 2FA — свойство аккаунта,
   не организации → миграция только в **system**-схеме.

## 3. Модель данных (system-миграция `add_two_factor_to_users`)

Новые колонки в `users`:

| Колонка | Тип | Что хранит |
|---|---|---|
| `two_factor_enabled` | boolean, default false | Включена ли 2FA |
| `two_factor_secret` | string(512), nullable | TOTP-секрет, зашифрованный AES-256-GCM ключом, выведенным из `jwt.secret` (scrypt). Формат `iv:tag:ciphertext` base64 |
| `two_factor_backup_codes` | text (JSON), nullable | Массив bcrypt-хэшей неиспользованных резервных кодов |
| `two_factor_enabled_at` | datetime, nullable | Когда включили |

Секрет пишется уже на этапе настройки (до подтверждения), но 2FA считается
активной только при `two_factor_enabled = true`. `down()` дропает колонки.

## 4. Backend (`packages/server/src/modules/TwoFactor/` + правки Auth)

### 4.1 Утилиты (чистые функции, покрыть тестами)

- `totp.ts`: `generateTotpSecret()` (20 случайных байт → base32),
  `generateTotpCode(secret, time)` и `verifyTotpCode(secret, code, time)`
  с окном ±1 шаг (30 с); сравнение — `timingSafeEqual`.
  `buildOtpAuthUri(secret, email)` → `otpauth://totp/Bigfin:<email>?secret=...&issuer=Bigfin`.
- `backupCodes.ts`: `generateBackupCodes()` → 10 кодов формата
  `XXXX-XXXX` (алфавит без похожих символов), хэширование bcrypt,
  `consumeBackupCode(hashes, code)` → новый список без использованного.
- `secretCipher.ts`: AES-256-GCM шифрование/дешифрование секрета.

### 4.2 Сервисы-команды (по образцу Auth/commands)

- `TwoFactorSetup.service` — старт настройки: генерирует секрет, шифрует,
  сохраняет, возвращает секрет + otpauth-URI. Повторный вызов до включения —
  перегенерация. Если 2FA уже включена — ошибка.
- `TwoFactorEnable.service` — проверяет код по сохранённому секрету,
  ставит `enabled=true`, генерирует и возвращает резервные коды
  (единственный раз, в открытом виде).
- `TwoFactorDisable.service` — проверяет пароль, чистит все 2FA-поля.
- `TwoFactorRegenerateBackupCodes.service` — проверяет TOTP-код, выдаёт
  новые 10 кодов.
- `TwoFactorVerify.service` — используется на входе: принимает TOTP-код или
  резервный код; резервный после употребления удаляется из списка.

### 4.3 Изменение входа (двухшаговый signin)

`POST /auth/signin` (контроллер Auth): если у пользователя
`two_factor_enabled`, вместо access-токена вернуть

```json
{ "requiresTwoFactor": true, "twoFactorToken": "<jwt 5 мин, scope: 'two-factor'>" }
```

Новый эндпоинт `POST /auth/signin/2fa` (публичный, троттлинг как у auth):
принимает `{ twoFactorToken, code }` → валидирует токен (подпись, срок,
scope), затем код через `TwoFactorVerify` → возвращает обычный
`AuthSigninResponseDto`. `Jwt.strategy`/`verifyPayload` должны **отвергать**
токен со scope `two-factor` для обычных запросов.

### 4.4 Эндпоинты управления (авторизованные, `/auth/2fa/...`)

- `GET /auth/2fa` → `{ enabled, enabledAt, backupCodesRemaining }`
- `POST /auth/2fa/setup` → `{ secret, otpauthUri }`
- `POST /auth/2fa/enable` `{ code }` → `{ backupCodes: string[] }`
- `POST /auth/2fa/disable` `{ password }`
- `POST /auth/2fa/backup-codes/regenerate` `{ code }` → `{ backupCodes }`

Ошибки — по образцу существующих exceptions (`errors: [{ type: ... }]`):
`TWO_FACTOR.INVALID_CODE`, `TWO_FACTOR.ALREADY_ENABLED`,
`TWO_FACTOR.NOT_ENABLED`, `TWO_FACTOR.INVALID_TOKEN`.

## 5. Frontend (`packages/webapp`)

### 5.1 Вход (LoginPage.tsx, shadcn + RHF + Zod)

Ответ с `requiresTwoFactor` переключает форму на второй шаг: поле кода
(6 цифр, автофокус, автосабмит по заполнению), ссылка «Использовать
резервный код» (то же поле, формат `XXXX-XXXX`), кнопка «Назад».
`twoFactorToken` живёт в состоянии страницы. Истечение токена → понятная
ошибка и возврат к паролю.

### 5.2 Настройки → «Безопасность» (`/preferences/security`)

Новая страница по образцу General (shadcn): карточка «Двухфакторная
аутентификация» со статусом и мастером включения из трёх шагов:
1. QR (вендорённый qrcodegen, SVG) + секрет текстом;
2. поле подтверждения кода;
3. показ резервных кодов с кнопкой «Скопировать» и предупреждением, что
   они показываются один раз.
Для включённой 2FA: дата включения, остаток резервных кодов,
«Перегенерировать коды» (запрос кода), «Отключить» (запрос пароля).

### 5.3 i18n

Все строки парно в `lang/{en,ru}/index.json`, ключи `two_factor.*` и
`auth.two_factor.*`; после правок — `lang-check.js`.

## 6. Безопасность

- Секрет — только зашифрованным; в API отдаётся один раз при setup.
- Резервные коды — только bcrypt-хэши; в открытом виде показываются один раз.
- Сравнение кодов — константное по времени; окно TOTP ±1 шаг.
- Полу-токен: 5 минут, scope `two-factor`, непригоден как access-токен.
- Троттлинг `/auth/signin/2fa` — существующий `auth`-троттлер.
- Отключение 2FA — только по паролю (не по коду: телефон может быть украден
  вместе с сессией).

## 7. Тестирование

- Jest: TOTP на векторах RFC 6238 (SHA-1), base32-кодек, backup-коды
  (генерация/расход/повтор), шифрование секрета (roundtrip),
  сервисы enable/disable/verify (happy + ошибки), signin-флоу с 2FA
  (полу-токен вместо access, отказ полу-токена в Jwt-гарде).
- Ручная проверка на живом бэкенде: полный цикл включения через UI +
  вход с кодом из настоящего аутентификатора.
