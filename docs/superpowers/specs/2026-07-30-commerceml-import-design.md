# ⑩ Импорт CommerceML из 1С — дизайн

Дата: 2026-07-30. Пункт дорожной карты v5 §5 п. 5 (после ⑨c).

## 1. Что есть и чего нет

Есть **выгрузка** денежных операций в 1С (`OnecExport`, формат
`1CClientBankExchange`) и импорт банковской выписки того же формата
(`BankStatementImport`). Обмена **справочниками** нет: карточки товаров и
контрагентов заводятся руками, хотя в 1С они уже есть.

## 2. Цель и рамки

Загрузить в Bigfin справочники из выгрузки 1С формата **CommerceML 2**:
товары (`import.xml`) и контрагентов (`contragents.xml` либо раздел
контрагентов внутри выгрузки). Повторная загрузка того же файла не должна
плодить дубликаты.

**В объёме (этот дизайн):**
- разбор CommerceML без внешних зависимостей;
- предпросмотр: что будет создано, что обновлено, что пропущено и почему;
- импорт с идемпотентностью по идентификатору 1С;
- страница загрузки файла с предпросмотром и подтверждением;
- флаг модуля `onec_import`.

**Вне объёма (следующие срезы):** документы CommerceML (заказы, накладные),
цены и остатки (`offers.xml`), обратная выгрузка справочников в 1С,
автоматический обмен по расписанию/HTTP-протоколу 1С.

## 3. Ограничение: XML-парсер пишем сами

В прямых зависимостях проекта нет ни одной XML-библиотеки, а добавлять
пакеты нельзя (`pnpm-lock.yaml` под защитой). `fast-xml-parser` в
`node_modules` — транзитивная зависимость AWS SDK: полагаться на неё нельзя,
она исчезнет при обновлении SDK.

Поэтому `utils/parseXml.ts` — маленький разборщик под подмножество XML,
которого достаточно для CommerceML: элементы, атрибуты, текст, CDATA,
комментарии, самозакрывающиеся теги, XML-декларация. Не поддерживаются
DTD и сущности кроме пяти стандартных (`&amp; &lt; &gt; &quot; &apos;`)
и числовых — при встрече DTD парсер бросает понятную ошибку, а не молча
портит данные. Кодировка: UTF-8 и Windows-1251 (1С выгружает и так, и так) —
определяется по XML-декларации, перекодировка через уже используемый в
проекте способ (`decodeStatement` в `BankStatementImport` делает то же
для выписок; берём оттуда подход, а не копипасту — выносим общий
`decodeBuffer` в `utils/`).

Результат разбора — простое дерево:

```ts
interface XmlNode {
  name: string;
  attrs: Record<string, string>;
  children: XmlNode[];
  text: string; // собственный текст узла
}
```

Плюс помощники `child(node, 'Имя')`, `childText(node, 'Имя')`,
`children(node, 'Имя')` — с ними извлечение читается как описание формата.

## 4. Извлечение данных

`utils/extractCommerceMl.ts` — чистые функции над деревом:

```ts
interface CommerceMlItem {
  externalId: string;   // <Ид>
  name: string;         // <Наименование>
  sku: string | null;   // <Артикул>
  unit: string | null;  // <БазоваяЕдиница>
  description: string | null;
}

interface CommerceMlContact {
  externalId: string;
  name: string;         // <Наименование>
  fullName: string | null; // <ОфициальноеНаименование>/<ПолноеНаименование>
  inn: string | null;
  kpp: string | null;
}

extractItems(root: XmlNode): CommerceMlItem[]
extractContacts(root: XmlNode): CommerceMlContact[]
```

Пути в документе (по стандарту CommerceML 2.x):
`КоммерческаяИнформация → Каталог → Товары → Товар` и
`КоммерческаяИнформация → Классификатор|Контрагенты → Контрагент`.
Товары с `<ПометкаУдаления>true` пропускаются. Записи без `<Ид>` или
`<Наименование>` пропускаются как непригодные (с причиной в отчёте).

## 5. Идемпотентность: таблица связей

Новая **тенантная** миграция `create_onec_import_links`:

| колонка | тип | смысл |
|---|---|---|
| `id` | increments | |
| `entity_type` | string(32) | `item` \| `contact` |
| `external_id` | string(191) | `<Ид>` из 1С |
| `entity_id` | integer | id сущности Bigfin |
| `created_at`/`updated_at` | timestamps | |

Уникальный индекс `(entity_type, external_id)`. Отдельная таблица, а не
колонка в `items`/`contacts`: не трогает существующие сущности и одинаково
работает для будущих типов (документы, категории).

Логика сопоставления при импорте:
1. связь по `(тип, external_id)` есть → обновляем сущность;
2. связи нет, но нашёлся контрагент с тем же **ИНН** (или товар с тем же
   **артикулом**) → привязываем к нему и обновляем (частый случай: справочник
   заводили руками до обмена);
3. иначе создаём новую сущность и связь.

Обновление **не затирает** заполненные поля Bigfin пустыми значениями из 1С.

## 6. Сервисы и API

- `ParseCommerceMlService.parse(buffer)` → `{ items, contacts, warnings }`.
- `PreviewCommerceMlImportService.preview(buffer)` → по каждому типу:
  `toCreate`, `toUpdate`, `skipped[{ externalId, reason }]`. Ничего не пишет.
- `ImportCommerceMlService.import(buffer)` → те же счётчики, но фактически
  создаёт/обновляет в одной транзакции (`UnitOfWork`).

Эндпоинты (`/onec-import`, `multipart/form-data`, поле `file`, лимит 10 МБ,
только `.xml`, право `manage all`, за флагом `onec_import`):

- `POST /onec-import/preview` → отчёт предпросмотра;
- `POST /onec-import` → отчёт импорта.

Товары создаются с `type: 'service'` по умолчанию — у CommerceML нет
сведений о складском учёте, а `inventory` требует счетов и остатков.
Контрагенты создаются как **клиенты** (`contactService: 'customer'`), если в
файле не указано иное; смена типа — ручная операция в Bigfin.

## 7. Фронт

Страница `/onec-import` (пункт меню рядом с «Выгрузка в 1С»):
выбор файла → «Проверить» (предпросмотр) → таблица «создастся N,
обновится M, пропущено K» с раскрытием причин → «Импортировать».
Строки через `intl.get`, ключи `onec_import.*` парно en/ru.

## 8. Тестирование

- Парсер XML: атрибуты, вложенность, CDATA, комментарии, самозакрывающиеся
  теги, числовые сущности, Windows-1251, понятная ошибка на DTD и на
  незакрытом теге.
- Извлечение: реальный фрагмент `import.xml` (товары с артикулом и без,
  помеченные на удаление) и фрагмент контрагентов (ИНН/КПП).
- Импорт: создание, повторный импорт того же файла (обновление, не дубли),
  подхват существующего контрагента по ИНН, отказ обновления пустыми
  значениями — на моках моделей.
- Живая проверка на стенде: загрузка примера CommerceML через UI, проверка
  созданных карточек и повторной загрузки.

## 9. Порядок работ

1. Парсер XML + декодирование (общий `decodeBuffer`).
2. Извлечение товаров и контрагентов.
3. Миграция связей + сервисы предпросмотра/импорта + эндпоинты.
4. Фронт: страница, хуки, i18n.
