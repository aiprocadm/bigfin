# ЧАСТЬ A. КОНТЕКСТ И ПРИНЦИПЫ

## A1. Зачем это ТЗ

Bigfin функционально **опережает** Финтабло, ПланФакт и Adesk: 113 серверных модулей, ~105 экранов, закрыты ДДС, ОПиУ, баланс, бюджеты, платёжный календарь, сделки, долги, кредиты, основные средства, зарплата, финмодель, интеграции с банками, 1С, МойСклад, маркетплейсами.

Но продукт унаследовал от Bigcapital информационную архитектуру **бухгалтерской программы**, а целевой пользователь — предприниматель без бухгалтерского образования. Плюс есть четыре настоящих функциональных пробела относительно рынка.

ТЗ состоит из трёх блоков, которые делаются **в этом порядке**:

| Блок | Содержание | Почему такой порядок |
|---|---|---|
| **Б1** | Переработка UX и интерфейса | Без него новые функции никто не найдёт |
| **Б2** | Консолидация по нескольким юрлицам | Самый тяжёлый архитектурный пробел, затрагивает все отчёты |
| **Б3** | Закрытие остальных пробелов, включая ИИ | Опирается на данные, приведённые в порядок в Б1–Б2 |

## A2. Правила работы (обязательны)

1. **Один этап = один PR.** Не смешивать этапы. Внутри этапа — нумерованные шаги, после каждого пауза и отчёт владельцу.
2. **Показать файл до правки.** Перед изменением показать текущий код фрагментом.
3. **Объяснять простыми словами.** Владелец не разработчик. Термины расшифровывать.
4. **Инструкция проверки и отката** после каждого шага: чем проверить + как откатить.
5. **Предупреждать о ломающих изменениях до того, как делать.** Особенно в блоке Б2 (миграции БД).
6. **Не удалять без разрешения:** файлы, ключи переводов, миграции, колонки БД.
7. **Зелёный прогон обязателен в конце каждого шага:**
   ```bash
   pnpm typecheck
   node packages/webapp/scripts/lang-check.js
   pnpm --filter @bigfin/server test
   ```
8. **Все строки — через i18n.** `intl.get('...')` или `<T id="..." />`. Новые ключи добавляются парно в `lang/en/index.json` и `lang/ru/index.json`. Хардкод английского в JSX = баг.
9. **Комментарии в коде — на русском.**
10. **Миграции — только с рабочим `down()`.** Проверять локально: `latest` → `rollback` → `latest`.
11. **Схемы БД не путать:** общее между организациями → `database/system/migrations/`, принадлежит одной организации → `database/tenant/migrations/`.
12. **Сторожевые тесты расширять, а не отключать.** Уже есть: `routes/navigationReachability.spec.ts`, `routes/routePathsAreReal.spec.ts`, `components/Dashboard/sidebarHonoursMenuGuards.spec.ts`, `containers/emptyStateTexts.spec.ts`, `containers/moduleDisabledSpeaks.spec.ts`, `containers/tableScrollOnPhone.spec.ts`.
13. **Новые экраны — только на новой дизайн-системе** (`components/ui/`, React Hook Form + Zod). Легаси на Blueprint + Formik не переписывать «по дороге».
14. **`@ts-nocheck` файлы не трогать** в рамках этого ТЗ — техдолг по типам ведётся отдельной линией (карты v84–v87).

## A4. Два пользователя продукта

| Роль | Частота | Что делает | Режим интерфейса |
|---|---|---|---|
| **Собственник** (основной) | ежедневно | Смотрит деньги, разносит операции, проверяет календарь платежей. Раз в месяц — прибыль по направлениям. | `business` |
| **Финансист / бухгалтер** (вторичный) | по задачам | Ведёт учёт, делает проводки, закрывает период, сверяет ОСВ. | `accountant` |

Механизм режимов уже есть (`constants/interfaceMode.ts`, флаг `interface_modes`), но режим «Бизнес» сегодня прячет всего 6 маршрутов из ~105.

**Правило:** режим `business` — это не «урезанный интерфейс», а **другая информационная архитектура**. Бухгалтерских сущностей в нём нет вовсе, а не спрятаны в подменю.

## A5. Три вопроса, на которые продукт обязан отвечать за 5 секунд

1. **Сколько у меня денег и хватит ли до конца месяца?** → Главная + платёжный календарь
2. **Сколько я на самом деле заработал?** → ОПиУ
3. **Куда утекают деньги?** → ДДС по статьям

Экран, не отвечающий ни на один из этих вопросов, не имеет права быть в первом уровне меню.

## ЭТАП 2. Главный экран (дашборд)

**Файлы:** `containers/Homepage/*`, `components/Dashboard/DashboardSummary.tsx`, `modules/Dashboard/queries/*`

### 2.1. Что не так сейчас

`HomepageContent.tsx` — шесть текстовых секций подряд, ни одного графика. При этом компонент `DashboardSummary.tsx` (KPI-плитки + столбчатый график доходов/расходов на recharts) **написан, работает и подключён только к Storybook**. В приложении его нет.

### 2.2. Состав новой главной

**Блок 1. Полоса ключевых показателей** — 4 плитки, каждая кликабельна и ведёт в соответствующий отчёт:

| Плитка | Значение | Подпись |
|---|---|---|
| Деньги на счетах | сумма остатков | изменение за период, ↑/↓ |
| Доходы | сумма за период | % к прошлому периоду |
| Расходы | сумма за период | % к прошлому периоду |
| Прибыль | сумма за период | рентабельность, % |

Переключатель периода в шапке: Месяц / Квартал / Год / Произвольный. Выбор запоминается между сессиями.

**Блок 2. График «Деньги по месяцам»** — столбцы доходов и расходов + линия остатка на счетах, 12 месяцев, тултип с суммами при наведении. Главный график продукта.

**Блок 3. «Требует внимания»** — карточки-действия, показываются только непустые:
- «N операций ждут разноски» → в «Операции» с включённым фильтром
- «Кассовый разрыв 14 марта: не хватает 340 000 ₽» → в платёжный календарь
- «Просрочена дебиторка на N ₽ по M контрагентам» → в долги
- «N заявок на оплату ждут согласования» → в заявки
- «Бюджет по статье "Реклама" превышен на 23%» → в бюджеты

**Блок 4. Остатки по счетам** — список с остатками, клик → операции по счёту.

**Блок 5. Топ-5 статей расходов** — горизонтальные полосы с суммами и долей в общих расходах.

**Блок 6. Первые шаги** — существующий `FirstStepsSection`, показывать **только пока не пройдены**, затем скрыть навсегда.

### 2.3. Серверная часть

Сегодня есть только `GetMoneySummary` и `GetTaxEstimate`.

Создать `GET /dashboard/overview?from=&to=&legalEntityId=`, отдающий **всё для главной одним ответом**: плитки, ряды графика, остатки по счетам, топ статей, счётчики «требует внимания». Пять отдельных запросов на главной недопустимы.

`GetMoneySummary` использовать как источник для плиток, логику не дублировать. **Обязателен Jest-тест на сверку:** суммы на главной совпадают с суммами соответствующих отчётов до копейки.

Кеширование агрегатов — через Redis, инвалидация по событию изменения проводок.

### 2.4. Приёмка

- Главная грузится одним запросом, время ответа < 800 мс на организации с 50 000 операций.
- Все цифры кликабельны и ведут туда, где раскладываются построчно.
- Пустая организация показывает не прочерки, а «начните с подключения счёта» с кнопкой.

## ЭТАП 3. Экран «Операции»

**Файлы:** `containers/CashFlow/AccountTransactions/*` (24 файла), `CategorizeTransaction/*`, `CategorizeTransactionAside/*`

### 3.1. Целевая конструкция

**Один список операций по всем счетам сразу.** Счёт — это фильтр, а не отдельный экран.

**Шапка:**

- Фильтры: юрлицо (блок Б2), счёт, статья, контрагент, проект/направление, сумма от–до, тип (поступление / списание / перевод)
- Поиск по назначению платежа
- Кнопки: «Добавить операцию», «Импорт выписки», «Экспорт в Excel»

**Полоса состояния:** «12 операций без статьи» — кнопка-фильтр, включающая режим разноски.

**Таблица:**

| Колонка | Поведение |
|---|---|
| Дата | сортировка |
| Контрагент | |
| Назначение | обрезается, полное — в тултипе |
| Статья | **редактируется прямо в строке**, выпадающий список с поиском |
| Проект / направление | редактируется в строке |
| Юрлицо | колонка появляется, если юрлиц больше одного |
| Сумма | цветом: поступление и списание визуально различимы |
| Счёт | |

**Массовые действия** (обязательно): выделить несколько → назначить статью / проект / юрлицо / удалить.

**Разнос одним движением:** у операции без статьи показывать подсказку от правила или от похожей прошлой операции — «Похоже на "Аренда офиса". Применить?» → один клик. Логика правил уже есть в `BankRules` и `BankingTranasctionsRegonize`, её нужно вывести в строку таблицы. Подсказки на основе истории — этап 12 (ИИ).

## ЭТАП 4. Отчёты

**Файлы:** `containers/FinancialStatements/*` (включая существующую папку `v2`), `modules/FinancialStatements/*`

### 4.1. Вход в раздел

Раздел открывается не списком из 20 позиций, а тремя большими карточками:

| Карточка | Подпись под названием |
|---|---|
| **Деньги (ДДС)** | Куда приходят и уходят деньги |
| **Прибыль (ОПиУ)** | Сколько заработал бизнес на самом деле |
| **Баланс** | Чем владеет компания и кому должна |

Ниже — «Другие отчёты» свёрнутым списком с группировкой.

### 4.2. Единый каркас отчёта

Все три главных отчёта получают одинаковую конструкцию:

**Шапка:** период · сравнение (с прошлым периодом / с планом) · разрез (месяцы / кварталы / годы) · фильтры: юрлицо, проект, направление.

**График над таблицей:** ДДС — поступления/выплаты по месяцам; ОПиУ — выручка и прибыль по месяцам; Баланс — структура активов и пассивов.

**Тело:** таблица со сворачиваемыми группами статей. **Клик по любой сумме раскрывает список операций, из которых она сложилась (drill-down).** Это ключевое требование — без него пользователь не доверяет цифрам и уходит обратно в Excel.

**Действия:** экспорт в Excel, экспорт в PDF, печать.

### 4.3. ОПиУ: два метода в одном экране

Переключатель «Кассовый метод / Метод начисления» прямо в шапке (флаг `accrual_pnl` уже есть). Рядом — пояснение в одну строку человеческим языком, чем они отличаются.

### 4.4. План-факт

В ДДС и ОПиУ добавить колонки «План» и «Отклонение», если по периоду заведён бюджет (`modules/Budgets`). Данные для этого уже есть — нужен только вывод.

## ЭТАП 5. Единый визуальный язык

Это прямой ответ на «не нравится дизайн». Дело не в палитре, а в том, что систем две.

### 5.1. Правило миграции

**Не переписывать 667 файлов.** Мигрировать по экранам, в порядке частоты использования:

1. Главная (сделана на этапе 2)
2. Операции (этап 3)
3. Отчёты (этап 4)
4. Платёжный календарь
5. Бюджеты
6. Сделки и проекты
7. Контрагенты
8. Настройки

Смешение систем **внутри одного экрана — запрещено**. Между экранами — временно допустимо. Всё, что ниже в списке и не тронуто, остаётся на Blueprint до отдельного решения.

### 5.2. Дизайн-токены

Зафиксировать в `components/ui/colors.mdx` и конфиге Tailwind:

# ЧАСТЬ C. БЛОК 2 — КОНСОЛИДАЦИЯ ПО НЕСКОЛЬКИМ ЮРЛИЦАМ

Самый тяжёлый пробел. Финтабло и ПланФакт продают это первым пунктом: «единый отчёт по всем юрлицам — видите общую прибыль, долги и остатки, даже если у вас несколько ООО и ИП».

## C1. Архитектурное решение (читать обязательно до начала работ)

### C1.1. Почему нельзя «несколько тенантов»

Bigfin использует **отдельную базу данных на организацию**: `TenantDBManager.ts` выполняет `CREATE DATABASE` для каждого тенанта. Запросы между базами MariaDB в такой схеме невозможны без отдельного слоя агрегации. Путь «каждое юрлицо = свой тенант, сверху консолидатор» означает:
- распределённые запросы по N базам на каждый отчёт,
- отдельное хранилище агрегатов,
- дублирование справочников (статьи, контрагенты, проекты) в каждой базе.

Это месяцы работы и постоянный источник расхождений.

### C1.2. Принятое решение

**Один тенант = одна группа компаний.** Юрлицо становится **измерением внутри тенанта**, как проект или направление.

Обоснование: в таблице проводок `accounts_transactions` измерения уже предусмотрены — там есть `branch_id` (миграция `20220125121920_add_branch_column_to_accounts_transactions.ts`), `project_id`, `contact_id`. Добавление ещё одного измерения — штатная операция, а не переделка архитектуры.

### C1.3. Почему не переиспользовать Branches

`Branch` (`modules/Branches/models/Branch.model.ts`) — это подразделение: название, код, адрес, город, телефон, почта, сайт. Реквизитов (ИНН/КПП/ОГРН), системы налогообложения и признака «своё юрлицо» там нет.

Главное — **это ортогональные измерения**: у группы может быть 3 юрлица и 5 подразделений, и они пересекаются (склад в Питере обслуживает и ООО, и ИП). Схлопывание их в одну сущность закроет возможность резать отчёты по обоим срезам.

**Решение:** новая сущность `LegalEntity`. `Branch` остаётся как есть.

## ЭТАП 7. Консолидированная отчётность

### 7.1. Фильтр юрлица во всех отчётах

Единый компонент фильтра в шапке каждого отчёта:

- **Все юрлица (консолидировано)** — по умолчанию
- Отдельное юрлицо
- Произвольный набор (чекбоксы) — для случаев вроде «только ООО, без ИП»

Серверная часть: параметр `legalEntityIds?: number[]` во все DTO отчётов (`modules/FinancialStatements/modules/*/`). Отсутствие параметра = все юрлица.

### 7.2. Внутригрупповые обороты (ключевая часть)

Это то, что отличает настоящую консолидацию от простого суммирования. Если ООО перевело ИП 500 000 ₽, то в сумме по группе **не появилось ни дохода, ни расхода** — деньги остались внутри. Без исключения таких оборотов консолидированный ОПиУ завышает и выручку, и расходы.

**Реализация:**

1. Перевод между счетами разных юрлиц автоматически помечается признаком `is_intercompany = true`.
2. В ручной операции — переключатель «Внутригрупповая операция» с пояснением: «Деньги перемещаются между вашими юрлицами. В отчёте по группе такая операция не считается доходом или расходом».
3. В режиме «Все юрлица» внутригрупповые обороты **исключаются** из ОПиУ и ДДС (остатки на счетах при этом сходятся).
4. В режиме одного юрлица — **показываются**, потому что для этого юрлица это реальный доход или расход.
5. Отдельный отчёт «Внутригрупповые обороты» за период: кто кому и сколько. Нужен для сверки.

**Обязательные тесты:**
- Консолидированный ОПиУ = сумма ОПиУ юрлиц минус внутригрупповые обороты.
- Консолидированный баланс сходится: активы = пассивы.
- Сумма остатков по счетам всех юрлиц = остаток в консолидированном ДДС.

### 7.3. Что показывают консолидированные отчёты

| Отчёт | Особенности консолидации |
|---|---|
| **ДДС** | Остатки и потоки по всем счетам всех юрлиц. Внутригрупповые переводы — отдельной свёрнутой строкой, не в статьях. |
| **ОПиУ** | Выручка и расходы группы без внутренних оборотов. Разрез по юрлицам — колонками. |
| **Баланс** | Активы и пассивы группы. Взаимные долги юрлиц взаимоисключаются. |
| **Долги** | Дебиторка и кредиторка перед внешними контрагентами. Внутренние долги — отдельной вкладкой. |
| **Платёжный календарь** | Все платежи группы на одной ленте, цветовая метка юрлица. Кассовый разрыв считается и по группе, и по каждому юрлицу отдельно (у ООО могут быть деньги, а у ИП — нет). |

### 7.4. Многовалютность

Модуль `Currencies` уже есть. Если у юрлиц разные базовые валюты, консолидация ведётся в валюте группы (настройка организации) по курсу на дату операции. Курсовые разницы — отдельной строкой в ОПиУ.

## ЭТАП 8. Юрлицо в операционных сценариях

### 8.1. Счета

При создании счёта — обязательный выбор юрлица. Операции по счёту наследуют юрлицо автоматически; вручную переопределять нельзя (иначе остатки разъедутся).

### 8.2. Наличные и карты физлица

Отдельный тип счёта «Личные средства» с привязкой к юрлицу (или без привязки — «личный кошелёк собственника»). Нужно, потому что в малом бизнесе часть расходов идёт с личной карты. Операции с такого счёта в консолидированном ОПиУ учитываются, в балансе юрлица — как заём от учредителя.

### 8.3. Печатные формы

Модуль `RuPrintForms` сегодня берёт реквизиты организации. Переключить на реквизиты **юрлица документа**: счёт на оплату от ООО должен содержать реквизиты ООО, а не общие настройки аккаунта.

### 8.4. Права доступа

В `modules/Roles` добавить ограничение по юрлицам: бухгалтеру ИП видно только ИП, владельцу — всё. Использовать существующий `AbilitySchema` и `Permission.guard.ts`.

### 8.5. Приёмка блока Б2

- Организация с одним юрлицом не видит никаких изменений в интерфейсе.
- Организация с тремя юрлицами получает консолидированные ДДС, ОПиУ и баланс одним кликом.
- Переключение «все юрлица → одно юрлицо» не требует перезагрузки страницы.
- Все три теста сходимости из 7.2 зелёные.
- Отчёты по группе на 100 000 операций строятся менее чем за 3 секунды.

## ЭТАП 10. Разделение операции на части

Одна платёжка на 100 000 ₽ = аренда 70 000 + коммунальные 30 000. Сегодня это невозможно — операция целиком уходит в одну статью, и отчёты врут.

**Модель:** родительская операция + дочерние строки. Суммы дочерних обязаны сходиться с родительской (валидация на сервере). В отчёты попадают дочерние, в выписке и сверке с банком — родительская.

**Интерфейс:** в строке операции — действие «Разделить». Открывается панель: добавить строку, сумма, статья, проект, юрлицо. Внизу — «Осталось распределить: 0 ₽», кнопка сохранения неактивна, пока остаток не ноль.

**Правила разноски** (`BankRules`) должны уметь делить автоматически: условие → разбить в процентах между статьями.

## ЭТАП 12. ИИ: разнос операций по истории

**Важно:** в проекте сегодня нет ни одной ИИ-интеграции. `BankingTranasctionsRegonize` — это сопоставление по правилам (`matchTextCondition`, `matchNumberCondition`), обучения нет.

### 12.1. Решение: без внешнего ИИ

Разнос операций **не требует большой языковой модели** и не должен от неё зависеть. Задача классическая: по назначению платежа, контрагенту, сумме и счёту предсказать статью. Решается локально:

1. **Точное совпадение по контрагенту:** если 90% прошлых операций с этим контрагентом шли в статью X — предлагать X. Покрывает большинство случаев.
2. **Наивный байесовский классификатор по словам назначения платежа**, обучаемый на истории конкретного тенанта. Хранить модель в таблице `categorization_model` (веса слов по статьям), переобучать фоновой задачей BullMQ раз в сутки и после каждых 50 ручных разносок.
3. **Порог уверенности:** ниже 70% — подсказка не показывается. Пользователь никогда не должен видеть неуверенную догадку.

**Преимущества такого решения:** данные не покидают контур (критично для тех, кто ставит Bigfin на свой сервер), нет платы за токены, работает мгновенно, объяснимо («предложено, потому что 12 из 14 платежей этому контрагенту шли в эту статью»).

### 12.2. Интерфейс

- В строке операции без статьи — бледная подсказка со статьёй и кнопкой «Применить».
- Принятие подсказки — один клик, отклонение — просто выбор другой статьи.
- Обе реакции идут в обучение.
- Массовое действие: «Применить все подсказки с уверенностью выше 90%» — кнопка над таблицей с указанием количества операций.
- В настройках — переключатель «Подсказывать статьи» и счётчик точности: «За месяц: предложено 240, принято 218 (91%)».

Это то, что Финтабло, ПланФакт и Adesk в 2026 году вынесли в главную маркетинговую ценность.

### 13.1. Жёсткие ограничения (нарушение = откат этапа)

1. **Модель не считает цифры.** Все числа приходят из уже посчитанных агрегатов Bigfin. Модель формулирует наблюдение, а не вычисляет.
2. **В модель не уходят сырые операции, реквизиты, ФИО, назначения платежей.** Только агрегаты: суммы по статьям, по месяцам, по проектам, доли, отклонения.
3. **Каждый вывод кликабелен** и ведёт в отчёт, где цифра раскладывается построчно.
4. **Отключаемо флагом** `ai_analyst`, по умолчанию выключено.
5. **Настройка тенанта «не передавать данные во внешние сервисы»** — при её включении раздел недоступен, а не деградирует молча.

### 13.2. Выбор провайдера

Продукт нацелен на реестр российского ПО и развёртывание на своих серверах. Провайдер выносится за интерфейс `AiProvider` с реализациями:
- YandexGPT / GigaChat — для облачной версии,
- локальная модель через OpenAI-совместимый endpoint — для self-hosted,
- «выключено» — заглушка.

Ключи и адрес endpoint — в настройках организации, не в коде.

### 13.3. Что генерируется

Блок «Что говорят цифры» на главной и внизу каждого из трёх главных отчётов, 3–5 наблюдений:

- «Закупки выросли в 2,8 раза ко II кварталу. Проверьте, это рост объёмов или цен.»
- «Направление "Розница" третий месяц убыточно: −180 000 ₽ за квартал.»
- «Постоянные расходы составляют 64% выручки — при падении продаж на 15% бизнес уйдёт в минус.»
- «Дебиторка выросла на 40%, выручка — на 8%. Деньги замораживаются в долгах клиентов.»

Формируется раз в сутки фоновой задачей, кешируется. Не по запросу — иначе дорого и медленно.

### 13.4. Приёмка

- Ни одно число в тексте не расходится с отчётом.
- Отключение флага полностью убирает раздел, ничего не ломая.
- Тест: в промпт не попадает ни одно поле из «чёрного списка» (назначение платежа, ИНН, ФИО, названия контрагентов).

## ЭТАП 14. ИИ-чат по финансам

Делается **только после этапа 13** и только если он показал себя.

Пользователь спрашивает словами: «Сколько мы потратили на рекламу в прошлом квартале?», «Какой проект самый прибыльный?», «Когда ближайший кассовый разрыв?».

**Архитектура:** модель не получает доступ к базе. Ей даётся набор инструментов (function calling), каждый из которых — вызов существующего API отчётов с параметрами. Модель выбирает инструмент и формулирует ответ по возвращённым агрегатам. Ответ всегда сопровождается ссылкой на отчёт.

Ограничения из 13.1 действуют полностью.

## ЭТАП 15. Публичный API и вебхуки

OpenAPI-спека уже генерируется (`modules/CLI/commands/OpenApiExport.command.ts`), SDK собирается в `shared/sdk-ts/`.

Нужно:
- Смонтировать Swagger UI на `/api/docs` (закрыть для production за флагом).

- Публичная страница документации с примерами на curl и на TypeScript SDK.

# ЧАСТЬ E. ОБЩИЕ ТРЕБОВАНИЯ

## E1. Производительность

| Сценарий | Целевое время |
|---|---|
| Главная (1 запрос) | < 800 мс на 50 000 операций |
| Список операций, страница | < 500 мс |
| ОПиУ за год по группе юрлиц | < 3 с на 100 000 операций |
| Разнос операции (сохранение) | < 200 мс |

Тяжёлые агрегаты кешировать в Redis с инвалидацией по событию изменения проводок. Индексы под все новые разрезы (юрлицо, статья, проект).

## E2. Безопасность

- Права по юрлицам через существующий `AbilitySchema` (этап 8.4).
- ИИ-этапы: чёрный список полей, проверяемый тестом.
- Не логировать назначения платежей и реквизиты в открытом виде.
- Хуки блокировки правок `.env`, `pnpm-lock.yaml`, `*.key`, `docker-compose.prod.yml` — уже есть, не отключать.

## E3. Тесты

| Тип | Требование |
|---|---|
| Серверная бизнес-логика | Jest-спека рядом с модулем. Для консолидации и внутригрупповых оборотов — обязательно. |
| Сходимость отчётов | Отдельный набор: главная = отчёты; консолидация = сумма минус внутренние обороты; баланс сходится. |
| Миграции | `latest` → `rollback` → `latest` локально перед PR. |
| Витрина | Расширить существующие сторожевые спеки, новые не отключать. |
| E2E | Playwright: основной суточный сценарий (вход → разнос 3 операций → календарь). |

## E4. Переводы

После каждой правки `lang/*` — `node packages/webapp/scripts/lang-check.js`. Русский стиль: «счёт», не «инвойс»; «учёт», не «аккаунтинг»; кнопки в императиве; «вы» с маленькой буквы; в ошибках конкретика.

# ЧАСТЬ G. ЧЕГО ДЕЛАТЬ НЕ НАДО

- **Не удалять бухгалтерский функционал.** Он нужен второму типу пользователя и остаётся в режиме «Бухгалтер».
- **Не делать юрлица отдельными тенантами.** Причины в C1.1. Это тупик.
- **Не схлопывать юрлица с подразделениями (Branches).** Измерения ортогональные.
- **Не начинать со сплошной миграции Blueprint → shadcn.** 667 файлов, месяцы без видимого результата. Только по экранам.
- **Не отдавать расчёт цифр языковой модели.** Никогда. Модель формулирует, считает Bigfin.
- **Не отправлять во внешний ИИ сырые операции и реквизиты.**
- **Не трогать `@ts-nocheck` файлы** в рамках этого ТЗ.
- **Не добавлять функций сверх перечисленных.** Продукту не хватает не функций, а входа в них.
- **Не ломать парность переводов.**
