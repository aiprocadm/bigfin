## 0. Зачем этот документ и как он соотносится с роадмапом

Основатель попросил спроектировать «каркас + планирование» — слой, который превращает бухгалтерский движок Bigfin в управленческий учёт уровня Fintablo/PlanFact. В роадмапе от 2026-05-27 эта тема разнесена на три отдельных под-проекта (④/⑤/⑥). По осознанному решению основателя (брейншторм 2026-05-29) они **объединяются в одну спецификацию**, потому что у них общая модель данных («статьи» и «направления»), и проектировать их по отдельности — значит трижды возвращаться к одному и тому же каркасу.

**Что это меняет в роадмапе:** ④/⑤/⑥ помечаются как «консолидированы в `2026-05-29-management-core-and-planning-design.md`». Их scope не теряется — он переезжает сюда целиком, включая сценарии бюджета (роадмап §4.9).

**Что НЕ меняется:** все сквозные решения роадмапа (§4) действуют и здесь — additive-миграции, режим «Бизнес/Бухгалтер», парность EN↔RU, RUB, feature flags, проприетарный копирайт, минимум новых зависимостей.

## 1. Контекст и цели

### Что строим

Управленческий слой поверх существующего бухгалтерского движка:

1. **Каркас** — «статьи учёта» (управленческие категории доходов/расходов с любой вложенностью) и «направления» (разрез бизнеса).
2. **Платёжный календарь** — прогноз поступлений/выплат по дням, остаток на счетах, подсветка кассовых разрывов.
3. **Бюджеты БДДС / БДиР** — план по статьям × периодам, с тремя сценариями (опт./реал./пес.).
4. **План-факт** — отчёт сравнения плана с фактом по статьям и периодам.

### Целевая аудитория продукта

Предприниматели без бухгалтерского образования. Им непонятен план счетов — им понятны «откуда пришли деньги» и «куда ушли». Статьи говорят на их языке.

### Критерий успеха

В режиме «Бизнес» пользователь может: построить дерево статей и направлений; увидеть платёжный календарь с предупреждением о кассовом разрыве; задать бюджет БДДС/БДиР по статьям на квартал/год в трёх сценариях; открыть отчёт план-факт. Существующий бухгалтерский функционал (план счетов, проводки, ОПиУ/ДДС/Баланс) продолжает работать без изменений в режиме «Бухгалтер».

### Что в коде уже есть (фундамент, на который опираемся)

- **Двойная запись:** проводки в `accounts_transactions` (debit/credit, account_id, date, reference_type/reference_id) и `manual_journals_entries`.
- **Два аналитических разреза прямо на проводках:** `branch_id` и `projectId` (добавлены миграциями 2022 г. в `accounts_transactions` и `manual_journals_entries`). **Это ключ — направления переиспользуют существующий разрез, а не строятся с нуля.**
- **План счетов:** таблица `accounts` с `parent_account_id` (дерево до 5 уровней) и `account_type` (тип определяет нормальное сальдо дебет/кредит).
- **Движок отчётов:** ОПиУ/ДДС/Баланс уже считаются (`FinancialStatements/modules/*`), **группируют строки по счетам**, поддерживают экспорт PDF/Excel и фильтр по ветке (`FinancialSheetBranchesQueryDto`).

### Чего в коде нет (и это надо построить)

- Управленческого слоя «статей» поверх счетов.
- Понятия «плановая/будущая операция» — нет ни одной таблицы для планирования.
- Динамической категоризации ДДС (сейчас разнесение по разделам ДДС захардкожено по типам счетов).

## 3. Ключевое архитектурное решение: модель «статей»

Это развилка, определяющая всю работу. Три варианта:

| # | Подход | Плюсы | Минусы |
|---|---|---|---|
| A | **Статьи = переименованный план счетов** (роадмап ②b буквально) | Дешевле всего, движок отчётов не трогаем | План счетов скован бух-семантикой; негибко; «статья ДДС ≠ статья ОПиУ» не выразить |
| B | **Статьи = новый разрез `article_id` на проводках** (первичное предложение 2026-05-29) | Максимальная гибкость, как у Fintablo | Колонка на огромные таблицы проводок + бэкафилл; **движок отчётов придётся переучивать** (он группирует по счетам); две параллельные классификации |
| C ⭐ | **Статьи = управленческая надстройка-дерево над счетами** (рекомендуется) | Гибкое RU-дерево, НЕ трогаем проводки, движок отчётов переиспользуем через свёртку «счёт→статья»; идеально ложится на режим «Бизнес/Бухгалтер» | Одна проводка категоризуется на уровне своего счёта (нельзя разрезать один счёт по разным статьям внутри периода) |

> **★ Обоснование выбора C.** Существующий движок отчётов группирует по счетам. Вариант C сохраняет это: факт считается по счетам как сейчас, затем **сворачивается в статьи по карте соответствия** — движок не переписываем. При этом «статьи» — это отдельное удобное дерево с RU-названиями любой вложенности, независимое от кодов и типов счетов. В режиме «Бухгалтер» видны счета, в режиме «Бизнес» — статьи (= группы счетов). Минус варианта C (нельзя разнести один счёт по разным статьям) на практике некритичен: каждая проводка и так привязана к одному счёту, а для категоризации «приход/расход» аудитории без бухгалтерии гранулярности счёта достаточно.

**Решение к подтверждению основателем:** принимаем вариант **C**. (Если позже понадобится разрезать один счёт по статьям — мигрируем к гибриду B+C точечно, без переделки всего.)

## 4. Модель данных

Все таблицы — в **tenant**-схему (принадлежат одной организации). Миграции — через скилл `make-migration`, строго с рабочим `down()`. Всё additive: новые таблицы + nullable-колонки, существующее не ломаем.

### 4.1 Статьи учёта — `management_articles`

| Колонка | Тип | Назначение |
|---|---|---|
| `id` | increments | PK |
| `name` | string | Название статьи (RU), напр. «Выручка», «Аренда» |
| `parent_id` | integer nullable, FK→self | Вложенность (дерево любой глубины) |
| `kind` | enum `income`/`expense` | Доход или расход (для ОПиУ/БДиР) |
| `cashflow_section` | enum nullable `operating`/`investing`/`financing` | Раздел ДДС (для группировки в БДДС). nullable = не участвует в ДДС |
| `sort_order` | integer | Порядок в дереве |
| `active` | boolean default true | Мягкое отключение |
| `timestamps` | | created_at / updated_at |

### 4.2 Соответствие «статья ↔ счета» — `management_article_accounts`

| Колонка | Тип | Назначение |
|---|---|---|
| `article_id` | FK→management_articles | |
| `account_id` | FK→accounts | Какие счета сворачиваются в эту статью |

Связь: одна статья собирает 1..N счетов; один счёт по умолчанию входит в одну статью (UNIQUE по `account_id` в v1 — упрощает свёртку и исключает двойной счёт). Дефолтную карту наполняет сид ②b при создании RU-организации.

### 4.3 Направления

**Новых таблиц не создаём.** Направление = существующий разрез `branch_id` (первичный, есть на большинстве таблиц проводок), при необходимости второй разрез — `projectId`. В режиме «Бизнес» лейбл `branch` → «Направление». **Решение к подтверждению:** считаем «направление» бизнес-сегментом (Розница/Опт/Услуги) и кладём его на `branch_id`. Если основателю нужны и физические филиалы, и сегменты одновременно — тогда заводим отдельный разрез `direction_id` (отложенный вариант, помечен в Открытых вопросах).

### 4.4 Плановые операции — `planned_operations`

Сущность, которой в коде нет вообще. Питает платёжный календарь и факт-независимую часть БДДС.

| Колонка | Тип | Назначение |
|---|---|---|
| `id` | increments | PK |
| `direction` | enum `inflow`/`outflow` | Поступление или выплата |
| `amount` | decimal(13,3) | Сумма |
| `currency_code` | string(3) | Валюта (default RUB) |
| `planned_date` | date, index | Когда ожидается |
| `article_id` | FK→management_articles nullable | Статья |
| `branch_id` | integer nullable | Направление |
| `project_id` | integer nullable | Проект |
| `cashflow_account_id` | FK→accounts nullable | С какого/на какой денежный счёт |
| `contact_id` | FK→contacts nullable | Контрагент |
| `status` | enum `planned`/`confirmed`/`done`/`cancelled` | Жизненный цикл |
| `source_type`/`source_id` | string/integer nullable | Ссылка на источник (invoice/bill), если сгенерировано автоматически |
| `recurrence` | jsonb nullable | Правило повтора (аренда, зарплата): частота, интервал, дата окончания |
| `description` | string nullable | Заметка |
| `timestamps` | | |

### 4.5 Бюджеты — `budgets` и `budget_lines`

> Если в кодовой базе уже есть модуль Budget (роадмап ⑤ упоминает «существующий модуль Budget») — **сначала проверяем при планировании** и расширяем его, а не дублируем. Ниже — целевая структура независимо от того, новая она или расширение существующей.

**`budgets`:** `id`, `name`, `type` enum `bdds`(БДДС)/`bdir`(БДиР), `fiscal_year`, `period_granularity` enum `month`/`quarter` (v1 = month), `active_scenario` enum `optimistic`/`realistic`/`pessimistic` default `realistic`, `branch_id` nullable (бюджет на направление или общий), `timestamps`.

**`budget_lines`:** `id`, `budget_id` FK, `article_id` FK, `period` date (первый день месяца/квартала), `scenario` enum default `realistic` (роадмап §4.9 — additive), `planned_amount` decimal(13,3), `timestamps`. UNIQUE по (`budget_id`,`article_id`,`period`,`scenario`).

## 5. Возможности

### 5.1 Каркас: статьи и направления

- CRUD статей: дерево с drag-and-drop переупорядочиванием (в зависимостях уже есть `react-sortablejs`), создание/переименование/вложение, привязка счетов к статье.
- Сид дефолтного RU-дерева для новой организации (Выручка / Себестоимость / Аренда / ФОТ / Маркетинг / Налоги / Прочее — синхронно с ②b).
- Направления: справочник на базе `branch_id` (используем существующий модуль Branches, лейбл в режиме «Бизнес»).
- **Бэкафилл не нужен** (в отличие от варианта B): факт сворачивается в статьи на лету через карту `management_article_accounts`, исторические проводки не трогаем.

### 5.2 Платёжный календарь

Источники строк календаря:
1. **Ожидаемые из открытых обязательств** — неоплаченные `sales_invoices` (по `due_date` → ожидаемый приток) и `bills` (по `due_date` → ожидаемый отток). Берём из существующих данных, модуль «Долги» не требуется.
2. **Ручные плановые операции** — `planned_operations` со статусом `planned`/`confirmed`.
3. **Повторяющиеся** — развёртка `recurrence` (аренда, зарплата) на горизонт календаря.

Расчёт: на каждый день = (остаток денежных счетов на начало) + Σ притоков − Σ оттоков. **Кассовый разрыв** = день, где прогнозный остаток < 0 → подсветка красным + предупреждение «через N дней кассовый разрыв на сумму X».

UI: горизонт по умолчанию — месяц вперёд, переключение неделя/месяц/квартал. Поскольку готового календарного компонента в новом стеке нет, строим **табличную ленту по дням** (Tailwind-grid) — проще и мобильнее, чем классический календарь-сетка. Добавление ручного плана — модалка на React Hook Form + Zod.

### 5.3 Бюджеты БДДС / БДиР (со сценариями)

- Экран-сетка: статьи в строках (дерево с раскрытием), периоды (месяцы) в столбцах, ввод план-сумм в ячейки.
- Тип бюджета: **БДДС** (по денежным потокам, группировка по `cashflow_section`) или **БДиР/БДР** (по доходам/расходам, группировка по `kind`).
- Три сценария на тот же период (опт./реал./пес.), переключатель активного + режим «сравнить три рядом» (роадмап §4.9). По умолчанию UI показывает только реалистичный (риск №14 роадмапа — не путать пользователя).
- Шаблоны бюджета по типу бизнеса — опционально, в конце этапа.

### 5.4 План-факт

- Новый отчёт в движке `FinancialStatements` по существующему паттерну (репозиторий ledger + table-injectable + экспортеры PDF/Excel — всё переиспользуется).
- Колонки: Статья | План (из `budget_lines` активного сценария) | Факт (агрегация ledger по счетам → свёртка в статью) | Отклонение ₽ | Отклонение %.
- Фильтры: период, направление (`branch_id`), сценарий, тип (БДДС/БДиР).

## 6. Этапы реализации

Спека цельная, но строим по этапам, с паузами (правило «маленькие шаги»). **Старт — после Ф1 роадмапа.** (Здесь «Этап» — внутренний порядок этой спеки; «Фаза/Ф» — фазы роадмапа. Не путать.) Каждый этап под своим feature flag, по умолчанию выключен.

| Этап | Содержание | Flag | Самодостаточная ценность |
|---|---|---|---|
| **Этап 0 — Каркас** | `management_articles` + `management_article_accounts`, сид RU-дерева, CRUD-дерево статей, направления на `branch_id`, свёртка отчётов «счёт→статья» | `FEATURE_MGMT_ARTICLES` | Отчёты ОПиУ/ДДС начинают говорить «статьями» в режиме «Бизнес» |
| **Этап 1 — Платёжный календарь** | `planned_operations` + повторы, расчёт остатка и разрывов, экран-лента | `FEATURE_PAYMENT_CALENDAR` | Видно кассовые разрывы заранее — «вау»-фича |
| **Этап 2 — Бюджеты** | `budgets`/`budget_lines` (+`scenario`), экран-сетка, 3 сценария | `FEATURE_BUDGETS` | План по статьям на год |
| **Этап 3 — План-факт** | отчёт сравнения в `FinancialStatements` | (под `FEATURE_BUDGETS`) | Контроль исполнения бюджета |

Зависимости этапов: Этап 1 и Этап 2 требуют Этап 0 (нужны статьи). Этап 3 требует Этап 2 (нужен план).

## 7. Что НЕ входит (anti-scope)

- **Разделение кассового и начисленного метода.** v1 — кассовый метод (проще для аудитории). Раздельные статьи ДДС vs ОПиУ на одной операции — backlog.
- **Гибкий разрез `article_id` на проводках** (вариант B) — только если упрёмся в ограничение варианта C.
- **Полноценный модуль «Долги»** (старение по корзинам, напоминания) — это ⑭, отдельно. Здесь только запрос открытых обязательств для календаря.
- **Правила автораспределения общих расходов** (роадмап §4.10) — это ⑦ Сделки.
- **Интеграции** (банки РФ, 1С, маркетплейсы), **ИИ-аналитик**, **мобильное приложение** — отдельные темы роадмапа.
- **Формулы между сценариями бюджета** (пес. = реал.×0.8) — backlog (роадмап открытый вопрос №5).
- **Автоматическая отправка платежей в банк** из календаря — требует ЭКО-сертификации, не входит.

## 8. Сквозные решения (наследуются из роадмапа §4)

- **Миграции:** только additive (новые таблицы, nullable-колонки). Tenant-схема. Обязательный рабочий `down()`, тест `latest→rollback→latest` локально. Скилл `make-migration`.
- **Режим «Бизнес/Бухгалтер»:** статьи и планирование — фичи режима «Бизнес». В «Бухгалтер» — счета как сейчас.
- **i18n:** все строки экранов — через `intl.get(...)`/`<T id=.../>`, парность EN↔RU, после правок — `node packages/webapp/scripts/lang-check.js`. Скилл `i18n-add-string`. Сообщения валидации Zod — тоже через i18n (не хардкодить RU в схемах).
- **Валюта:** суммы в RUB по умолчанию, мультивалютность сохраняется.
- **Feature flags:** `FEATURE_MGMT_ARTICLES`, `FEATURE_PAYMENT_CALENDAR`, `FEATURE_BUDGETS`. Откат = выключить флаг.

## 10. Риски

| # | Риск | Митигация |
|---|---|---|
| 1 | Свёртка «счёт→статья» даёт расхождение с бухгалтерскими отчётами | Один счёт = одна статья (UNIQUE на `account_id`); регрессионный тест «сумма по статьям == сумма по счетам» |
| 2 | Календарь даёт ложные кассовые разрывы (неучтённый приток) | Прозрачный список источников строки дня (раскрытие «из чего сложилось»); ручная корректировка плановых операций |
| 3 | Три сценария бюджета путают пользователя | По умолчанию только «реалистичный», остальные за переключателем (роадмап риск №14) |
| 4 | Реализация стартует до готовности ① русификации | Дизайн зафиксирован, реализация явно gated за Ф1 роадмапа; не начинаем Этап 0 раньше |
| 5 | «Существующий модуль Budget» конфликтует с новой структурой | На этапе writing-plans сначала аудит текущего Budget, затем решение расширять/заменять |
| 6 | Вариант C окажется тесным (нужно резать счёт по статьям) | Запланирован путь миграции к гибриду B+C без переделки каркаса |

## 11. Критерии приёмки (вся спека)

1. В режиме «Бизнес» можно построить дерево статей и привязать к ним счета; ОПиУ/ДДС отображаются по статьям, суммы совпадают с отчётами по счетам.
2. Направления работают на `branch_id`; отчёты фильтруются по направлению.
3. Платёжный календарь показывает прогноз остатка на месяц вперёд из открытых счетов/актов + ручных + повторяющихся операций и подсвечивает кассовый разрыв.
4. Можно создать БДДС и БДиР на год по статьям в трёх сценариях; виден активный сценарий и режим сравнения.
5. Отчёт план-факт сравнивает план активного сценария с фактом по статьям и периодам, экспорт PDF/Excel работает.
6. Все новые таблицы — additive tenant-миграции с рабочим `down()`; `lang:check` = 0; e2e на `en` зелёные.
