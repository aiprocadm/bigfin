## 2. Что дала разведка этой итерации

Прошлые фазы отвечали на вопросы «можно ли верить цифрам» (v6) и «можно ли верить самому факту
сохранения» (v7). Следующий естественный вопрос — **«можно ли верить тому, что чужой человек
не сделает лишнего»**.

Он не абстрактный. Как только владелец приглашает бухгалтера, помощника или менеджера, роль
перестаёт быть украшением: она либо ограничивает, либо нет.

**В продукте есть две готовые роли:** «Администратор» и «Сотрудник». Роль «Сотрудник» по
задумке даёт права ровно на **шесть видов документов** — счета покупателям, сметы, чеки, оплаты
покупателей, счета поставщиков, оплаты поставщикам. Всё остальное ей не разрешено.

**Проверка на стенде показала, что «не разрешено» соблюдается меньше чем наполовину.**

## 3. Долг, вскрытый этой разведкой (новое в v8)

Порядок — по риску.

| № | Что | Почему важно | Объём |
|---|---|---|---|
| **П1** | **Половина записывающих ручек не проверяет права** | 41 контроллер из 80 пишущих не спрашивает разрешения — это **129 действий записи**. Сотрудник делает то, что его роли не давали | Разметить `@RequirePermission`, где право уже существует; для остального — решение, какое право требовать |
| **П2** | **Сотрудник может создать роль с любыми правами** | Прямой обход всей системы разграничения: роль создаётся, дальше её кто угодно кому угодно назначает | Закрыть управление ролями и пользователями правом владельца |
| **П3** | **Сотрудник может закрыть период всей организации** | Закрытый период запрещает правку документов **всем, включая владельца**. В схеме прав для этого есть отдельная возможность «блокировка периода» — но ручка её не спрашивает | Одна пометка + проверка живьём |
| **П4** | **Нет сторожа против повторения** | Ровно как было с флагами модулей: без машинной проверки список снова разъедется | Тест по образцу `featureGates.spec.ts` |
| **П5** | **Встроенная роль «Сотрудник» не даёт ничего** | Найдено при живой проверке П2/П3: сотрудник не может выписать счёт — то единственное, ради чего роль существует | Две правки в засеваемых данных + перенос для существующих организаций |
| **П6** | **Девять контроллеров с мнимой защитой** | Право объявлено, стража нет — запрос проходит. Найдено сторожем П4 при заведении | Подключить стража, каждый — с живой пробой |

### Что проверено живьём (стенд, роль «Сотрудник»)

Завёл на стенде второго пользователя с ролью «Сотрудник» и попробовал за него действия,
которых эта роль не даёт:

| Действие | Право в схеме | Итог |
|---|---|---|
| Создать роль с правами на счета, настройки и блокировку периода | не давалось | **создано (201)** ⛔ |
| Закрыть период всей организации до 31.12.2026 | «блокировка периода» — не давалась | **закрыто (200)** ⛔ |
| Создать категорию товаров | не давалось | **создано (201)** ⛔ |
| Изменить настройки организации | «настройки» — не давались | отклонено (403) ✅ |
| Создать счёт учёта | «счета: создание» — не давалось | отклонено (403) ✅ |
| Назначить себе новую роль | — | отклонено, отдельная защита ✅ |

Контраст в последних трёх строках и есть суть: **механизм прав работает, он просто не подключён
к половине ручек.** Это не архитектурная переделка, а разметка.

### П5 подробно: роль «Сотрудник» не работает вовсе

Найдено при живой проверке П2/П3 — сотрудник, которому роль даёт право выписывать счета,
получил отказ. Причин **две, и каждой хватило бы отдельно**:

1. **Признак включённости права пуст.** Права засеваются без колонки «включено», в базе там
   `NULL`. Сборка прав отбирает только включённые (`.filter(p => p.value)`) — значит
   отбрасывает все двадцать четыре.
2. **Названия действий в другом регистре.** В засеваемых данных `create`, а код спрашивает
   `Create`. Сверка регистрозависимая.

Итог: **приглашённый сотрудник не может сделать ничего.** Дефект не связан с правками П2/П3 —
они не касаются ни счетов, ни сборки прав; в данных обе причины видны напрямую.

Лечение — правка засеваемых данных плюс перенос для уже созданных организаций. Перенос
обязателен: у существующих организаций строки прав уже лежат с `NULL` и в нижнем регистре.

### П6 подробно: право объявлено, исполнять некому

Сторож П4 при первом же прогоне нашёл девять контроллеров, где стоит пометка права, но страж,
который её исполняет, не подключён. Это тот же класс «мнимой защиты», что уже ловился на флагах
модулей: в коде выглядит закрытым, на деле открыто.

Список записан в самом тесте и **может только сокращаться**. Закрываются они в П1: подключение
стража меняет поведение ручки, каждую надо проверить живой пробой за сотрудника.

### Чего в списке НЕТ

Общей защиты «по умолчанию всё запрещено» в приложении нет и не предлагается вводить одним
махом: часть ручек законно открыта (вход, подтверждение почты, приём уведомлений от банка и
платёжных систем), и глобальный запрет сломал бы их разом. Правильный порядок — разметить явно,
потом закрепить сторожем.

## 4. Предлагаемая фаза: «Кто что может»

Смысл фазы — чтобы **приглашённый человек мог ровно то, что ему дали**. Это прямое продолжение
логики: v6 — верить цифрам, v7 — верить факту сохранения, v8 — верить границам.

**Рекомендованный порядок:**

1. **П2 + П3 — самое опасное первым.** ✅ **Закрыто (#219).** Управление ролями,
   пользователями и закрытие периода. Заведён страж «только владелец» (`OwnerGuard` +
   `@RequireOwner`) — по образцу уже имеющихся стражей права и флага. Закрытие периода
   получило существовавшую, но не спрашиваемую возможность «блокировка периода».
   Живая проба: сотруднику 403 на все три действия, владельцу 200; чтение списка участников
   и состояния периода осталось открытым.
2. **П5 — роль «Сотрудник» должна начать работать.** Пока она не даёт ничего, разграничение
   доступа бессмысленно: единственная урезанная роль в продукте нерабочая.
3. **П1 + П6 — сплошная разметка.** Идти группами: деньги (банк, правила разбора,
   сопоставление) → структура (склады, отделения, валюты) → справочники (контрагенты,
   категории, статьи) → прочее. Девять контроллеров с мнимой защитой (П6) идут первыми:
   там пометка уже стоит, нужен только страж. После каждой группы — живая проба за сотрудника.
4. **П4 — сторож.** ✅ **Заведён (#219).** `Roles/accessGates.spec.ts`: пометка права и
   пометка «только владелец» обязаны идти со своим стражем; самое опасное закрыто и остаётся
   закрытым; у закрытия периода и состава участников охраняется каждая изменяющая ручка.
   Список мнимой защиты может только сокращаться и проверяется на выдуманные записи.

**Что НЕ делать сейчас** (без изменений с v7): тяжёлые банковские интеграции и нативный клиент.
Консолидацию мультиюрлица начинать только как осознанную ставку на несколько недель.
