# Дорожная карта: Bigfin → паритет функционала с Fintablo

**Дата:** 2026-05-22
**Тип документа:** Roadmap (дорожная карта над портфелем под-проектов)
**Статус:** Draft → ожидает review основателя
**Длительность:** 24-42 месяца full-time solo + Claude
**Количество под-проектов:** 16

---

## 1. Контекст и цели

### Что мы строим

Дорожную карту доработки кодовой базы Bigfin до уровня функциональности, эквивалентной [fintablo.ru/features](https://fintablo.ru/features). Карта охватывает 16 последовательных под-проектов, каждый из которых получит собственную детальную спецификацию.

### Целевая аудитория продукта

Предприниматели без бухгалтерского образования. Профиль клиента — универсальный: услуги, товары, смешанные модели. Основатель тоже использует продукт в своём бизнесе (dogfooding).

### Целевая аудитория документа

Основатель Bigfin (исполнитель) + Claude (со-разработчик).

### Принципы

1. **Под-проекты последовательны** (подход «Фундамент → Этажи»). Solo + full-time не позволяет параллелизма.
2. **Каждый под-проект — отдельный полный цикл:** brainstorming → spec → plan → implementation → review → следующий. Без пропусков.
3. **Каждый PR обратим** (`git revert` без последствий). Без миграций БД, ломающих обратную совместимость.
4. **Двойная запись остаётся под капотом.** Бухгалтерские UI скрываются за переключателем «Бизнес-режим / Бухгалтерский режим».
5. **EN остаётся как fallback** для строк, ещё не переведённых на RU. Никогда не удаляем существующий функционал — только добавляем или скрываем.

### Что НЕ входит в дорожную карту

- Бизнес-план, маркетинг, монетизация
- Графический ребрендинг — отдельный под-проект, может быть вставлен между фазами
- Юридическая регистрация продукта в РФ, налоговая регистрация
- Хостинг и DevOps-инфраструктура
- Сертификация в качестве оператора персональных данных (152-ФЗ) — будет до запуска ⑨c

### Критерий успеха

После завершения всех 16 под-проектов в Bigfin доступен весь функционал страницы fintablo.ru/features на русском языке, в режиме «Бизнес», с российскими банковскими интеграциями и мобильным приложением. Полный бухгалтерский функционал остаётся доступным через режим «Бухгалтерский» для опытных пользователей.

## 2. Структура под-проектов

Каждый sub-project имеет 4 атрибута: **scope** (что входит), **anti-scope** (что не входит), **критерий завершения**, **зависимости**. Оценки даны в неделях полной занятости — реальное календарное время больше из-за обучения, переделок и пауз.

### Sub-project ① — Полная русификация и терминология

- **Scope:** русская локаль на frontend (~2400 ключей) и server (~30 JSON-файлов), русская терминология (ДДС, ОПиУ, Баланс, Сделки, Статьи учёта), RUB как валюта, дата-формат `DD.MM.YYYY`, числовой формат `1 234,56`, демо-данные на русском, переключатель `en/ru` в UI.
- **НЕ входит:** российские юр.формы (ИНН и пр.) — это ②. Графический ребрендинг — отдельно.
- **Готовность:** draft-спек `docs/superpowers/specs/2026-05-21-russian-localization-design.md`.
- **Критерий завершения:** при переключении на `?lang=ru` весь UI на русском. Скрипт `pnpm run lang:check` возвращает 0. Существующие e2e-тесты на `en` проходят.
- **Зависимости:** нет.
- **Оценка:** 8-12 недель.

### Sub-project ② — Российская юридическая специфика

- **Scope:** поля ИНН/КПП/ОГРН/ОКПО/банковские реквизиты в сущностях `Organization`, `Customer`, `Vendor`. Российская печатная форма счёта (УПД), акта выполненных работ. Адаптация плана статей учёта под управленческую структуру РФ. Российские ставки НДС (20%, 10%, 0%, без НДС).
- **НЕ входит:** ЭДО (Контур, Диадок) — отдельный крупный под-проект в будущем. Полный РСБУ — не нужно (продукт управленческий).
- **Критерий завершения:** можно создать организацию с ИНН/КПП, выписать счёт-фактуру с НДС, экспортировать PDF на русском с правильными реквизитами.
- **Зависимости:** ①.
- **Оценка:** 6-10 недель.

### Sub-project ③ — Режимы «Бизнес» / «Бухгалтерский» + Onboarding

- **Scope:** на странице настроек переключатель `mode: business | accountant`. В режиме `business` скрыты: Manual Journals UI, Trial Balance, продвинутые опции Plan of Accounts. Onboarding-wizard при первом входе спрашивает: тип бизнеса (услуги/товары/смешанное), наличие НДС, наличие сотрудников. Результат → дефолтный набор статей учёта и видимость модулей.
- **НЕ входит:** автоматическое скрытие модулей на основе паттернов использования.
- **Критерий завершения:** новый пользователь после onboarding видит чистый UI без бухгалтерских страниц. Существующие пользователи остаются в `accountant` для обратной совместимости.
- **Зависимости:** ①, ②.
- **Оценка:** 2-4 недели.

### Sub-project ④ — Финансовые отчёты как ДДС / ОПиУ / Баланс

- **Scope:** интерфейс отчётов переработан в Fintablo-стиль. Панель приборов — первая страница после логина в режиме `business`. Три ключевых отчёта (ДДС, ОПиУ, Баланс) получают упрощённый UI с фильтрами «по статье/проекту/подразделению». Логика расчётов — без изменений.
- **НЕ входит:** новые методы расчёта (косвенный метод ДДС, segment reporting).
- **Критерий завершения:** все 3 отчёта переименованы и упрощены, доступны через Панель приборов, экспорт в Excel/PDF работает.
- **Зависимости:** ①, ②, ③.
- **Оценка:** 4-6 недель.

### Sub-project ⑬a — PWA-режим (мобильная адаптация)

- **Scope:** адаптивная вёрстка для мобильных экранов на ключевых страницах (Панель, отчёты, формы). Service Worker для офлайн-кэширования. Manifest для install-as-app на iOS/Android.
- **НЕ входит:** push-уведомления (это ⑬b), доступ к камере, нативные функции.
- **Критерий завершения:** на iPhone и Android можно открыть Bigfin через браузер, добавить на главный экран, использовать ключевые экраны без горизонтальной прокрутки.
- **Зависимости:** ④.
- **Оценка:** 2-4 недели.

### Sub-project ⑤ — Бюджеты как БДДС и БДиР

- **Scope:** существующий модуль Budget → два представления: БДДС (бюджет ДДС) и БДиР (бюджет доходов и расходов). План-факт сравнение в реальном времени. Шаблоны бюджетов по типам бизнеса.
- **НЕ входит:** сложное бюджетирование с несколькими сценариями («что если»), консолидация по группе компаний.
- **Критерий завершения:** можно создать БДДС или БДиР на квартал/год, ввести план по статьям, видеть факт vs план в табличной и графической форме.
- **Зависимости:** ④.
- **Оценка:** 3-5 недель.

### Sub-project ⑥ — Платёжный календарь (новый модуль)

- **Scope:** новая страница «Платёжный календарь». Список запланированных входящих/исходящих платежей по датам. Прогноз остатков на счетах по дням. Предупреждения о кассовых разрывах. Автоматическое создание планируемых платежей из счетов (Invoices/Bills) по `due_date`.
- **НЕ входит:** автоматическая отправка платежей в банк (это часть ⑨). Только планирование и визуализация.
- **Критерий завершения:** видна таблица платежей на месяц вперёд, можно добавить ручной планируемый платёж, видны прогноз остатка и предупреждение «через 5 дней кассовый разрыв».
- **Зависимости:** ④.
- **Оценка:** 4-8 недель.

### Sub-project ⑦ — Сделки (новый модуль)

- **Scope:** новая сущность «Сделка» — группировка операций (Invoices, Bills, Expenses) по проекту/клиенту/направлению. Расчёт прибыльности сделки: (доходы) − (прямые расходы). Дашборд сделок: воронка, рентабельность, дебиторка.
- **НЕ входит:** CRM-функционал (контакты, лиды, задачи). Сделки — только финансовая сторона.
- **Критерий завершения:** можно создать сделку, привязать к ней счёт и расходы, увидеть рентабельность. Список сделок с сортировкой по прибыльности.
- **Зависимости:** ④, ⑥.
- **Оценка:** 6-10 недель.

### Sub-project ⑬b — Capacitor-обёртка (нативное мобильное приложение)

- **Scope:** упаковка веб-приложения в нативный wrapper через Capacitor. Push-уведомления для платёжного календаря (FCM). Доступ к камере (сканировать чеки). Публикация в App Store и Google Play.
- **НЕ входит:** полностью нативный UI (это ⑬c). Офлайн-режим — базовый, через Service Worker из ⑬a.
- **Критерий завершения:** установленное на iPhone и Android приложение Bigfin, работают push-уведомления о платежах, можно сделать фото чека.
- **Зависимости:** ⑬a, ⑥, ⑦.
- **Оценка:** 6-10 недель.

### Sub-project ⑧ — Зарплаты и налоги на ФОТ

- **Scope:** учёт сотрудников (ФИО, должность, ставка), начисление зарплаты (оклад, премии, удержания), расчёт страховых взносов (СВ — 30%) и НДФЛ (13%/15%/30%). Платёжная ведомость, расходный кассовый ордер. Отчёт «Налоги к уплате».
- **НЕ входит:** автоматическая отправка отчётов в ФНС/СФР (СЗВ-ТД, РСВ, 6-НДФЛ). Кадровый учёт по ТК РФ. Только финансовый аспект ФОТ.
- **Критерий завершения:** можно завести сотрудника, начислить зарплату за месяц, увидеть отдельные суммы к выплате, НДФЛ к перечислению, СВ к уплате.
- **Зависимости:** ④, ⑤.
- **Оценка:** 8-12 недель — самый сложный, требует глубокого знания РФ-законодательства.

### Sub-project ⑨a — Универсальный импорт выписок

- **Scope:** загрузка выписки в форматах CSV / Excel / PDF / 1C-bank exchange (xml-формат для обмена с банками, не путать с ⑩ — это самостоятельный стандарт банковской выгрузки). Парсеры для топ-вариантов экспорта банков (Тинькофф/Сбер/Альфа и др.). Автоматическое сопоставление импортируемых платежей с существующими Invoices/Bills через эвристики (сумма, дата, контрагент).
- **НЕ входит:** API-интеграция с банками (это ⑨c-⑫). Двусторонняя синхронизация.
- **Критерий завершения:** загруженная из любого банка выписка распарсилась, операции попали в очередь сопоставления, можно подтвердить одним кликом.
- **Зависимости:** ④.
- **Оценка:** 2-4 недели.

### Sub-project ⑨b — Интеграция с Дзенмани

- **Scope:** API-импорт операций из Дзенмани (если основатель/клиенты используют его для личных финансов). Webhook-приём новых операций.
- **НЕ входит:** двустороннее синхронизирование (Bigfin → Дзенмани).
- **Критерий завершения:** можно подключить аккаунт Дзенмани, увидеть импортируемые операции в очереди сопоставления.
- **Зависимости:** ⑨a.
- **Оценка:** 2-4 недели.

### Sub-project ⑨c — Банковские API: волна 1 (Тинькофф + Альфа)

- **Scope:** API-интеграция с Тинькофф Бизнес и Альфа-Банк. Автоматический импорт выписки, сопоставление, статусы платежей. Партнёрские договоры — заключаются параллельно с разработкой, **переговоры начинаются в Ф3**.
- **НЕ входит:** инициация платежей **из** Bigfin **в** банк (это требует ЭКО-сертификации, отдельный под-проект в будущем).
- **Критерий завершения:** можно подключить аккаунт Тинькофф и Альфа, выписка автоматически импортируется ежедневно.
- **Зависимости:** ⑨a.
- **Оценка:** 4-8 недель (включая Альфа после Тинькофф — переиспользование кода).

### Sub-project ⑩ — Интеграция с 1С

- **Scope:** файловый обмен с 1С через формат CommerceML (XML). Импорт контрагентов, товаров, документов из 1С в Bigfin. Экспорт операций из Bigfin в 1С.
- **НЕ входит:** REST API через 1C:Web Services (отдельный под-проект). Внешняя обработка-плагин для 1С (отдельный под-проект).
- **Критерий завершения:** можно выгрузить из 1С файл CommerceML, загрузить в Bigfin, увидеть синхронизированные данные.
- **Зависимости:** ④, ⑤.
- **Оценка:** 6-10 недель.

### Sub-project ⑪ — Банковские API: волна 2 (Сбер + Точка + Райффайзен)

- **Scope:** API-интеграция со Сбер Бизнес, Точка, Райффайзен. Сбер и ВТБ требуют партнёр-статуса — переговоры с Сбером начинаются в начале Ф4.
- **НЕ входит:** ВТБ и ПСБ — это ⑫.
- **Критерий завершения:** работающая API-интеграция со всеми тремя банками.
- **Зависимости:** ⑨c.
- **Оценка:** 6-10 недель на банк = 18-30 недель на весь под-проект (три банка последовательно, переиспользование кода между ними).

### Sub-project ⑫ — Банковские API: волна 3 (ВТБ + ПСБ + другие)

- **Scope:** API-интеграция с ВТБ, ПСБ. Дополнительные банки (Открытие, Промсвязьбанк и т.д.) — по запросу пользователей.
- **НЕ входит:** банки, у которых нет publicly documented API (на момент написания спека).
- **Критерий завершения:** ВТБ и ПСБ работают через API.
- **Зависимости:** ⑪.
- **Оценка:** 6-10 недель на банк = 12-20 недель на весь под-проект (два банка).

### Backlog: Sub-project ⑬c — Полный нативный мобильный (опционально)

- **Scope:** разработка React Native (или Flutter) приложения с независимым нативным UI. Полный офлайн-режим. Быстрый старт.
- **Когда:** только после запуска и обратной связи от первых пользователей. Принимается отдельным решением.
- **Оценка:** 16-24 недели.

- ⑬b требует ⑬a — нативная обёртка строится поверх PWA.

### Точки естественной паузы

После любой из точек ниже можно сделать паузу на недели/месяцы без вреда для проекта:

- После ②: продукт «российский» (юр.формы есть)
- После ③: продукт «дружелюбный к непрофи» (onboarding и режимы)
- После ⑤: «MVP Fintablo-light» (отчёты + бюджеты + мобильный)
- После ⑦: основной Fintablo-функционал
- После ⑧: закрыт раздел «Операции» Fintablo
- После ⑨a: универсальный импорт выписок работает для всех банков
- После ⑨c: первый партнёрский банк = маркетинговый аргумент

### Возможные параллельные действия

- ⑬a (PWA) можно вести параллельно с ⑤ — независимо от бюджетов.
- ⑨a (импорт выписок) можно начать **в Ф3**, во время Сделок, если устал от ⑦.
- Партнёрские переговоры с банками (организационно, не разработка) идут параллельно с любым sub-project.

## 4. Сквозные архитектурные решения

Эти правила действуют во всех 16 под-проектах. Формулировка сейчас экономит часы споров с собой в будущем.

### 4.1 Существующий фундамент сохраняется

- Двойная запись под капотом работает как сейчас. Новые модули пишут проводки через существующие сервисы.
- Не переписываем существующие модули, если они работают. Только дополняем, переименовываем UI, скрываем.
- Не делаем миграций, ломающих обратную совместимость. Только additive (новые колонки `nullable: true`, новые таблицы).

### 4.2 UI-модель: режим «Бизнес» / «Бухгалтерский»

- Глобальный флаг на уровне организации: `mode: 'business' | 'accountant'`. Default = `accountant` для совместимости.
- В `business` скрываются: Manual Journals UI, Trial Balance, продвинутые разделы Plan of Accounts.
- Переключатель в Settings, доступен в любое время. Не требует миграции данных — только UI-фильтр.
- Onboarding для новых организаций устанавливает `business` по умолчанию.

### 4.3 Локализация

- Стек: `react-intl-universal` (web) + `nestjs-i18n` (server).
- `SUPPORTED_LOCALES`: `['en', 'ru']`. AR/ES/SV — мёртвый код, не активируем.
- Новые ключи добавляются **парно** — EN + RU. CI-проверка `pnpm run lang:check` падает, если есть missing keys.
- EN остаётся как fallback на уровне библиотеки.

### 4.4 Валюта

- RUB добавляется в существующий список валют как первый элемент.
- В onboarding для RU-локали — preset = RUB.
- Multi-currency функционал сохраняется (USD, EUR работают).

### 4.5 Тестирование

- **Unit-тесты** — на бизнес-логику новых модулей (Сделки, Календарь, ЗП). Существующие — не трогаем.
- **e2e (Playwright)** — каждый PR должен проходить e2e на `en`. Регрессии = блокер.
- **Ручная проверка на `ru`** — чек-лист в PR-описании.
- **Dogfooding** — основатель сам пользуется продуктом в своём бизнесе, реальная обратная связь.

### 4.6 Feature flags

- Новые модули (⑥, ⑦, ⑧) выпускаются под флагами `FEATURE_PAYMENT_CALENDAR`, `FEATURE_DEALS`, `FEATURE_PAYROLL`.
- По умолчанию выключены. Включаются для тестовых организаций, затем постепенно для всех.
- Откат модуля = выключить флаг, без `git revert`.

### 4.7 Минимум новых зависимостей

- Новые npm-пакеты — только при наличии обоснования в PR.
- Текущий React-стек не меняем.

## 5. Риски и митигации

| # | Риск | Вероятность | Митигация |

| 1 | Выгорание solo full-time за 24-36 мес | **Высокая** | Точки естественной паузы после Ф1/Ф2/Ф3. Чёткий «definition of done» каждого sub-project. Возможность переключаться между «фундаментальной» (⑥/⑦/⑧) и «декоративной» (⑨a, ⑬a) работой при усталости. |

| 4 | Терминология не зайдёт первым пользователям | Средняя | Терминология в JSON-локалях правится за минуту. Первые 5-10 пользователей — фокус-группа. |
| 5 | Существующий код сломается при изменениях | Средняя | e2e на `en` зелёный — обязательное условие мерджа. Каждое изменение `git revert`-friendly. |
| 6 | 152-ФЗ / утечка персональных данных | Низкая, но критичная | До запуска ⑨c — изучить требования к оператору ПД. Хостинг в РФ-юрисдикции. Шифрование банковских токенов в БД. |

- Производительность — на первых 100-1000 пользователях текущая архитектура (PostgreSQL + Node) достаточна.

## 6. Операционная модель и первый шаг

### 6.1 Цикл для каждого под-проекта

```
1. brainstorming  — обсуждаем детали, получаем подтверждение
2. writing-plans  — детальный план разбит на PR/задачи
3. executing      — исполняем по плану, каждый PR atomic
4. review         — e2e + dogfooding + баги
5. retro          — что узнали, что поменять в дорожной карте
6. next           — следующий под-проект
```

Между под-проектами можно (и нужно) делать паузы.

### 6.2 Точки повторной ревизии дорожной карты

Обязательная ревизия дорожной карты после завершения каждой фазы (Ф1, Ф2, Ф3, Ф4):

- Что узнали из dogfooding?
- Что больше не актуально?
- Какие новые риски появились?
- Нужно ли добавить под-проект, который раньше не виделся?

Финальная дорожная карта будет отличаться от той, что сегодня. Это нормально.

### 6.3 Технические артефакты

- Этот документ: `docs/superpowers/specs/2026-05-22-fintablo-parity-roadmap.md`.
- Каждый под-проект получает собственный спек в той же папке: `2026-XX-XX-<topic>-design.md`.
- После спека — собственный план: `docs/superpowers/plans/2026-XX-XX-<topic>-plan.md`.

### 6.4 Первый шаг

После одобрения этой дорожной карты:

1. Запускаем `superpowers:writing-plans` для существующего draft-спека русификации (`2026-05-21-russian-localization-design.md`).
2. Превращаем 16 шагов спека в детальный план PR-за-PR с конкретными файлами, командами проверки и инструкциями отката.
3. После одобрения плана — `superpowers:executing-plans` либо ручная работа PR-за-PR.

### 6.5 Что НЕ делаем сейчас (явный gate)

- НЕ начинаем кодить sub-project ① прямо сегодня. Сначала writing-plans.
- НЕ пишем детальные спеки для sub-projects ②-⑫, ⑬a-c. Только когда дойдём.
- НЕ ставим календарные даты. Только оценки трудоёмкости.
