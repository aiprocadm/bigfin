## 1. Контекст и цели

### Что строим

1. **Бюджеты** — план «сколько заработать/потратить по каждой статье в каждом месяце», в двух видах (БДиР — по прибыли, БДДС — по деньгам) и трёх сценариях (опт./реал./пес.).
2. **План-факт** — отчёт сравнения плана с фактом по статьям и периодам, для обоих видов бюджета.

### Целевая аудитория

Предприниматели без бухгалтерского образования. Им понятно «запланировал 500 000 выручки — получил 512 000», непонятен «бюджет по счетам ГК». Бюджет говорит статьями (язык Этапа 0).

### Критерий успеха

В режиме «Бизнес» пользователь может: создать БДиР и БДДС на год, ввести план по статьям×месяцам в трёх сценариях, переключать активный сценарий и сравнивать три; открыть отчёт план-факт и увидеть отклонения плана от факта по статьям — для обоих видов бюджета.

### Что в коде уже есть (фундамент)

- **Статьи учёта** — `management_articles` (дерево, `kind` income/expense, `cashflow_section`) и карта `management_article_accounts` (счёт→статья). Этап 0.
- **P&L-факт по статьям** — `ArticlesPlRollup` (свёртка оборотов доходно-расходных счетов в статьи). Готов. → источник факта для **БДиР**.
- **Движок отчётов** — `FinancialStatements/modules/*` (ОПиУ/ДДС/Баланс), экспорт PDF/Excel, фильтр по ветке (`FinancialSheetBranchesQueryDto`).
- **Движения по денежным счетам** — `accounts_transactions` (debit/credit) на счетах типа `cash`/`bank`; категоризация денежных потоков — в `CashFlowStatement`.

### Чего в коде нет (строим)

- Таблиц `budgets` / `budget_lines` (модуля бюджетов нет — greenfield, подтверждено разведкой).
- **Кассового факта по статьям** — `ArticlesCashflowRollup` (брат `ArticlesPlRollup` для денежных движений). → источник факта для **БДДС**.
- Отчёта план-факт (сравнение плана и факта).

## 2. Объём v1

### Входит (решения основателя 2026-05-31)

- **Бюджеты обоих видов:** БДиР (`type=bdir`, группировка по `kind`) и БДДС (`type=bdds`, группировка по `cashflow_section`).
- **Три сценария** на тот же период: `optimistic`/`realistic`/`pessimistic`. По умолчанию виден реалистичный; режим «Сравнить сценарии» — три рядом.
- **Гранулярность — месяц** (12 столбцов в году).
- **План-факт для обоих видов:** факт БДиР из `ArticlesPlRollup`, факт БДДС из нового `ArticlesCashflowRollup`.
- Сетка ввода бюджета (статьи×месяцы), отчёт план-факт, CRUD бюджетов.

### НЕ входит (anti-scope)

- **Формулы между сценариями** («пес = реал × 0.8») — бэклог (роадмап откр. вопрос №5).
- **Гранулярность квартал/год** как ввод — v1 только месяц; квартал/год — агрегация поверх месяцев позже.
- **Шаблоны бюджета по типу бизнеса** — опционально, в самом конце.
- **Консолидация по группе компаний** — это ⑰.
- **Экспорт план-факта в PDF/Excel** — v1 отдаёт JSON для экрана; экспорт через движок `FinancialStatements` — follow-up (Открытый вопрос №2).
- **Мультивалютные бюджеты** — план вводится в базовой валюте организации.

## 3. UX

### 3.1 Сетка ввода бюджета

```
Бюджет: [БДиР ▾]  Год: [2026 ▾]  Сценарий: [Реалистичный ▾] [Сравнить сценарии]
┌────────────────────┬────────┬────────┬────────┬───┬──────────┐
│ Статья             │  Янв   │  Фев   │  Мар   │…  │  Итого   │
├────────────────────┼────────┼────────┼────────┼───┼──────────┤
│ ▼ Доходы           │        │        │        │   │          │
│    Выручка         │ 500000 │ 520000 │ 540000 │   │ …        │  ← ячейки редактируемые
│ ▼ Расходы          │        │        │        │   │          │
│    Аренда          │ 150000 │ 150000 │ 150000 │   │          │
│    ФОТ             │ 300000 │ 300000 │ 320000 │   │          │
├────────────────────┼────────┼────────┼────────┼───┼──────────┤
│ Прибыль (план)     │  50000 │  70000 │  70000 │   │          │  ← авторасчёт
└────────────────────┴────────┴────────┴────────┴───┴──────────┘
```

- Строки — дерево статей (Этап 0) с раскрытием; столбцы — месяцы года; ячейки — ввод плановой суммы.
- Переключатель типа: БДиР (по `kind`, внизу «Прибыль») / БДДС (по `cashflow_section`).
- Селектор сценария: по умолчанию реалистичный; «Сравнить сценарии» → три рядом.
- Автоитоги по строкам/столбцам.
- Сохранение — массовый upsert изменённых ячеек по кнопке «Сохранить».

### 3.2 Экран план-факт

```
Период: [Март 2026 ▾]  Тип: [БДиР ▾]  Сценарий: [Реалистичный ▾]  Направление: [Все ▾]
┌────────────────────┬──────────┬──────────┬───────────┬─────────┐
│ Статья             │   План   │   Факт   │  Откл ₽   │  Откл % │
├────────────────────┼──────────┼──────────┼───────────┼─────────┤
│ Выручка            │  540000  │  512000  │  −28000   │  −5,2%  │  🔴
│ Аренда             │  150000  │  150000  │     0      │   0%    │
│ ФОТ                │  320000  │  335000  │  +15000   │  +4,7%  │  🔴
└────────────────────┴──────────┴──────────┴───────────┴─────────┘
```

- Колонки: Статья | План (из `budget_lines` активного сценария) | Факт | Отклонение ₽ | Отклонение %.
- Факт: БДиР → `ArticlesPlRollup`; БДДС → `ArticlesCashflowRollup`.
- Фильтры: период, тип (БДиР/БДДС), сценарий, направление (`branch`).
- Цвет отклонения: перерасход/недобор — красным.

### 3.3 Мобильный

Сетка по природе широкая (12 месяцев × десятки статей). Мобильный — **один месяц за раз**: выбор месяца → список статей с планом (и фактом на план-факт-экране). Десктоп — полная сетка. Те же данные, форма под экран (тот же приём, что лента в календаре).

### 3.4 Переиспользование UI

shadcn `components/ui` (таблица, инпуты, селекты) + React Hook Form (форма создания бюджета) + React Query. Новых UI-зависимостей не вводим.

## 4. Модель данных

Две новые таблицы в **tenant**-схему. Всё additive, рабочий `down()`. Существующее не трогаем.

### `budgets`

| Колонка | Тип | Назначение |
|---|---|---|
| `id` | increments | PK |
| `name` | string | Название бюджета |
| `type` | string | `bdir` / `bdds` |
| `fiscal_year` | integer | Год |
| `period_granularity` | string | `month` (v1) |
| `active_scenario` | string | `optimistic`/`realistic`/`pessimistic`, default `realistic` |
| `branch_id` | integer nullable | бюджет на направление или общий |
| `created_at` / `updated_at` | timestamps | |

### `budget_lines`

| Колонка | Тип | Назначение |
|---|---|---|
| `id` | increments | PK |
| `budget_id` | integer → `budgets.id` (ON DELETE CASCADE) | |
| `article_id` | integer → `management_articles.id` | статья (Этап 0) |
| `period` | date | первый день месяца |
| `scenario` | string | `optimistic`/`realistic`/`pessimistic`, default `realistic` |
| `planned_amount` | decimal(13,3) | план-сумма (базовая валюта) |
| `created_at` / `updated_at` | timestamps | |
| **UNIQUE** | | (`budget_id`, `article_id`, `period`, `scenario`) |

UNIQUE-ключ = координаты ячейки сетки. «Сохранить бюджет» = upsert по этому ключу. Факт матчится на тот же ключ через `article_id` + месяц.

## 5. Движок план-факта

### 5.1 План

`budget_lines` выбранного бюджета и сценария, сгруппированные по `article_id` × `period`.

### 5.2 Факт

- **БДиР:** существующий `ArticlesPlRollup` — обороты доходно-расходных счетов, свёрнутые в статьи за период. Готов.
- **БДДС:** новый `ArticlesCashflowRollup` — движения по денежным счетам (`cash`/`bank`), свёрнутые в статьи через ту же карту `management_article_accounts`, применённую к **встречной (не-денежной) ноге** каждой кассовой проводки. Точный источник данных (прямой проход по `accounts_transactions` денежных счетов vs переиспользование категоризации `CashFlowStatement`) — определяется на этапе плана (Открытый вопрос №1).

### 5.3 Отклонение

Per статья × период: `Δ₽ = факт − план`; `Δ% = (факт − план) / план × 100` (при план=0 показываем «—»). Знак трактуется по `kind`: для доходов недобор факта = «плохо», для расходов перерасход = «плохо» (UI красит соответствующе).

### 5.4 Согласованность

Сумма «факт» план-факта БДиР за период == ОПиУ по статьям за тот же период (обе из `ArticlesPlRollup`). Регрессионный тест.

## 7. Сквозные решения

- **Миграции:** две additive-таблицы в tenant-схему, рабочий `down()`, прогон `latest → rollback → latest`. Скилл `make-migration`.
- **Feature flag:** `budgets`, по умолчанию `false`. Откат = выключить флаг.
- **Режим:** бюджеты и план-факт — фичи режима «Бизнес».
- **i18n:** все строки через `intl.get`/`<T id=.../>`; сообщения Zod — через i18n; парность EN↔RU; после правок — `lang-check.js`. Скилл `i18n-add-string`.
- **Валюта:** план в базовой валюте организации; мультивалютные бюджеты — вне v1.
- **Зависимости:** переиспользуем существующий стек; новых не вводим.
- **Копирайт:** © 2026 Bigfin, проприетарная лицензия.
- **Старт реализации:** после Ф1 роадмапа (① русификация, ③ режимы), как и весь каркас. После Этапа 1 (календарь).

## 8. Тестирование

- **Unit (Jest), критично:** расчёт отклонения план-факт (Δ₽/Δ% с план=0); `ArticlesCashflowRollup` (свёртка кассовых движений по статьям, встречная нога, исключение переводов между своими счетами); upsert сетки (правка существующей ячейки vs вставка новой по UNIQUE-ключу).
- **Unit:** валидатор бюджета; сервис план-факта с замоканными rollup-сервисами.
- **Регрессия согласованности:** факт БДиР план-факта == ОПиУ по статьям за период (§5.4).
- **Миграции:** прогон `latest → rollback → latest` для обеих таблиц.
- **e2e (Playwright) на `en`** — зелёный (условие мерджа).
- **Ручная проверка на `ru` + dogfooding** — чек-лист в PR.

## 10. Критерии приёмки

1. В режиме «Бизнес» можно создать БДиР и БДДС на год, ввести план по статьям×месяцам, сохранить (upsert по ячейкам).
2. Поддержаны три сценария: виден активный (по умолчанию реалистичный), есть режим сравнения трёх.
3. Отчёт план-факт показывает План | Факт | Отклонение ₽ | Отклонение % по статьям за период — для БДиР (факт из `ArticlesPlRollup`) и для БДДС (факт из `ArticlesCashflowRollup`).
4. Факт БДиР план-факта сходится с ОПиУ по статьям за тот же период.
5. Фильтры план-факта: период, тип, сценарий, направление.
6. Обе новые таблицы — additive tenant-миграции с рабочим `down()`; `lang:check` = 0; e2e на `en` зелёные; флаг `budgets` по умолчанию выключен.

## 11. Открытые вопросы

1. **Источник кассового факта (`ArticlesCashflowRollup`).** Прямой проход по `accounts_transactions` денежных счетов с маппингом встречной ноги на статью, или переиспользование категоризации `CashFlowStatement`? Решить на этапе плана (нужна разведка кода, как для движка календаря). Обязательно исключить внутренние переводы между своими счетами.
2. **Экспорт план-факта в PDF/Excel.** v1 — JSON для экрана. Экспорт через движок `FinancialStatements` (как ОПиУ/ДДС) — follow-up внутри этапа.
3. **Сохранение сетки: автосейв ячейки vs кнопка «Сохранить».** Предложено — кнопка (массовый upsert). Пересмотреть после dogfooding.
4. **Режим «Сравнить сценарии».** Три столбца на период рядом vs три отдельные сетки. Решить на UI-этапе.
5. **Старт реализации** — после Ф1 и Этапа 1 (календарь). Бюджеты используют статьи (Этап 0, готов); прямой зависимости от календаря нет, но порядок этапов сохраняем.
