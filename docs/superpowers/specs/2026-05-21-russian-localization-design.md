# Spec: Русская локализация и терминологическая адаптация Bigfin

**Дата:** 2026-05-21
**Автор:** Команда Bigfin (с помощью Claude)
**Статус:** Draft → ожидает review от пользователя
**Sub-project:** ①+② из общей задачи «Русификация + UX»

---

## 1. Проблема и контекст

Bigfin — платформа управленческого учёта для малого бизнеса, адаптируемая под российский рынок. Целевая аудитория — предприниматели без бухгалтерского образования (аналог Fintablo.ru / PlanFact.io).

В текущем состоянии Bigfin имеет английский и арабский интерфейс. Чтобы продукт был пригоден к запуску в РФ, нужно:

1. **Технически** добавить русскую локаль (~2400 строк UI + ~30 серверных JSON).
2. **Терминологически** адаптировать перевод под управленческий учёт, а не бухгалтерский (например, "Cash Flow" → "ДДС", а не "Отчёт о движении денежных средств").

Эта спецификация описывает **только эти две задачи**. UX-редизайн, ребрендинг, российские юр.формы и PDF-шаблоны — отдельные подпроекты.

## 2. Цели и не-цели

### В скоупе

- Полная русская локаль `ru` для frontend (`packages/webapp/src/lang/ru/`)
- Полная русская локаль `ru` для server (`packages/server/src/i18n/ru/`)
- Поиск и замена хардкод-английских строк через `intl.get()`
- Дата-формат `DD.MM.YYYY` по умолчанию (`moment.locale('ru')`)
- Числовой формат `1 234,56` (через `accounting`)
- Добавление `RUB` (₽) как валюты, дефолтная для новых организаций
- Языковой переключатель `en/ru` в UI
- Демо/seed-данные на русском
- Email-шаблоны на русском (`@bigfin/email-components`)

### Не в скоупе (отдельные spec-ы)

- UX-редизайн дашборда, форм, навигации
- Юр.формы РФ: ИНН, КПП, ОГРН, банковские реквизиты
- PDF-шаблоны (счета, акты)
- Ребрендинг (визуальный): логотип, цвета, шрифты
- Адаптация плана счетов под РСБУ
- Налоговая логика (УСН, ОСНО, ЕНВД и т.д.)

## 3. Решения по содержанию

### 3.1 Опорные принципы перевода

1. **Управленческий, а не бухгалтерский** язык. Цель: предприниматель должен понять без словаря.
2. **Конвенции Fintablo / PlanFact** как ориентир там, где они согласованы между собой (де-факто стандарт российского управленческого учёта).
3. **Длинные формулировки лучше коротких**, если короткое путает.
4. **Английский остаётся как fallback** — частично переведённый продукт работает.

### 3.2 Ключевые терминологические решения

| English (исходный) | Русский (наш выбор) | Что НЕ берём | Обоснование |
|----------------------|---------------------|---------------|-------------|
| Cash Flow Statement | **ДДС** (Движение денежных средств) | Отчёт о движении | Fintablo / PlanFact |
| Profit & Loss | **Прибыль и Убытки** | ОПиУ, Отчёт о фин.результатах | Понятнее для непрофи |
| Balance Sheet | **Баланс** | Бухгалтерский баланс | Короче, привычнее |
| Trial Balance | **Оборотно-сальдовая ведомость** | — | Устоявшийся термин |
| Chart of Accounts | **Статьи учёта** | План счетов | PlanFact-style, "План счетов" — бухгалтерия |
| Account (в плане счетов) | **Статья** / **Счёт учёта** | — | По контексту |
| Bank Account | **Банковский счёт** / **Касса** | — | Касса для наличного |
| Journal Entry | **Операция** | Проводка | "Проводка" пугает непрофи |
| Transaction | **Операция** | — | PlanFact-style |
| Invoice | **Счёт** (клиенту) | Инвойс | Привычнее в РФ |
| Estimate | **Коммерческое предложение** / КП | — | Стандарт b2b |
| Receipt | **Поступление** | Чек | "Чек" путает с фискальным |
| Credit Note | **Возврат** (клиенту) | Кредит-нота | Понятнее |
| Bill | **Счёт от поставщика** | Билл, Накладная | Точнее |
| Expense | **Расход** | — | — |
| Vendor Credit | **Возврат поставщику** | — | — |
| Customer | **Клиент** | Покупатель, Заказчик | Универсально |
| Vendor | **Поставщик** | Контрагент | Точнее по роли |
| Workspace / Organization | **Организация** | Рабочее пространство | PlanFact-style |
| Item | **Товар или Услуга** | Номенклатура | 1С-вский термин пугает |
| Inventory | **Склад** | — | — |
| Reconciliation | **Сверка** | — | — |
| Budget | **Бюджет** | — | — |
| VAT / Tax | **НДС / Налог** | — | — |
| Branches | **Подразделения** / Филиалы | — | По смыслу |

### 3.3 Спорные решения, итерируем после запуска

- **"Bill" → "Счёт от поставщика"** — длинно. Альтернатива: "Счёт" + контекст (входящий). Решим после тестов с пользователями.

## 4. Архитектура

### 4.1 i18n-инфраструктура (унаследована из исходной кодовой базы)

**Frontend:**
- Библиотека: `react-intl-universal` v2.4.7
- Текущие локали: `lang/{en, ar}` (в `SUPPORTED_LOCALES`), `lang/{es, sv}` (мёртвый код)
- Yup-валидация: отдельный `locale.tsx` в каждой папке
- Дата: `moment` (имеет встроенную русскую локаль)
- Числа: `accounting`
- Валюты: список в `js-money` + кастомный в `constants/currencies.tsx`

**Backend:**
- Библиотека: `nestjs-i18n` v10.4.9
- Текущие локали: только `i18n/en/`
- Структура: ~30 JSON-файлов по модулям

### 4.2 Изменения в файлах

```
packages/webapp/src/
├── components/AppIntlLoader.tsx          ← МОДИФИЦИРУЕМ (+ 'ru' в SUPPORTED_LOCALES)
├── lang/ru/                              ← НОВАЯ ПАПКА
│   ├── index.json                       ← ~2400 ключей UI
│   └── locale.tsx                       ← yup-валидация
│   (authentication.tsx из en/ — мёртвый код, не копируем; verified: не импортируется ни откуда)
├── constants/currencies.tsx              ← МОДИФИЦИРУЕМ (+ RUB)
├── routes/dashboard.tsx                  ← МОДИФИЦИРУЕМ (хардкод-строки)
├── containers/**/*.tsx                   ← по необходимости
└── scripts/lang-check.js                 ← НОВЫЙ (валидатор ключей ru vs en)

packages/server/src/
├── i18n/ru/                              ← НОВАЯ ПАПКА (~30 JSON)
└── modules/Currencies/InitialCurrenciesSeed.service.ts  ← + RUB

packages/email-components/                ← переводы email-шаблонов
```

## 5. Фазированный план

### Step 0 — Фундамент (2 PR, ~3-4 часа)

**PR #1: Инфраструктура локали `ru`**
- Добавить `'ru'` в `SUPPORTED_LOCALES` в `AppIntlLoader.tsx`
- Создать `lang/ru/index.json` — точная копия `en/index.json` (заглушка; настоящий перевод в PR3+)
- Создать `lang/ru/locale.tsx` — копия `en/locale.tsx` с переводом yup-сообщений на русский
- **НЕ создавать** `lang/ru/authentication.tsx` — в `en/` он мёртвый код (verified)
- Расширить `transformMomentLocale` — `'ru'` → `'ru'` (moment имеет встроенную русскую локаль)
- Создать `packages/webapp/scripts/lang-check.js` — сравнение ключей между ru/en JSON. Добавить script `"lang:check": "node scripts/lang-check.js"` в `package.json`
- **Проверка:** `pnpm dev:webapp`, открыть `http://localhost:4000?lang=ru` — UI не падает, даты в формате `21 мая 2026`, остальные строки английские (потому что текст в `ru/index.json` ещё английский — это заглушка)
- **Проверка:** `pnpm run lang:check` — выводит "0 missing keys"
- **Откат:** `git revert`

**PR #2: Валюта RUB + русские числовые форматы**
- В `constants/currencies.tsx`: добавить `{ name: intl.get('russian_ruble'), code: 'RUB' }`
- В `server/.../InitialCurrenciesSeed.service.ts`: добавить запись RUB при сидинге БД
- В `lang/en/index.json` И `lang/ru/index.json` добавить ключ `russian_ruble` ("Russian Ruble" / "Российский рубль")
- Создать helper `webapp/src/utils/accountingFormat.ts` — конфигурация `accounting.settings` с русским thousand-separator (`' '`) и decimal (`','`) для текущей локали
- **«Дефолтная для новых организаций»** — это UI-предпопуляция в форме создания организации (`OrganizationSetupForm`). Когда `currentLocale === 'ru'`, пресет валюты — `RUB`. Не меняем модель данных, не делаем миграций — только UI-дефолт.
- **Проверка:** в форме создания организации (`/setup`) виден `RUB - Российский рубль` в списке валют. Если язык `ru` — `RUB` предзаполнен. В дашборде суммы отображаются как `1 234,56 ₽`.
- **Откат:** `git revert`. (Существующие организации не затрагиваются.)

### Steps 1-13 — Перевод по модулям

Каждый модуль = 1 PR. Внутри каждого PR:
1. Найти все ключи модуля в `lang/en/index.json` (например, все с префиксом `customers.*`)
2. Перевести в `lang/ru/index.json` (AI-драфт + ручная проверка)
3. Запустить `pnpm typecheck`
4. Запустить `pnpm dev:webapp`, переключиться на `?lang=ru`
5. Пройти по страницам модуля — нет английских строк
6. Запустить `pnpm run lang:check` (новый скрипт, добавляем в Step 0)
7. Если есть хардкод-строки (не через `intl.get()`) — заменить через `intl.get('...')` и добавить ключ

## 6. Тестирование

### 6.1 Ручная проверка per-PR

Каждый PR имеет в описании чек-лист:
- [ ] `pnpm typecheck` без ошибок
- [ ] `pnpm dev:webapp` запускается, переключение на `?lang=ru` работает
- [ ] Все страницы модуля визуально проверены, нет английских строк
- [ ] Нет ошибок в консоли браузера (особенно `intl.get() missing key`)
- [ ] Существующие Playwright e2e-тесты проходят на `en`

### 6.2 Автоматическая проверка

**Новый скрипт `packages/webapp/scripts/lang-check.js`** — добавляется в Step 0:
- Сравнивает ключи `lang/ru/index.json` и `lang/en/index.json`
- Выводит missing/extra keys
- Завершается с exit code 1 если есть missing keys (для CI)
- Вызывается через `pnpm run lang:check`

**JSON-валидация:** Vite уже валидирует JSON при импорте.

### 6.3 E2E (опционально)

После Step 16: добавить один Playwright-тест, который переключается на `ru` и проверяет ключевые экраны (Login, Dashboard, новый счёт). Этого достаточно как smoke-test.

## 7. Обработка ошибок

| Сценарий | Поведение | Защита |
|----------|-----------|--------|
| Отсутствующий ключ в `ru/index.json` | Fallback на `en` (по умолчанию react-intl-universal) | Скрипт `lang:check` |
| Невалидный JSON | Splash screen бесконечно | JSON-валидация в Vite + git-hook |
| Хардкод-строка не переведена | Английский текст в UI | Визуальная проверка в PR |
| `lang/ru/` отсутствует | Падение при импорте | Не может случиться (PR atomic) |
| Юзер выбрал `ru`, но не залогинен | Locale из localStorage → URL `?lang=ru` | Уже работает в `determineLocale` |

## 8. Стратегия отката

- **Каждый PR атомарный**, откат через `git revert <commit_hash>`
- **Нет миграций БД** в скоупе → откат тривиален
- **Языковой переключатель остаётся всегда**: если что-то ломается в `ru`, пользователь переключается на `en` без потери данных
- **Если плохая строка в `ru/index.json`**: можно `git revert`, или удалить ключ (fallback на en), или править live на проде (это просто JSON)

## 9. Зависимости и риски

### Зависимости
- pnpm 9.x, Node 18.16.1 (см. `.claude/CLAUDE.md`)
- `react-intl-universal` v2.4.7 — стабильная версия, обновлять не требуется
- `moment` v2.24+ — встроенная русская локаль уже есть
- `accounting` v0.4.1 — поддерживает кастомные format-strings

### Риски

| Риск | Вероятность | Митигация |
|------|------------|-----------|
| Терминология не понравится первым пользователям | Средняя | Итерируем — `index.json` правится за минуту |
| Хардкод-строк больше, чем кажется | Средняя | Скрипт grep по проекту в начале Step 0 |
| Некоторые UI-компоненты не поддерживают RTL/LTR-переключение | Низкая | Русский — LTR, как английский. Проблем не должно быть. |
| Сломан существующий e2e на en | Низкая | Запускаем e2e в каждом PR |
