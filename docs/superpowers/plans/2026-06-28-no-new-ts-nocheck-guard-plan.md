# Guard: запрет НОВЫХ `@ts-nocheck` (борьба с долгом №2)

> **Статус: Трек A РЕАЛИЗОВАН** (коммит `c66934877`). Скрипт-ядро, pre-commit
> и CI-воркфлоу готовы и проверены (блокировка нового @ts-nocheck, грандфазер
> существующих, e2e-тест хука). Трек B (полный ESLint) — по-прежнему опционален.

> **Для исполнителя:** шаги размечены чекбоксами (`- [ ]`). Это инфраструктурная задача (хуки + CI), не фича — TDD-скилл не обязателен; проверка = ручной прогон хука на тест-коммите.

**Проблема.** В `packages/webapp` ~250 файлов с `// @ts-nocheck` (≈8% кода) — в них проверка типов полностью отключена, баги не ловятся. Чинить все разом нельзя. Но можно **остановить рост**: не давать добавлять новые `@ts-nocheck`. Сейчас этого барьера нет.

**Почему НЕ «починить ESLint».** Разведка 2026-06-28: у `webapp` фактически нет рабочего ESLint — установлен eslint 8.57, но `@typescript-eslint/parser` 2.34 (2019 г., несовместим), нет конфига, нет скрипта `lint`. Полный ремонт = апгрейд typescript-eslint (→ `pnpm install`, изменение lockfile, риск на Windows), новый flat-config, правило `ban-ts-comment`, и всё равно нужна стратегия «грандфазер» для 250 существующих файлов. Это отдельный большой трек (см. «Трек B» внизу). Для самой цели он избыточен.

**Решение (Трек A, рекомендуется).** Лёгкий страж на Node, который смотрит только **добавленные строки** в дифф-е коммита/PR. Существующие 250 файлов не трогаются (их строки не «добавленные»), поэтому грандфазер получается автоматически — без allowlist. Подключается в пустой `.husky/pre-commit` + дублируется в CI (на случай `--no-verify`).

**Точки подключения (уже есть в репо):**
- `.husky/pre-commit` — сейчас пустой (только подключает `husky.sh`). Идеальное место.
- `.github/workflows/typecheck.yml` — образец CI (ubuntu, pnpm 9, node 18, `--frozen-lockfile`).

**Конвенции репо:** Node 18.16.1. Коммит-сабджект с маленькой буквы; **тело коммита ≤100 символов в строке** (husky commitlint). Стейджить пути явно (`git add <paths>`), не `git add -A` (в дереве есть посторонняя `tools/`). Без push/PR без явной просьбы. Хуки исполняются в sh (Git Bash на Windows) → скрипт на Node ради переносимости.

## Структура файлов

- `scripts/check-no-new-ts-nocheck.mjs` — *создать*: ядро проверки (Node, без зависимостей).
- `.husky/pre-commit` — *изменить*: вызвать скрипт по staged-диффу.
- `.github/workflows/no-new-ts-nocheck.yml` — *создать*: тот же скрипт по дифф-у PR против базовой ветки.

## Task 1: Скрипт-ядро проверки

**Файл:** создать `scripts/check-no-new-ts-nocheck.mjs`.

Логика:
- Режим по умолчанию (локально): `git diff --cached -U0 --diff-filter=ACM -- '*.ts' '*.tsx'` — взять только **добавленные** строки (начинаются с `+`, но не `+++`).
- Режим CI: `--base <ref>` → сравнивать `git diff <ref>...HEAD -U0 ...`.
- Если среди добавленных строк есть совпадение с `/@ts-nocheck/` — собрать список `файл:строка`, напечатать понятное сообщение и `process.exit(1)`. Иначе exit 0.
- Сообщение об ошибке (RU, для основателя): объяснить, что новый `@ts-nocheck` запрещён, и как быть (типизировать файл; в исключительном случае — осознанный обход `--no-verify` с пояснением в PR).

- [ ] **Step 1:** написать скрипт (парсинг `git diff -U0`, выделение `+`-строк и их номеров через хедеры `@@`).
- [ ] **Step 2:** ручной тест — создать временный файл с `// @ts-nocheck`, `git add`, прогнать скрипт → ожидать exit 1 и имя файла; убрать строку → exit 0. Откатить тестовый файл.

## Task 2: Подключить в pre-commit

**Файл:** изменить `.husky/pre-commit`.

- [ ] **Step 1:** добавить строку запуска ядра в режиме staged. Использовать Node 18 (в хуке — относительный вызов `node ./scripts/check-no-new-ts-nocheck.mjs`).
- [ ] **Step 2:** проверить, что обычный коммит без `@ts-nocheck` проходит, а коммит с новым `@ts-nocheck` блокируется. Подтвердить, что существующий файл с уже имеющимся `@ts-nocheck` (без правок этой строки) коммитится свободно.

## Task 3: Продублировать в CI (защита от `--no-verify`)

**Файл:** создать `.github/workflows/no-new-ts-nocheck.yml` по образцу `typecheck.yml`.

- [ ] **Step 1:** триггеры `pull_request` (paths: `**.ts`, `**.tsx`). `actions/checkout` с `fetch-depth: 0` (нужна база для диффа).
- [ ] **Step 2:** один шаг: `node scripts/check-no-new-ts-nocheck.mjs --base origin/${{ github.base_ref }}`. Без `pnpm install` — скрипт без зависимостей, быстро.
- [ ] **Step 3:** проверить на тест-PR, что добавление `@ts-nocheck` валит чек, а обычные правки — нет.

## Task 4: Зафиксировать

- [ ] Стейджить явно три пути, один коммит: `chore(repo): запрет новых @ts-nocheck (pre-commit + CI)`.
- [ ] Тело коммита ≤100 симв./строка. Без push/PR без явной просьбы основателя.

## Трек B (опционально, больше): полноценный ESLint для webapp

Делать отдельно, если нужен линтинг шире, чем один guard. Грубая последовательность:
1. Апгрейд `@typescript-eslint/{parser,plugin}` 2.x → совместимая версия под eslint 8 (требует `pnpm install` — спросить основателя; известные грабли bcrypt на Windows касаются server, не webapp).
2. Добавить конфиг (flat `eslint.config.js`, как в `shared/*`) + скрипт `lint` в `packages/webapp/package.json`.
3. Правило `@typescript-eslint/ban-ts-comment` c `ts-nocheck: true`. Для грандфазера 250 файлов — либо baseline-плагин, либо запускать eslint только по изменённым файлам (lint-staged). Без этого CI станет красным на 250 ошибок.
4. Включить в CI отдельным джобом (не блокировать на легаси-находках сразу — сначала warn).

**Вывод:** Трек A закрывает заявленную цель (стоп росту долга №2) дёшево и кросс-платформенно. Трек B — это уже «вернуть линтинг вообще», самостоятельная инициатива.
