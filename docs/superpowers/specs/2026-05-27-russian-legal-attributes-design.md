## 1. Контекст и цели

### Что мы строим

Базовую инфраструктуру российских юридических реквизитов в Bigfin: поля ИНН/КПП/ОГРН/банковские реквизиты в сущностях Organization и Customer/Vendor, юр.форму и налоговый режим организации, российские ставки НДС.

### Sub-project ② был разбит на три части

При брейншторме (2026-05-27) выяснилось, что исходный scope Sub-project ② («российская юр.специфика») слишком велик для одного цикла. Разбиение:

- **②a (этот документ):** Реквизиты + НДС-ставки. Фундамент. 3–5 недель.
- **②b:** План статей учёта (управленческий, ориентированный на РФ). Независим от ②a. 2–3 недели.
- **②c:** Печатные формы (Счёт на оплату, УПД, Акт выполненных работ, ТОРГ-12+С/Ф). Зависит от ②a. 5–8 недель.

### Целевая аудитория продукта

Предприниматели без бухгалтерского образования. Аудитория широкая: ООО, ИП, самозанятые (НПД), АО — все юр.формы охватываются на старте. Налоговые режимы: УСН (Доходы 6% и Доходы−Расходы 15%), ОСНО, Патент, АУСН.

### Целевая аудитория документа

Основатель Bigfin (исполнитель) + Claude (со-разработчик).

### Принципы (наследуются из roadmap §4)

1. **Additive миграции только** — все новые колонки `nullable: true`, никакого `DROP COLUMN`, никакого `ALTER NOT NULL`.
2. **Каждый PR обратим** через `git revert`. Каждая миграция имеет работающий `down()`.
3. **Existing data не ломается** — организации/контакты без новых полей продолжают работать.
4. **EN-локаль продолжает работать** — все сообщения и UI на EN остаются.

### Критерий завершения

После ②a можно:
- Создать организацию-ООО или ИП с ИНН/КПП/ОГРН и банковскими реквизитами
- Создать контрагента (Customer или Vendor) с юр.формой и реквизитами
- Выписать счёт/расход с корректной налоговой ставкой по умолчанию исходя из tax_regime организации
- Получить локализованное сообщение об ошибке валидации при невалидном ИНН/ОГРН

### Что НЕ входит в ②a

- Печатные формы УПД/Акта/Счёта на оплату — это ②c
- Адаптация плана статей учёта — это ②b
- Onboarding-wizard с выбором юр.формы — это Sub-project ③
- ЭДО (Контур, Диадок) — отдельный under-project в будущем
- Полный РСБУ — продукт управленческий, не нужно
- OKPO — отложено в backlog (мало где требуется в МСБ)
- Существование ИНН в реестре ФНС / интеграция с DaData — отдельная задача, возможно в ⑨c

## 2. Решения по моделированию

### 2.1 Хранение реквизитов — отдельные колонки

Между тремя подходами (колонки / отдельная таблица / JSON) выбран **вариант А — отдельные nullable-колонки в существующих таблицах**:

| Критерий | A. Колонки | B. Отдельная таблица | C. JSON |
|---|---|---|---|
| Простота | ✅ | ⚠ JOIN | ⚠ парсинг |
| Соответствие §4.1 roadmap | ✅ | ⚠ требует FK + cascade-delete | ✅ |
| Индексы на ИНН для поиска | ✅ | ✅ | ❌ |
| Гибкость для других стран | ❌ | ✅ | ✅ |

Bigfin сейчас ориентирован на РФ-рынок. Гипотетическая поддержка других стран не оправдывает усложнение архитектуры. Если в будущем добавится Казахстан/Беларусь — рефакторинг на B или C будет дешевле, чем сейчас платить за гибкость, которая не используется.

### 2.2 Юр.формы и налоговые режимы — enum в коде

Юр.форма организации хранится как строка с конечным набором значений: `OOO | IP | NPD | AO`. Налоговый режим: `USN_INCOME | USN_INCOME_EXPENSE | OSNO | PATENT | AUSN`. Эти константы — на уровне TypeScript-enum'ов в server/webapp, без отдельной таблицы-справочника. Причина: список фиксирован законодательством РФ, меняется редко, отдельная таблица — оверинжиниринг.

### 2.3 Контрагенты-физлица

В `contacts.legal_form` добавляется значение `INDIVIDUAL` — для случаев «продал физлицу». Поля ИНН/КПП/ОГРН для INDIVIDUAL остаются NULL. На UI для физлица скрываются все РФ-реквизиты.

## 3. Архитектура

### 3.1 Модель данных

#### Таблица `organizations` — новые nullable колонки

| Колонка | Тип | Описание |
|---|---|---|
| `legal_form` | varchar(20) | `OOO` / `IP` / `NPD` / `AO`. NULL = не РФ-организация. |
| `tax_regime` | varchar(20) | `USN_INCOME` / `USN_INCOME_EXPENSE` / `OSNO` / `PATENT` / `AUSN`. |
| `inn` | varchar(12) | 10 цифр для ООО/АО, 12 для ИП/НПД. |
| `kpp` | varchar(9) | 9 цифр. Не заполняется для ИП и НПД. |
| `ogrn` | varchar(15) | 13 ОГРН для ООО/АО, 15 ОГРНИП для ИП. NPD без ОГРН. |
| `bank_name` | varchar(255) | Например «АО Тинькофф Банк». |
| `bank_bik` | varchar(9) | БИК банка. |
| `bank_account` | varchar(20) | Расчётный счёт организации. |
| `bank_correspondent_account` | varchar(20) | Корр.счёт банка. |

#### Таблица `contacts` (Customer + Vendor) — новые nullable колонки

| Колонка | Тип | Описание |
|---|---|---|
| `legal_form` | varchar(20) | `OOO` / `IP` / `NPD` / `AO` / `INDIVIDUAL`. |
| `inn` | varchar(12) | Опционально. |
| `kpp` | varchar(9) | Опционально (только для ООО/АО). |
| `ogrn` | varchar(15) | Опционально. |
| `bank_name` | varchar(255) | Опционально — для контрагентов, которым переводим оплату. |
| `bank_bik` | varchar(9) | Опционально. |
| `bank_account` | varchar(20) | Опционально. |
| `bank_correspondent_account` | varchar(20) | Опционально. |

#### Таблица `tax_rates` — сидинг русских ставок

Новые записи, добавляемые сид-функцией:

| code | name | rate | description |
|---|---|---|---|
| `VAT_20` | НДС 20% | 20.00 | Стандартная ставка |
| `VAT_10` | НДС 10% | 10.00 | Льготная (продукты, лекарства, детские товары) |
| `VAT_0` | НДС 0% | 0.00 | Экспорт |
| `VAT_NONE` | Без НДС | 0.00 | Для УСН/Патент/АУСН/НПД |

Существующие записи (`LYD`-эпоха) НЕ удаляются — пользователь может их деактивировать через `active` флаг.

### 3.2 UI

#### Settings → Organization → раздел «Реквизиты (РФ)»

Один экран с тремя группами:

1. **Юр.форма и налогообложение** (всегда видимая)
   - Select «Юр.форма»: ООО / ИП / Самозанятый / АО
   - Select «Система налогообложения»: пять вариантов выше

2. **Регистрационные данные** (поля conditional по `legal_form`)
   - ИНН (всегда; placeholder и валидация меняются по форме)
   - КПП (только ООО/АО)
   - ОГРН/ОГРНИП (ООО/АО → 13 цифр; ИП → 15 цифр; НПД → скрыто)

3. **Банковские реквизиты** (всегда)
   - Наименование банка
   - БИК (9 цифр)
   - Расчётный счёт (20 цифр)
   - Корр.счёт (20 цифр)

#### Customer/Vendor — раскрывающийся блок «Реквизиты (РФ)»

В существующей форме создания контрагента — добавляется опциональная секция, всё необязательно:

- Select «Юр.форма контрагента»: Юр.лицо (ООО/АО) / ИП / Самозанятый / Физлицо
- При не-физлице: ИНН, КПП (если Юр.лицо), ОГРН/ОГРНИП
- Опциональный подблок «Банковские реквизиты получателя» — для Vendor'ов, кому переводим оплату

#### Бейдж юр.формы в списках

В таблице контрагентов рядом с именем — маленький бейдж: `ООО`, `ИП`, `Сам.`, `Физ.`, или ничего.

### 3.3 Автоподстановка налоговой ставки

При создании Invoice/Bill дефолтная ставка определяется по `tax_regime` организации:

| `tax_regime` | Дефолтная ставка |
|---|---|
| `USN_INCOME` / `USN_INCOME_EXPENSE` | `VAT_NONE` (Без НДС) |
| `OSNO` | `VAT_20` (НДС 20%) |
| `PATENT` / `AUSN` | `VAT_NONE` |

Это **только дефолт** — пользователь меняет ставку в строке счёта вручную.

### 3.4 Валидация

#### Правила

| Поле | Длина | Формат | Контр. сумма |
|---|---|---|---|
| ИНН (юр.лицо) | 10 | только цифры | да, последняя цифра |
| ИНН (физлицо/ИП) | 12 | только цифры | да, последние две |
| КПП | 9 | цифры; на позициях 5-6 допускается лат. буква | нет |
| ОГРН | 13 | только цифры | да |
| ОГРНИП | 15 | только цифры | да |
| БИК | 9 | только цифры, начинается с `04` | нет |
| Расчётный счёт | 20 | только цифры | нет (на старте) |
| Корр.счёт | 20 | только цифры, начинается с `30101` | нет (на старте) |

#### Уровни валидации

1. **Webapp (yup-схема в Formik):** показ ошибки сразу. Сообщения через `intl.get('validation.<field>.<rule>')`.
2. **Server (NestJS class-validator):** повторная проверка на сохранении в БД. Возвращает 422 с локализованной ошибкой через `nestjs-i18n` (используется `ru/validation.json`, новый файл).
3. **БД:** check-constraint на длину **не добавляем** — дублирует app-валидацию и усложняет миграции при изменении правил.

#### Локализация ошибок

Новые ключи добавляются в `translations/ru.json` (через workflow ①):
- `validation.inn.length`, `validation.inn.checksum`
- `validation.kpp.length`, `validation.kpp.format`
- `validation.ogrn.length`, `validation.ogrn.checksum`
- `validation.ogrnip.length`, `validation.ogrnip.checksum`
- `validation.bik.length`, `validation.bik.prefix`
- `validation.bank_account.length`, `validation.correspondent_account.length`

Server-сторона: новый файл `packages/server/src/i18n/ru/validation.json` (рядом с существующими 30 файлами).

## 5. Стратегия отката

- **Каждая миграция — отдельный PR**, имеющий рабочий `down()` метод.
- **Откат на проде:** `pnpm --filter @bigfin/server run db:migrate:rollback` — последняя миграция откатывается.
- **Откат серии PR:** `git revert <merge-commit>` на каждой ветке в обратном порядке.
- **Existing data:** колонки nullable — null-значения для существующих записей не ломают логику. Все consumers (UI, API, сервисы) трактуют `legal_form === null` как «не РФ-организация» и используют существующий генерик-flow.
- **Если что-то ломается на `?lang=ru`:** переключение на `?lang=en` — всё работает без РФ-полей (они просто не отображаются).

## 6. Тестирование

### 6.1 Unit-тесты

- **Webapp (Vitest):** валидаторы (10+ кейсов на каждый), Formik-схемы с conditional fields
- **Server (Jest):** class-validators, OrganizationService.update с новыми полями

### 6.2 Integration-тесты

- Создание организации через API с заполненными ИНН/КПП → проверка БД
- Обновление с невалидным ИНН → 422 с локализованной ошибкой
- Создание Customer с `legal_form = INDIVIDUAL` без ИНН → успех
- Создание Invoice с организацией на УСН → дефолтная ставка `VAT_NONE`

### 6.3 E2E (Playwright)

- Один сценарий ru-локали: Settings → Organization → заполнить РФ-реквизиты → сохранить → перезагрузить → значения сохранились
- Один регрессионный сценарий en-локали: существующий e2e зелёный

## 7. Acceptance criteria для ②a

1. Можно создать организацию-ООО или ИП с заполненными ИНН/КПП/ОГРН и банковскими реквизитами.
2. Можно создать Customer и Vendor с юр.формой и реквизитами; форма меняется в зависимости от выбранной юр.формы.
3. В справочнике налоговых ставок есть НДС 20%, НДС 10%, НДС 0%, Без НДС.
4. При создании Invoice/Bill автоподстановка налоговой ставки по `tax_regime` организации работает.
5. ИНН (10 и 12 цифр) и ОГРН/ОГРНИП валидируются по контрольной сумме на фронте и на сервере.
6. Сообщения об ошибках валидации локализованы (en + ru).
7. Organizations и contacts без заполненных РФ-полей продолжают работать без регрессий.
8. Существующие Playwright e2e на `en` остаются зелёными.
9. `pnpm run lang:check` и `pnpm typecheck` — exit 0.

## 8. Зависимости и риски

### Зависимости

- Sub-project ① (русская локаль) — выполнен.
- Существующая инфраструктура yup + Formik (используется во всём webapp).
- Существующая `nestjs-i18n` (уже работает после Sub-project ①).
- knex.js для миграций (стандартный стек проекта).

### Риски

| # | Риск | Вероятность | Митигация |
|---|---|---|---|
| 1 | Алгоритм checksum ИНН/ОГРН неточный | Низкая | Использовать существующую npm-библиотеку (`validations` или подобную) либо документированный алгоритм ФНС. Покрыть unit-тестами с известными валидными/невалидными ИНН. |
| 2 | conditional fields в Formik глючат при смене юр.формы | Средняя | При смене `legal_form` явно очищать неактуальные поля (`setFieldValue('kpp', '')` для ИП). Тестировать в Vitest. |
| 3 | Невалидные данные у существующих организаций после миграции | Очень низкая | Колонки nullable, миграция ничего не заполняет. Существующие записи просто получают NULL. |
| 4 | Терминология не подойдёт пользователям | Средняя | Все названия полей через `intl.get()` — терминологические правки мгновенные. |
| 5 | Конфликт с будущими интеграциями (DaData, ФНС API) | Низкая | Поля простые строки, любая интеграция надстраивается сверху без миграций. |

## 9. Открытые вопросы

1. **Справочник банков по БИК** — есть ли смысл подгрузить справочник ЦБ РФ для автоподстановки названия банка/корр.счёта по БИК? Решение — в backlog, возможно в Sub-project ⑨c (банковские API).
2. **DaData для автозаполнения** — интеграция с `https://dadata.ru/api/` для автозаполнения по ИНН (название, адрес и т.д.). Очень удобная фича, но требует API-ключа и платной подписки. Решение — после первых dogfooding.
3. **OKPO** — не входит в ②a. Если хотя бы один пользователь попросит — добавим в backlog.
4. **Бейдж юр.формы для физлица** — показывать `Физ.` или скрывать вообще? Решение — после первых пользователей, фокус-группа.

## 10. Что после ②a

Согласно [дорожной карте](2026-05-27-fintablo-planfact-parity-roadmap.md), следующие шаги Sub-project ②:

- **②b — План статей учёта (русский управленческий).** Независим от ②a, можно начать параллельно (если будет ассистент или вторая итерация). Оценка: 2–3 недели.
- **②c — Печатные формы** (Счёт на оплату, УПД, Акт выполненных работ, ТОРГ-12+С/Ф). Зависит от ②a (используются заполненные реквизиты). Оценка: 5–8 недель.

После ② целиком (a+b+c) — Sub-project ③ (режимы Бизнес/Бухгалтерский + Onboarding).
