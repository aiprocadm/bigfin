# ⑨ Банковские выписки — импорт операций (дизайн)

**Дата:** 2026-06-22
**Статус:** согласовано основателем (брейншторм), готово к плану Фазы 1
**Флаг:** `bank_statement_import` (off по умолчанию)
**Роадмап:** Ф4, пункт ⑨. Следующее за ним по запросу: ⑯ CRM / ㉕ фин.коэффициенты.

---

## 1. Контекст и цель

Bigfin — российский управленческий учёт для предпринимателей без бухгалтерского
образования; основатель сам пользователь (dogfooding) → приоритет простоте и скорости
повседневных операций. Сейчас денежные операции вводятся вручную. Цель ⑨ — загрузить
файл банковской выписки и за несколько кликов превратить его в учтённые операции
(доходы/расходы), не задваивая выручку по уже выставленным счетам.

### Ключевая находка разведки (2026-06-22)

Bigfin унаследовал от базовой кодовой базы **целый банковский конвейер**, и он
**подключён и доступен** (в отличие от вырезанных «Проектов»):

- Роуты живые: `/cashflow-accounts` (денежные счета), `/cashflow-accounts/:id/transactions`
  (категоризация/сопоставление, вкладки «Непривязанные/Ожидающие/Распознанные/Исключённые»),
  `/cashflow-accounts/:id/import` (импорт), `/bank-rules` (правила).
- Серверные модули: `Import` (загрузка→маппинг→предпросмотр→процесс), `BankingCategorize`
  (непривязанные операции + категоризация→проводка), `BankingMatching` (сопоставление со
  счетами/накладными/расходами), `BankRules` (хранилище правил), `BankingTransactions`
  (`CreateBankTransactionService` → проводки GL), `BankingPlaid` (за флагом `BankSyncing`,
  для РФ бесполезен — Plaid не работает с российскими банками).

Поэтому ⑨ — это **«дотянуть конвейер под РФ + русифицировать»**, а не «строить с нуля».
Зеркалит успешный приём «Сделки переиспользовали Проекты».

### Российские разрывы, которые надо закрыть

1. **Парсер формата 1С (.txt, `1CClientBankExchange`)** — отсутствует. Универсальный формат
   выгрузки почти всех банков РФ; несёт ИНН, назначение платежа, дебет/кредит.
2. **Сопоставление контрагента по ИНН** — поля ИНН у `Contact` есть (миграция 2026-05-27),
   но finder по ИНН отсутствует. Имя — ненадёжный ключ, ИНН — надёжный.
3. **Память по контрагенту** (контрагент → статья) — отсутствует.
4. **Движок применения правил** (`BankRules`) — хранилище есть, применения нет.
5. **Защита от дублей** при повторном импорте — отсутствует полностью.
6. **Русификация** затронутых экранов (унаследованный UI в западном бухгалтерском стиле).

## 2. Решения основателя (брейншторм 2026-06-22)

| Вопрос | Решение |
|---|---|
| Форматы файлов | **1С (.txt) — основной**; CSV/Excel конкретного банка — второй (Фаза 3) |
| Результат импорта | **Категоризация + умное сопоставление** (платёж по счёту Bigfin → предложить привязать, не задваивая выручку) |
| Новый контрагент (нет по ИНН) | **Предложить создать одним кликом** (имя+ИНН подставлены); не молча, не пропускать |
| Авто-статья | **Память по контрагенту + правила** (`BankRules`) |
| Подход к коду | **A — дотянуть существующий конвейер** (макс. реюз, мин. риск) |
| Разбивка | **Фазы 1→2→3 отдельными PR**; начинаем с Фазы 1 |
| Дубли при повторной загрузке | **Показать «загружено N, пропущено M дублей»** |
| Тестовый файл | Парсер по стандарту `1CClientBankExchange`; реальный файл — на живой приёмке |

## 3. Архитектура (подход A)

Поток (переиспользует существующий конвейер):

```
файл .txt (1С)
   │  parse1CStatement(text)  ← НОВОЕ (чистая функция, cp1251)
   ▼
канонические записи { дата, сумма, приход/расход, контрагент, ИНН, назначение, №док }
   │  Import1CStatement.service  ← НОВОЕ (дедуп + направление + цикл)
   ▼
CreateUncategorizedTransactionService.create(...)  ← СУЩЕСТВУЕТ
   ▼
«Разбор» (uncategorized_cashflow_transactions)  ← СУЩЕСТВУЕТ (+2 колонки)
   │  экран разбора: контрагент по ИНН / «создать», статья
   ▼
CategorizeBankTransaction.categorize(ids, dto+contactId)  ← РАСШИРИТЬ (contactId)
   ▼
проводка (cashflow_transactions + GL)  ← СУЩЕСТВУЕТ
```

### Изоляция и границы единиц

- **`parse1CStatement(text): ParsedStatementRecord[]`** — чистая, без I/O и без БД; вся логика
  формата 1С здесь; легко тестируется фикстурой. Вход — декодированный текст, выход — массив
  записей. Декодирование cp1251 — отдельная утилита-обёртка (см. §6).
- **`Import1CStatement.service`** — оркестрация: декодировать → parse → определить направление
  по расчётному счёту → отфильтровать дубли по `external_id` → создать непривязанные через
  существующий сервис. Возвращает `{ imported: N, skipped: M }`.
- **`GetContactByInn` (finder в Contacts)** — `Contact.query().where('inn', inn)`; одна ответственность.
- **Расширение `CategorizeBankTransaction`** — добавить опциональный `contactId` в DTO и
  пробросить на создаваемую проводку (поведение без `contactId` не меняется).

## 4. Объём по фазам

### Фаза 1 — «Выписка попадает в Bigfin» (этот PR)

- Парсер 1С (.txt, cp1251).
- Эндпоинт импорта по выбранному денежному счёту → строки в «Разбор».
- Защита от дублей (`external_id`), отчёт «загружено N / пропущено M».
- Контрагент по ИНН: найден → привязать; не найден → создать из {имя, ИНН} одним кликом.
- Подтверждение строки → проводка (доход/расход + контрагент + статья).
- Русификация затронутых экранов.

### Фаза 2 — «Bigfin угадывает статью» (отдельный PR)

- Память по контрагенту (контрагент → статья по умолчанию; учится на подтверждениях).
- Движок применения правил `BankRules` (найти подходящее правило для строки).

### Фаза 3 — «Умное сопоставление + другие банки» (отдельный PR)

- Подсказка «привязать к счёту #N» через `BankingMatching` (не задваивая выручку).
- Импорт CSV/Excel конкретного банка через существующий маппинг колонок.

## 5. Изменения в данных (Фаза 1)

Аддитивная **tenant**-миграция (с рабочим `down()`):

- `uncategorized_cashflow_transactions`:
  - `payee_inn` — `string(12)`, nullable. ИНН контрагента из выписки (для сопоставления и
    показа до создания контакта).
  - `external_id` — `string`, nullable, **индекс**. Ключ дедупликации.
- `cashflow_transactions`:
  - `contact_id` — `integer unsigned`, nullable, FK на `contacts` — **только если поля ещё нет**
    (проверить на этапе плана; возможно, уже есть).

Дедуп-ключ `external_id` = устойчивый хеш `(№документа + дата + сумма + направление)`.
Проверка дубля — по `(account_id, external_id)` перед вставкой.

## 6. Крайние случаи и риски

- **Кодировка cp1251.** Файлы 1С обычно cp1251 (реже UTF-8). Node нативно cp1251 не декодирует.
  *Риск:* нужна `iconv-lite`. План: проверить, есть ли она транзитивно в проекте; если нет —
  встроенная таблица перекодировки cp1251→Unicode (без `pnpm install`, по правилу основателя).
  Определение кодировки: по сигнатуре/попытке, дефолт cp1251.
- **Битый/частичный файл** → понятная ошибка «Не удалось разобрать файл выписки», импорт не идёт.
- **Счёт не совпал ни с плательщиком, ни с получателем** → строка помечается «уточните
  приход/расход», не угадываем вслепую.
- **Несколько счетов в файле** → импортируем только документы по выбранному денежному счёту.
- **Валюта** → берём валюту денежного счёта; валютные выписки вне Фазы 1.
- **Форматы**: дата `ДД.ММ.ГГГГ`, десятичная запятая в суммах.

## 7. Тестирование

- **Юнит (TDD): `parse1CStatement`** на фикстуре формата `1CClientBankExchange` (несколько
  документов, приход+расход, cp1251) — корректные дата/сумма/направление/ИНН/назначение/№.
- Юнит: устойчивость `external_id`; `GetContactByInn`; создание контрагента из {имя, ИНН}.
- Серверный интеграционный: импорт-эндпоинт (разбор→«Разбор», счётчик пропущенных дублей,
  повторный импорт того же файла → 0 новых).
- Статическая приёмка: `pnpm typecheck` (3 пакета), `lang-check` (парность EN↔RU),
  `pnpm --filter @bigfin/server test` (новые наборы зелёные), ru-translation-reviewer.
- **Живая приёмка** на локальном стеке: импорт реального обезличенного файла, создание
  контрагента по ИНН, подтверждение строки → проводка, остаток счёта меняется; миграция
  `latest → rollback → latest`.

---

## 8. Anti-scope (не входит)

- PDF-выписки.
- Прямая интеграция с банком по API (аналог Plaid для РФ).
- Авто-постинг без подтверждения пользователем.
- Мультивалютная переоценка.
- Перемещения между своими счетами как отдельный распознаваемый класс (в Фазе 1 — обычный доход/расход).
