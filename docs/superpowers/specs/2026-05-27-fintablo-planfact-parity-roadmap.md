### Архитектурные решения брейншторма 2026-06-05

1. **Структура патча — вариант B.** Каждый найденный пробел = отдельный под-проект ⑲–㉛ (а не расширение существующего). Причина: максимум видимости и трекинга parity-фич. Tier 3/4 формально получают свои номера, но тесно привязаны к базовым ④/⑦/⑮/②a (отмечено в зависимостях).
2. **Telegram-бот — рано, Capacitor — по плану.** ㉓ (ввод операций) выносится в Ф2 как ранняя мобильность (приоритет основателя) и ничем не блокируется. ⑬b Capacitor остаётся в Ф3 как полноценное нативное приложение — Telegram его не заменяет, а даёт раннюю мобильность.
3. **Метод начисления — кассовый по умолчанию + тумблер.** Снимает соответствующий пункт из anti-scope каркаса (§7 спеки 2026-05-29). Движок ОПиУ BigCapital по природе двойной записи начисленный; «начисление» — это представление-тумблер над существующим леджером, а не новый расчёт. См. ㉙ и §4.13.

### Новые под-проекты v4 (⑲–㉛)

#### Кластер «Капитал, долги, имущество» (Tier 1)

##### Sub-project ⑲ — Дивиденды / вывод средств собственнику ⚡v4

- **Scope:** расчёт чистой прибыли, доступной к выводу; регистрация выплат собственнику; статья капитала «Выплаты собственнику»/«Дивиденды»; история выплат и остаток нераспределённой прибыли; подсказка «безопасной к выводу суммы» с учётом будущих обязательств из ⑥/⑭.
- **НЕ входит:** авто-расчёт НДФЛ 13% с дивидендов в бюджет (можно завести как обычную статью налога); распределение между несколькими учредителями по долям (v2); юридическое оформление решения о выплате.
- **Критерий завершения:** в режиме «Бизнес» видно «доступно к выводу», можно зарегистрировать выплату, она отражается в ДДС/ОПиУ/Балансе, появляется предупреждение при риске кассового разрыва.
- **Зависимости:** ④, ⑥; желательно ⑭ (обязательства) для «безопасной суммы».
- **Оценка:** 3–5 недель.
- **Приоритет:** Ф3b — высокая ценность для dogfooding (основатель сам выводит деньги из бизнеса).

##### Sub-project ⑳ — Кредиты и займы ⚡v4

- **Scope:** учёт полученных кредитов/займов: тело, ставка, график (аннуитет/дифференцированный), разбивка каждого платежа на тело и проценты. Проценты → расход в ОПиУ; тело → обязательство в Балансе. Автогенерация плановых операций для календаря ⑥ из графика. Выгрузка графика, остаток долга.
- **НЕ входит:** выданные займы как актив (зеркальный кейс — v2); лизинг (бэклог); сложная реструктуризация / частичное досрочное погашение с пересчётом графика (базовое — да); банковская выдача кредита.
- **Критерий завершения:** заводится кредит с телом/ставкой/графиком → будущие платежи видны в календаре → проценты падают в ОПиУ → тело уменьшает обязательство в Балансе → виден остаток и график.
- **Зависимости:** ④ (статья «Проценты по кредитам»), ⑥.
- **Оценка:** 4–6 недель.
- **Приоритет:** Ф3b, рядом с ⑲.

##### Sub-project ㉑ — Основные средства и амортизация ⚡v4

- **Scope:** реестр ОС/НМА (стоимость, дата ввода, срок полезного использования, линейный метод — v1); автоматический график амортизации; ежемесячное начисление → расход в ОПиУ; накопленная амортизация и остаточная стоимость в Балансе; выгрузка справочника имущества и графика.
- **НЕ входит:** нелинейные методы амортизации (v2); переоценка; разница БУ/НУ (продукт управленческий — не нужно); сложная проводка прибыли/убытка от продажи ОС (базовое списание — да).
- **Критерий завершения:** объект ОС → авто-график → ежемесячная амортизация в ОПиУ → остаточная стоимость в Балансе → выгрузка работает.
- **Зависимости:** ④ (статья «Амортизация»).
- **Оценка:** 4–6 недель.
- **Приоритет:** Ф3b (независим — может сдвигаться в Ф4).

#### Кластер «Уведомления, Telegram, Заявки» (Tier 2)

##### Sub-project ㉒ — Движок уведомлений ⚡v4

- **Scope:** событийная модель + доставка по каналам (in-app через `Socket`, email через `Mail`, Telegram через ㉓). Четыре типа событий: приближение кассового разрыва (из ⑥), остаток на счёте ниже минимума, счёт клиента не оплачен в срок (из ⑭), подозрительная/ошибочная операция (простые правила: дубль, резкое отклонение суммы). Настройки: события × каналы × пороги.
- **НЕ входит:** SMS/WhatsApp (бэклог, открытый вопрос №10); push на мобильное (это ⑬b/FCM); ML-детекция аномалий.
- **Критерий завершения:** настроил «кассовый разрыв + просрочка → email», получил уведомление при наступлении события; in-app центр уведомлений показывает список.
- **Зависимости:** ⑥ (разрыв/остаток — в коде), ⑭ (просрочка). Переиспользует `Socket` + `Mail`.
- **Оценка:** 4–6 недель.
- **Приоритет:** Ф3b, после ⑭.

##### Sub-project ㉓ — Telegram-бот (ввод операций + канал уведомлений) ⚡v4

- **Scope:** (1) ввод «на ходу» — отправить боту поступление/расход (сумма, статья, счёт, контрагент), бот пишет операцию через существующий API; (2) канал доставки уведомлений из ㉒ и напоминаний о плановых операциях из ⑥; привязка Telegram-аккаунта к пользователю Bigfin.
- **НЕ входит:** отчёты/редактирование в боте (только ввод + уведомления); фото-ввод чеков (это камера в ⑬b); голосовой ввод.
- **Критерий завершения:** привязал Telegram → отправил «+50000 выручка Розница» → операция появилась в Bigfin; кассовый разрыв прилетает в бот.
- **Зависимости:** API ввода операций (уже есть) — **ввод ничем не блокируется**; функция уведомлений включается с ㉒.
- **Оценка:** 4–6 недель.
- **Приоритет:** **Ф2 (ввод)** — ранняя мобильность по решению основателя; половина «уведомления» зажигается при ㉒ (Ф3b). Capacitor ⑬b остаётся в Ф3 по плану.

##### Sub-project ㉔ — Заявки на оплату (согласование платежей) ⚡v4

- **Scope:** сотрудник создаёт заявку (сумма, статья, контрагент, срок, основание); согласующий (владелец/директор) одобряет/отклоняет; одобренная → плановый отток в календаре ⑥. Реестр заявок по статусам; роли «кто создаёт / кто согласует» на базе CASL (`Roles`).
- **НЕ входит:** авто-отправка платежа в банк (ЭКО-сертификация — не входит); многоуровневое согласование (v2); контроль «заявка превышает лимит статьи бюджета ⑤» (позже).
- **Критерий завершения:** заявка создана → согласующий одобрил → она появилась в платёжном календаре как плановый отток.
- **Зависимости:** ⑥, `Roles`.
- **Оценка:** 3–5 недель.
- **Приоритет:** Ф3a, расширяет ⑥.

#### Аналитика и качество (Tier 3)

##### Sub-project ㉕ — Финансовые коэффициенты («Показатели PRO») ⚡v4

- **Scope:** ROE/ROA, ликвидность (текущая/быстрая), оборотный капитал, долговая нагрузка/платёжеспособность; вертикальный анализ ОПиУ (доля статьи от выручки) и горизонтальный (динамика период-к-периоду). Считается из Баланса/ОПиУ.
- **НЕ входит:** кастомные пользовательские коэффициенты (preset-набор на старте); отраслевые бенчмарки; прогноз коэффициентов.
- **Критерий завершения:** на странице видны 6–8 ключевых коэффициентов с фильтром по периоду + верт./гориз. анализ ОПиУ.
- **Зависимости:** ④; расширяет ⑮ Финмодель.
- **Оценка:** 3–5 недель.
- **Приоритет:** Ф4, вместе с/после ⑮.

##### Sub-project ㉖ — Анализ НДС ⚡v4

- **Scope:** выделение и «очистка» сумм от НДС для управленческих отчётов (чтобы прибыль не завышалась на НДС); отчёт «НДС начислен / к вычету / к уплате». На ставках из ②a.
- **НЕ входит:** декларация по НДС в ФНС (не заменяем бухгалтерию); раздельный учёт, экспортный НДС 0% с подтверждением.
- **Критерий завершения:** НДС выделяется в операциях; ОПиУ можно показать «без НДС»; виден отчёт по НДС за период.
- **Зависимости:** ②a (ставки НДС), ④.
- **Оценка:** 3–5 недель.
- **Приоритет:** Ф4 (или раньше рядом с ②a, если НДС-учёт нужен с первых дней).

##### Sub-project ㉗ — Кросс-проверка ОПиУ↔ДДС (качество данных) ⚡v4

- **Scope:** сверка расхождений ОПиУ↔ДДС, операции без статьи, возможные дубли — список «что проверить» с переходом к операции. Опц.: блокировка статей (как у Fintablo).
- **НЕ входит:** автоисправление (только подсветка + переход к источнику).
- **Критерий завершения:** виден отчёт «качество данных» (операции без статьи, расхождения, возможные дубли) с кликом к источнику.
- **Зависимости:** ④.
- **Оценка:** 2–4 недели.
- **Приоритет:** Ф3a, мелкое расширение ④.

##### Sub-project ㉘ — Этапы сделки (поэтапное признание прибыли) ⚡v4

- **Scope:** разбивка длинной сделки ⑦ на этапы; признание выручки и прямых расходов по факту закрытия этапа (а не всей сделки целиком); план/факт и прогресс по этапам.
- **НЕ входит:** признание по проценту готовности от затрат (v2); шаблоны этапов по типам сделок.
- **Критерий завершения:** в сделке создаются этапы; закрытие этапа → выручка/расходы этапа признаются в ОПиУ за нужный период; виден прогресс.
- **Зависимости:** ⑦ Сделки (расширяет его).
- **Оценка:** 3–5 недель.
- **Приоритет:** Ф3a, сразу после ⑦.

#### Tier 4 — метод, безопасность, интеграция

##### Sub-project ㉙ — Метод начисления (тумблер ОПиУ) ⚡v4

- **Scope:** переключатель режима ОПиУ «кассовый / начисление», по умолчанию кассовый (для аудитории без бухгалтерии). Начисление — по дате документа (счёт/акт), кассовый — по дате оплаты. Тумблер на отчёте ОПиУ и в настройках организации. См. §4.13.
- **НЕ входит:** ручная настройка месяца начисления отдельной операции (как у Fintablo «перенести в нужный период») — v2; раздельные статьи ДДС vs ОПиУ на одной операции (вариант B каркаса).
- **Критерий завершения:** ОПиУ переключается кассовый↔начисление; цифры прибыли корректны для каждого метода; по умолчанию кассовый.
- **Зависимости:** ④ (движок ОПиУ — в коде).
- **Оценка:** 3–5 недель.
- **Приоритет:** Ф2-доработка / ранняя Ф3a — фундаментально для корректности ОПиУ, на нём строится вся аналитика.

##### Sub-project ㉚ — 2FA (двухфакторная аутентификация) ⚡v4

- **Scope:** TOTP-приложения (Google Authenticator и пр.), резервные коды, управление в настройках безопасности; усиление модуля `Auth`.
- **НЕ входит:** SMS-2FA (требует провайдера — бэклог); аппаратные ключи / WebAuthn (v2); SSO/SAML.
- **Критерий завершения:** пользователь включает 2FA → при входе запрашивается код; есть резервные коды.
- **Зависимости:** `Auth` (в коде). Независим.
- **Оценка:** 2–3 недели (мини).
- **Приоритет:** слот в любой момент — рекомендуется Ф1 (закалка) или перед ⑨c (банки = чувствительные данные).

##### Sub-project ㉛ — Интеграция МойСклад ⚡v4

- **Scope:** двусторонняя синхронизация с МойСклад: товары, закупки, себестоимость, продажи (финансовая сторона) — для тех, у кого склад уже ведётся в МойСклад.
- **НЕ входит:** замена собственного склада Bigfin (`Items`/`Inventory`); складские остатки по ячейкам.
- **Критерий завершения:** подключается аккаунт МойСклад → товары/продажи/себестоимость подтягиваются и отражаются в ДДС/ОПиУ по статьям.
- **Зависимости:** ④, каркас импорта ⑨a (как маркетплейсы ⑱).
- **Оценка:** 4–6 недель.
- **Приоритет:** Ф4, рядом с ⑱. **Низкий** — у Bigfin свой склад, это для миграции с МойСклада.

### Новое сквозное решение

#### §4.13 Метод начисления — тумблер ОПиУ ⚡v4

- На уровне отчёта ОПиУ и настроек организации — режим `pnl_method: 'cash' | 'accrual'`, по умолчанию `cash` (для аудитории без бухгалтерии).
- `accrual` переиспользует существующие проводки по дате документа (счёт/акт), `cash` — по дате оплаты. Новый расчётный движок не пишется — это представление над существующим леджером (паттерн `ProfitLossSheet` + Query-DTO).
- Снимает соответствующий пункт из anti-scope каркаса [2026-05-29-management-core-and-planning-design.md](2026-05-29-management-core-and-planning-design.md) §7.
- Ручной перенос месяца начисления отдельной операции (как у Fintablo) — НЕ входит, backlog.

#### Feature flags v4 ⚡v4

`FEATURE_DIVIDENDS`, `FEATURE_LOANS`, `FEATURE_FIXED_ASSETS`, `FEATURE_NOTIFICATIONS`, `FEATURE_TELEGRAM_BOT`, `FEATURE_PAYMENT_REQUESTS`, `FEATURE_FINANCIAL_RATIOS`, `FEATURE_VAT_ANALYSIS`, `FEATURE_ACCRUAL_PNL`, `FEATURE_2FA`, `FEATURE_MOYSKLAD`. По умолчанию off (§4.6). Откат модуля = выключить флаг.

## 1. Контекст и цели

### Что мы строим

Дорожную карту доработки кодовой базы Bigfin до уровня функциональности, эквивалентной Fintablo и PlanFact. Карта охватывает 22 последовательных под-проекта, каждый из которых получит собственную детальную спецификацию.

### Целевая аудитория продукта

Предприниматели без бухгалтерского образования. Профиль клиента — универсальный: услуги, товары, смешанные модели. Основатель тоже использует продукт в своём бизнесе (dogfooding).

### Целевая аудитория документа

Основатель Bigfin (исполнитель) + Claude (со-разработчик).

### Принципы

1. **Под-проекты последовательны** (подход «Фундамент → Этажи»). Solo + full-time не позволяет параллелизма.
2. **Каждый под-проект — отдельный полный цикл:** brainstorming → spec → plan → implementation → review → следующий. Без пропусков.
3. **Каждый PR обратим** (`git revert` без последствий). Без миграций БД, ломающих обратную совместимость.
4. **Двойная запись остаётся под капотом.** Бухгалтерские UI скрываются за переключателем «Бизнес-режим / Бухгалтерский режим».
5. **EN остаётся как fallback** для строк, ещё не переведённых на RU. Никогда не удаляем существующий функционал — только добавляем или скрываем.

### Что НЕ входит в дорожную карту

- Бизнес-план, маркетинг, монетизация
- Графический ребрендинг — отдельный под-проект, может быть вставлен между фазами
- Юридическая регистрация продукта в РФ, налоговая регистрация
- Хостинг и DevOps-инфраструктура
- Сертификация в качестве оператора персональных данных (152-ФЗ) — будет до запуска ⑨c
- Разработка собственной CRM Bigfin как продукта — это другой проект. v2 покрывает только **Bigfin-сторону интеграции** с собственной CRM (⑯c).

### Критерий успеха

После завершения всех 22 под-проектов в Bigfin доступен функционал, эквивалентный страницам fintablo.ru/features и planfact.io/product, на русском языке, в режиме «Бизнес», с российскими банковскими интеграциями, мобильным приложением, тремя CRM-коннекторами и поддержкой групп компаний. Полный бухгалтерский функционал остаётся доступным через режим «Бухгалтерский» для опытных пользователей.

## 2. Структура под-проектов

Каждый sub-project имеет 4 атрибута: **scope** (что входит), **anti-scope** (что не входит), **критерий завершения**, **зависимости**. Оценки даны в неделях полной занятости — реальное календарное время больше из-за обучения, переделок и пауз.

### Sub-project ① — Полная русификация и терминология

- **Scope:** русская локаль на frontend (~2400 ключей) и server (~30 JSON-файлов), русская терминология (ДДС, ОПиУ, Баланс, Сделки, Статьи учёта), RUB как валюта, дата-формат `DD.MM.YYYY`, числовой формат `1 234,56`, демо-данные на русском, переключатель `en/ru` в UI.
- **НЕ входит:** российские юр.формы (ИНН и пр.) — это ②. Графический ребрендинг — отдельно.
- **Готовность:** draft-спек `docs/superpowers/specs/2026-05-21-russian-localization-design.md`.
- **Критерий завершения:** при переключении на `?lang=ru` весь UI на русском. Скрипт `pnpm run lang:check` возвращает 0. Существующие e2e-тесты на `en` проходят.
- **Зависимости:** нет.
- **Оценка:** 8–12 недель.

### Sub-project ② — Российская юридическая специфика ⚡ разбит на ②a/②b/②c (2026-05-27)

При брейншторме 2026-05-27 выяснилось, что исходный scope ② слишком велик для одного цикла (4 юр.формы × 4 налоговых режима × 4 печатные формы). Разбит на три под-под-проекта с независимыми циклами brainstorming→spec→plan→executing.

#### Sub-project ②a — Реквизиты + ставки НДС

- **Scope:** nullable-колонки ИНН/КПП/ОГРН/ОГРНИП/банковские реквизиты в `organizations` и `contacts`. Юр.форма (ООО/ИП/Самозанятый/АО/Физлицо) и налоговый режим (УСН Доходы 6% / УСН Доходы−Расходы 15% / ОСНО / Патент / АУСН) как поля Organization. Российские ставки НДС (20%/10%/0%/Без НДС) в сидере `tax_rates`. Автоподстановка дефолтной ставки на Invoice/Bill по `tax_regime`. Валидация ИНН/ОГРН с контрольной суммой на webapp+server. Локализация ошибок валидации.
- **НЕ входит:** печатные формы (②c), план статей учёта (②b), Onboarding-wizard (③), OKPO (backlog), интеграция с DaData/ФНС API.
- **Готовность:** spec `docs/superpowers/specs/2026-05-27-russian-legal-attributes-design.md`.
- **Критерий завершения:** можно создать ООО/ИП с ИНН/КПП/ОГРН и банк-реквизитами; создать контрагента с реквизитами; выписать Invoice с автоподстановкой ставки НДС по режиму организации; ИНН/ОГРН валидируется по checksum; existing organizations/contacts без новых полей продолжают работать.
- **Зависимости:** ①.
- **Оценка:** 3–5 недель.

#### Sub-project ②b — План статей учёта (русский управленческий)

- **Scope:** адаптация дефолтного плана счетов под русские управленческие статьи (Выручка / Себестоимость / Аренда / ФОТ / Маркетинг / Налоги / Прочее). Сид-функция, заменяющая англоязычные дефолты при создании русскоязычной организации. Существующие организации не затрагиваются.
- **НЕ входит:** пресеты под тип бизнеса (услуги/товары/смешанное) — это часть ③ Onboarding.
- **Критерий завершения:** новая RU-организация создаётся с русским управленческим планом статей по умолчанию.
- **Зависимости:** ①. Независим от ②a.
- **Оценка:** 2–3 недели.

#### Sub-project ②c — Печатные формы РФ

- **Scope:** четыре печатные формы — Счёт на оплату (универсальный, для всех режимов), УПД (для ОСНО, объединяет С/Ф+Накладную), Акт выполненных работ (для услуг), ТОРГ-12 (накладная) + Счёт-фактура отдельно (альтернатива УПД). UI выбора формы при печати/PDF-экспорте. Подстановка реквизитов организации и контрагента из ②a.
- **НЕ входит:** ЭДО (Контур, Диадок) — отдельный under-project в будущем. Дизайн фирменного бланка с лого — после ②c.
- **Критерий завершения:** можно сгенерировать PDF любой из 4 форм с реквизитами организации и контрагента, корректной нумерацией и суммой НДС.
- **Зависимости:** ②a.
- **Оценка:** 5–8 недель.

### Sub-project ③ — Режимы «Бизнес» / «Бухгалтерский» + Onboarding

- **Scope:** на странице настроек переключатель `mode: business | accountant`. В режиме `business` скрыты: Manual Journals UI, Trial Balance, продвинутые опции Plan of Accounts. Onboarding-wizard при первом входе спрашивает: тип бизнеса (услуги/товары/смешанное), наличие НДС, наличие сотрудников. Результат → дефолтный набор статей учёта и видимость модулей.
- **НЕ входит:** автоматическое скрытие модулей на основе паттернов использования.
- **Критерий завершения:** новый пользователь после onboarding видит чистый UI без бухгалтерских страниц. Существующие пользователи остаются в `accountant` для обратной совместимости.
- **Зависимости:** ①, ②.
- **Оценка:** 2–4 недели.

### Sub-project ④ — Финансовые отчёты как ДДС / ОПиУ / Баланс

Scope ниже сохранён целиком; здесь ④ отвечает за слой статей и свёртку отчётов по статьям.

- **Scope:** интерфейс отчётов переработан в стиле Fintablo/PlanFact. Панель приборов — первая страница после логина в режиме `business`. Три ключевых отчёта (ДДС, ОПиУ, Баланс) получают упрощённый UI с фильтрами «по статье/проекту/подразделению». Логика расчётов — без изменений.
- **НЕ входит:** новые методы расчёта (косвенный метод ДДС, segment reporting).
- **Критерий завершения:** все 3 отчёта переименованы и упрощены, доступны через Панель приборов, экспорт в Excel/PDF работает.
- **Зависимости:** ①, ②, ③.
- **Оценка:** 4–6 недель.

### Sub-project ⑬a — PWA-режим (мобильная адаптация)

- **Scope:** адаптивная вёрстка для мобильных экранов на ключевых страницах (Панель, отчёты, формы). Service Worker для офлайн-кэширования. Manifest для install-as-app на iOS/Android.
- **НЕ входит:** push-уведомления (это ⑬b), доступ к камере, нативные функции.
- **Критерий завершения:** на iPhone и Android можно открыть Bigfin через браузер, добавить на главный экран, использовать ключевые экраны без горизонтальной прокрутки.
- **Зависимости:** ④.
- **Оценка:** 2–4 недели.

### Sub-project ⑤ — Бюджеты как БДДС и БДиР (с сценариями) ⚡v2

> **КОНСОЛИДИРОВАНО** → [2026-05-29-management-core-and-planning-design.md](2026-05-29-management-core-and-planning-design.md). Этап 2 объединённой спеки (`budgets`/`budget_lines`, 3 сценария). Scope ниже сохранён целиком, включая версионирование сценариев (§4.9).

- **Scope:** существующий модуль Budget → два представления: БДДС (бюджет ДДС) и БДиР (бюджет доходов и расходов). План-факт сравнение в реальном времени. Шаблоны бюджетов по типам бизнеса. **Новое в v2:** три сценария бюджета на тот же период — `optimistic | realistic | pessimistic`. Переключатель активного сценария, режим сравнения трёх сценариев рядом.
- **НЕ входит:** формулы между сценариями («пессимист = реалист × 0.8»), консолидация по группе компаний (это ⑰), более 3 сценариев.
- **Критерий завершения:** можно создать БДДС или БДиР на квартал/год, ввести план по статьям в трёх сценариях, видеть факт vs план активного сценария, сравнивать три сценария между собой.
- **Зависимости:** ④.
- **Оценка:** 5–9 недель (было 3–5 в v1).

### Sub-project ⑭ — Дебиторка/кредиторка (модуль «Долги») ⚡v2

- **Scope:** новая страница «Долги». Реестр непогашенных Invoices (дебиторка) и Bills (кредиторка). Старение долгов по корзинам 0–30 / 31–60 / 61–90 / 90+ дней. Шаблоны напоминаний клиенту по email. План погашения для крупных долгов (рассрочка). Дашборд: суммы дебиторки/кредиторки по статусам, ТОП-должники.
- **НЕ входит:** SMS/WhatsApp напоминания (отдельный мини-под-проект). Юридический документооборот по взысканию (претензии и пр.).
- **Критерий завершения:** видна страница «Долги», можно отправить напоминание дебитору, виден отчёт «старение долгов».
- **Зависимости:** ④.
- **Оценка:** 4–6 недель.

### Sub-project ⑥ — Платёжный календарь

> **КОНСОЛИДИРОВАНО** → [2026-05-29-management-core-and-planning-design.md](2026-05-29-management-core-and-planning-design.md). Этап 1 объединённой спеки. Реконсиляция зависимости от ⑭: календарю нужны только открытые обязательства по `due_date`, а не весь модуль «Долги» — поэтому в объединённой спеке ⑥ не блокируется полным ⑭.

- **Scope:** новая страница «Платёжный календарь». Список запланированных входящих/исходящих платежей по датам. Прогноз остатков на счетах по дням. Предупреждения о кассовых разрывах. Автоматическое создание планируемых платежей из счетов (Invoices/Bills) по `due_date`. Источники: непогашенные долги из ⑭, повторяющиеся платежи (аренда, зарплата), ручные планы.
- **НЕ входит:** автоматическая отправка платежей в банк (это часть ⑨). Только планирование и визуализация.
- **Критерий завершения:** видна таблица платежей на месяц вперёд, можно добавить ручной планируемый платёж, видны прогноз остатка и предупреждение «через 5 дней кассовый разрыв».
- **Зависимости:** ④, ⑭.
- **Оценка:** 4–8 недель.

### Sub-project ⑦ — Сделки (с автораспределением) ⚡v2

- **Scope:** новая сущность «Сделка» — группировка операций (Invoices, Bills, Expenses) по проекту/клиенту/направлению. Расчёт прибыльности сделки: (доходы) − (прямые расходы). Дашборд сделок: воронка, рентабельность, дебиторка. **Новое в v2:** правила автораспределения общих расходов (`CostAllocationRule`). Расходы по статье «Аренда» / «Маркетинг» / «Адм. персонал» разносятся по сделкам по ключу `revenue | payroll | headcount | manual_share`.
- **НЕ входит:** CRM-функционал (контакты, лиды, задачи) — это ⑯. Сделки — только финансовая сторона. Кастомные формулы автораспределения. Подключение к Сделкам поля «ответственный менеджер» — это в ⑧.
- **Критерий завершения:** можно создать сделку, привязать к ней счёт и расходы, увидеть рентабельность. Создать правило автораспределения «Аренда раскидывается по сделкам пропорционально выручке», увидеть в отчёте «прибыльность сделки» строки «после распределения».
- **Зависимости:** ④, ⑥.
- **Оценка:** 9–15 недель (было 6–10 в v1).

### Sub-project ⑬b — Capacitor-обёртка (нативное мобильное приложение)

- **Scope:** упаковка веб-приложения в нативный wrapper через Capacitor. Push-уведомления для платёжного календаря (FCM). Доступ к камере (сканировать чеки). Публикация в App Store и Google Play.
- **НЕ входит:** полностью нативный UI (это ⑬c). Офлайн-режим — базовый, через Service Worker из ⑬a.
- **Критерий завершения:** установленное на iPhone и Android приложение Bigfin, работают push-уведомления о платежах, можно сделать фото чека.
- **Зависимости:** ⑬a, ⑥, ⑦.
- **Оценка:** 6–10 недель.

### Sub-project ⑧ — Зарплаты и налоги на ФОТ (с KPI) ⚡v2

- **Scope:** учёт сотрудников (ФИО, должность, ставка), начисление зарплаты (оклад, премии, удержания), расчёт страховых взносов (СВ — 30%) и НДФЛ (13%/15%/30%). Платёжная ведомость, расходный кассовый ордер. Отчёт «Налоги к уплате». **Новое в v2:** KPI/бонусы по сотрудникам — план продаж на менеджера, расчёт переменной части ФОТ от показателя (выручка/маржа/чек), воронка плана vs факт. Привязка сделок к ответственному менеджеру.
- **НЕ входит:** автоматическая отправка отчётов в ФНС/СФР (СЗВ-ТД, РСВ, 6-НДФЛ). Кадровый учёт по ТК РФ. Только финансовый аспект ФОТ.
- **Критерий завершения:** можно завести сотрудника, начислить зарплату за месяц, увидеть отдельные суммы к выплате, НДФЛ к перечислению, СВ к уплате. Назначить менеджеру план по выручке, увидеть факт и расчёт бонуса.
- **Зависимости:** ④, ⑤, ⑦.
- **Оценка:** 10–16 недель (было 8–12 в v1) — самый сложный, требует глубокого знания РФ-законодательства.

### Sub-project ⑮ — Финмодель и юнит-экономика ⚡v2

- **Scope:** новая страница «Финмодель». Дашборд метрик юнит-экономики: маржинальность по продукту/проекту/менеджеру, LTV, CAC (вводится вручную или из ⑯), ROMI, точка безубыточности. Графики «маржа во времени», «доход на сотрудника», «рентабельность по сегментам».
- **НЕ входит:** машинное обучение и предсказательная аналитика. Кастомные метрики, определяемые пользователем (только preset метрики на старте).
- **Критерий завершения:** на странице «Финмодель» виден дашборд с 6 ключевыми метриками, можно отфильтровать по периоду/продукту/менеджеру.
- **Зависимости:** ④, ⑦.
- **Оценка:** 5–8 недель.

### Sub-project ⑨a — Универсальный импорт выписок

- **Scope:** загрузка выписки в форматах CSV / Excel / PDF / 1C-bank exchange (xml-формат для обмена с банками, не путать с ⑩ — это самостоятельный стандарт банковской выгрузки). Парсеры для топ-вариантов экспорта банков (Тинькофф/Сбер/Альфа и др.). Автоматическое сопоставление импортируемых платежей с существующими Invoices/Bills через эвристики (сумма, дата, контрагент).
- **НЕ входит:** API-интеграция с банками (это ⑨c-⑫). Двусторонняя синхронизация.
- **Критерий завершения:** загруженная из любого банка выписка распарсилась, операции попали в очередь сопоставления, можно подтвердить одним кликом.
- **Зависимости:** ④.
- **Оценка:** 2–4 недели.

### Sub-project ⑨b — Интеграция с Дзенмани

- **Scope:** API-импорт операций из Дзенмани (если основатель/клиенты используют его для личных финансов). Webhook-приём новых операций.
- **НЕ входит:** двустороннее синхронизирование (Bigfin → Дзенмани).
- **Критерий завершения:** можно подключить аккаунт Дзенмани, увидеть импортируемые операции в очереди сопоставления.
- **Зависимости:** ⑨a.
- **Оценка:** 2–4 недели.

### Sub-project ⑨c — Банковские API: волна 1 (Тинькофф + Альфа)

- **Scope:** API-интеграция с Тинькофф Бизнес и Альфа-Банк. Автоматический импорт выписки, сопоставление, статусы платежей. Партнёрские договоры — заключаются параллельно с разработкой, **переговоры начинаются в Ф3**.
- **НЕ входит:** инициация платежей **из** Bigfin **в** банк (это требует ЭКО-сертификации, отдельный под-проект в будущем).
- **Критерий завершения:** можно подключить аккаунт Тинькофф и Альфа, выписка автоматически импортируется ежедневно.
- **Зависимости:** ⑨a.
- **Оценка:** 4–8 недель (включая Альфа после Тинькофф — переиспользование кода).

### Sub-project ⑩ — Интеграция с 1С

- **Scope:** файловый обмен с 1С через формат CommerceML (XML). Импорт контрагентов, товаров, документов из 1С в Bigfin. Экспорт операций из Bigfin в 1С.
- **НЕ входит:** REST API через 1C:Web Services (отдельный под-проект). Внешняя обработка-плагин для 1С (отдельный под-проект).
- **Критерий завершения:** можно выгрузить из 1С файл CommerceML, загрузить в Bigfin, увидеть синхронизированные данные.
- **Зависимости:** ④, ⑤.
- **Оценка:** 6–10 недель.

### Sub-project ⑯a — CRM-интеграция: Битрикс24 (волна 1) ⚡v2

- **Scope:** REST API + webhooks Битрикс24. **Перед написанием коннектора** — выделение абстракции `CrmConnector` в коде (см. §4.11). Маппинг «CRM-сделка ↔ Bigfin-сделка», «CRM-контакт ↔ Bigfin-контрагент». Импорт CAC из источников Битрикс24. Однонаправленная синхронизация Битрикс → Bigfin.
- **НЕ входит:** двунаправленная синхронизация (отправка статусов из Bigfin в Битрикс) — отдельная задача после первой обратной связи. CRM-функционал внутри Bigfin (задачи, воронка лидов).
- **Критерий завершения:** можно подключить аккаунт Битрикс24, увидеть импортируемые сделки в Bigfin, прогрузить CAC в ⑮.
- **Зависимости:** ⑦, ⑨a.
- **Оценка:** 5–8 недель.

### Sub-project ⑯b — CRM-интеграция: amoCRM (волна 2) ⚡v2

- **Scope:** второй коннектор поверх абстракции `CrmConnector` (готовой из ⑯a). API amoCRM, webhook-приёмник, маппинг сущностей.
- **НЕ входит:** то же, что в ⑯a.
- **Критерий завершения:** можно подключить аккаунт amoCRM, импортировать сделки.
- **Зависимости:** ⑯a.
- **Оценка:** 3–5 недель (меньше за счёт переиспользования абстракции).

### Sub-project ⑯c — CRM-интеграция: Собственная CRM Bigfin (волна 3) ⚡v2

- **Scope:** третий коннектор на ту же абстракцию. Универсальный webhook-приёмник + публичные REST-эндпоинты на стороне Bigfin для собственной CRM. Документация API для собственной CRM-команды.
- **НЕ входит:** разработка самой собственной CRM (это другой проект). Двунаправленная синхронизация (если потребуется — отдельный мини-под-проект).
- **Критерий завершения:** собственная CRM может отправить webhook о новой сделке, Bigfin её принимает и создаёт сделку через тот же контракт, что Битрикс24/amoCRM.
- **Зависимости:** ⑯a.
- **Оценка:** 2–4 недели (Bigfin-сторона; сроки собственной CRM не входят в эту оценку).

### Sub-project ⑪ — Банковские API: волна 2 (Сбер + Точка + Райффайзен)

- **Scope:** API-интеграция со Сбер Бизнес, Точка, Райффайзен. Сбер и ВТБ требуют партнёр-статуса — переговоры с Сбером начинаются в начале Ф4.

- **Критерий завершения:** работающая API-интеграция со всеми тремя банками.
- **Зависимости:** ⑨c.
- **Оценка:** 6–10 недель на банк = 18–30 недель на весь под-проект (три банка последовательно, переиспользование кода между ними).

### Sub-project ⑫ — Банковские API: волна 3 (ВТБ + ПСБ + другие)

- **Scope:** API-интеграция с ВТБ, ПСБ. Дополнительные банки (Открытие, Промсвязьбанк и т.д.) — по запросу пользователей.
- **НЕ входит:** банки, у которых нет publicly documented API (на момент написания спека).
- **Критерий завершения:** ВТБ и ПСБ работают через API.
- **Зависимости:** ⑪.

### Sub-project ⑰ — Мультиюрлицо и консолидация ⚡v2

- **Scope:** новый уровень `Workspace` над `Organization`. Один пользователь может иметь несколько Workspace, в каждом — несколько Organizations. Существующие пользователи получают **один Workspace по умолчанию** с одним Organization (additive миграция). Сводные отчёты ДДС/ОПиУ/Баланс на уровне Workspace. Внутригрупповые операции (продал из ЮЛ-1 в ЮЛ-2) помечаются флагом `intercompany` и исключаются из сводного отчёта. Роли пермиссий расширяются: «доступ ко всем Organization» / «к выбранным».
- **НЕ входит:** автоматическое определение интеркомпани (только ручной флаг). Сложная иерархия (Workspace в Workspace). Бухгалтерская консолидация по МСФО — управленческая консолидация только.
- **Критерий завершения:** можно создать второй Organization в Workspace, увидеть сводный отчёт ДДС, увидеть, что интеркомпани-операции корректно исключены.
- **Зависимости:** ④, ③.
- **Оценка:** 10–14 недель.

### Backlog: Sub-project ⑬c — Полный нативный мобильный (опционально)

- **Scope:** разработка React Native (или Flutter) приложения с независимым нативным UI. Полный офлайн-режим. Быстрый старт.
- **Когда:** только после запуска и обратной связи от первых пользователей. Принимается отдельным решением.
- **Оценка:** 16–24 недели.

### Жёсткие зависимости (нельзя нарушать)

- ②, ③, ④ требуют ① — без русской терминологии новый функционал именовать некак.
- ⑤–⑧, ⑭, ⑮ требуют ④ — новые модули используют статьи учёта и базовые отчёты.
- ⑥ требует ⑭ — Платёжный календарь подтягивает дебиторку.
- ⑦ требует ⑥ — Сделки используют платёжный календарь для прогнозов.
- ⑧ требует ⑦ — KPI на менеджера привязывает сделки к ответственному.
- ⑮ требует ⑦ — юнит-экономика считается по сделкам.
- ⑬a требует ④ — без отчётов мобильному нечего показывать.
- ⑬b требует ⑬a — нативная обёртка строится поверх PWA.
- ⑯a требует ⑦ + ⑨a — первая CRM-волна сопоставляет CRM-сделки с Bigfin-сделками.
- ⑯b, ⑯c требуют ⑯a — переиспользуют абстракцию `CrmConnector`.
- Банковские волны последовательны (⑨c → ⑪ → ⑫) — переиспользуют код.
- ⑰ требует ③ — пермиссии и режимы должны быть стабильны.

### Точки естественной паузы

После любой из точек ниже можно сделать паузу на недели/месяцы без вреда для проекта:

- После ②: продукт «российский» (юр.формы есть)
- После ③: продукт «дружелюбный к непрофи» (onboarding и режимы)
- После ⑤: «MVP Fintablo-light» (отчёты + бюджеты со сценариями + мобильный)
- После ⑭: закрыт раздел «Долги» — быстрая ценность для dogfooding
- После ⑦: основной Fintablo+PlanFact-функционал (сделки с автораспределением)
- После ⑧: закрыт раздел «Операции» Fintablo + KPI PlanFact
- После ⑮: полноценный аналитический пак уровня PlanFact для одного юрлица
- После ⑨a: универсальный импорт выписок работает для всех банков
- После ⑨c: первый партнёрский банк = маркетинговый аргумент

### Возможные параллельные действия

## 4. Сквозные архитектурные решения

Эти правила действуют во всех 22 под-проектах. Формулировка сейчас экономит часы споров с собой в будущем.

### 4.1 Существующий фундамент сохраняется

- Двойная запись под капотом работает как сейчас. Новые модули пишут проводки через существующие сервисы.
- Не переписываем существующие модули, если они работают. Только дополняем, переименовываем UI, скрываем.
- Не делаем миграций, ломающих обратную совместимость. Только additive (новые колонки `nullable: true`, новые таблицы).

### 4.2 UI-модель: режим «Бизнес» / «Бухгалтерский»

- Глобальный флаг на уровне организации: `mode: 'business' | 'accountant'`. Default = `accountant` для совместимости.
- В `business` скрываются: Manual Journals UI, Trial Balance, продвинутые разделы Plan of Accounts.
- Переключатель в Settings, доступен в любое время. Не требует миграции данных — только UI-фильтр.
- Onboarding для новых организаций устанавливает `business` по умолчанию.

### 4.3 Локализация

- Стек: `react-intl-universal` (web) + `nestjs-i18n` (server).
- `SUPPORTED_LOCALES`: `['en', 'ru']`. AR/ES/SV — мёртвый код, не активируем.
- Новые ключи добавляются **парно** — EN + RU. CI-проверка `pnpm run lang:check` падает, если есть missing keys.
- EN остаётся как fallback на уровне библиотеки.

### 4.4 Валюта

- RUB добавляется в существующий список валют как первый элемент.
- В onboarding для RU-локали — preset = RUB.
- Multi-currency функционал сохраняется (USD, EUR работают).

### 4.5 Тестирование

- **Unit-тесты** — на бизнес-логику новых модулей (Сделки, Календарь, ЗП, Долги, Финмодель). Существующие — не трогаем.
- **e2e (Playwright)** — каждый PR должен проходить e2e на `en`. Регрессии = блокер.
- **Ручная проверка на `ru`** — чек-лист в PR-описании.
- **Dogfooding** — основатель сам пользуется продуктом в своём бизнесе, реальная обратная связь.

### 4.6 Feature flags

- Новые модули (⑥, ⑦, ⑧, ⑭, ⑮, ⑯a/b/c, ⑰) выпускаются под флагами `FEATURE_PAYMENT_CALENDAR`, `FEATURE_DEALS`, `FEATURE_PAYROLL`, `FEATURE_AR_AP`, `FEATURE_FINMODEL`, `FEATURE_CRM_BITRIX`, `FEATURE_CRM_AMO`, `FEATURE_CRM_OWN`, `FEATURE_MULTI_ENTITY`.
- По умолчанию выключены. Включаются для тестовых организаций, затем постепенно для всех.
- Откат модуля = выключить флаг, без `git revert`.

### 4.7 Минимум новых зависимостей

- Новые npm-пакеты — только при наличии обоснования в PR.
- Текущий React-стек не меняем.

### 4.8 Авторские права

- Все новые файлы — копирайт «© 2026 Bigfin».
- Лицензия проприетарная.

### 4.9 Сценарии бюджета — версионирование ⚡v2

- В таблице `BudgetLine` появляется колонка `scenario` со значениями `optimistic | realistic | pessimistic`. По умолчанию все существующие строки — `realistic` (additive миграция).
- На уровне `Budget` — флаг `active_scenario`. UI показывает активный сценарий; в сравнительном режиме — все три рядом.
- Логика «факт vs план» сравнивает факт с активным сценарием. Сравнение факта со всеми тремя — отдельный режим.
- Формулы между сценариями (например, «пессимист = реалист × 0.8») — НЕ входят, в backlog.
- Более трёх сценариев — НЕ входят, в backlog.

### 4.10 Правила автораспределения общих расходов ⚡v2

- Новая сущность `CostAllocationRule`: что распределяем (статья учёта), куда (список проектов/сделок/направлений), по какому ключу (`revenue | payroll | headcount | manual_share`).
- Применение — **на стороне отчёта**, не модификация исходных проводок. Это значит, что отключение правила возвращает «как было», без миграции данных.
- Правила версионируются по дате применения (`valid_from` / `valid_to`). При изменении правила старая версия сохраняется и продолжает действовать на прошлые периоды; новая версия — только на периоды от даты применения. Прошлые отчёты не пересчитываются автоматически.
- В отчётах строки «после распределения» помечаются отдельной колонкой/индикатором.
- Кастомные формулы — НЕ входят, backlog.
- Ключ `headcount` принят основателем как реалистичный сценарий («раскинуть аренду по отделам по количеству людей»); зафиксировано в брейншторме 2026-05-27.

### 4.11 Абстракция «CRM-коннектор» ⚡v2

- Перед написанием ⑯a (Битрикс24) сначала выделяется интерфейс `CrmConnector` с базовыми операциями: `fetchDeals`, `fetchContacts`, `mapDealToBigfin`, `handleWebhook`. Любая будущая CRM подключается реализацией этого интерфейса.
- Webhook-приёмник один на все CRM, маршрутизация по типу источника (header `X-Crm-Source` или эндпоинт `/webhooks/crm/<source>`).
- Состояние синхронизации (`last_sync_at`, токены, конфигурация) — в отдельной таблице `CrmAccount`, не в `Organization`.
- Двунаправленная синхронизация и отправка статусов из Bigfin в CRM — НЕ входят в ⑯a, добавляются позже точечно по CRM.
- Решение об абстракции до первой реализации — сознательное архитектурное упреждение, чтобы избежать копипасты в ⑯b и ⑯c.

### 4.12 Модель «Workspace → Organizations» ⚡v2

- Над существующим уровнем `Organization` появляется уровень `Workspace` (= группа компаний/аккаунт владельца). Один пользователь может иметь несколько `Workspace`, в каждом — несколько `Organizations`.
- Существующие пользователи получают **один `Workspace` по умолчанию** с одним `Organization` (additive миграция). Текущий UI пользователя — без изменений до явного включения мультиюрлица.
- Сводные отчёты — на уровне `Workspace`, обычные — на уровне `Organization`.
- Внутригрупповые операции (продал из ЮЛ-1 в ЮЛ-2) помечаются специальным флагом `intercompany` (ручной флаг, не автодетект) и исключаются из сводного ДДС/ОПиУ.
- Роли пермиссий расширяются: «доступ ко всем `Organization` в `Workspace`» / «только к выбранным `Organization`».
- Сложная иерархия (Workspace в Workspace) — НЕ входит.

### Что мы НЕ боимся

- Конкуренция с Fintablo/PlanFact — у Bigfin своя бизнес-модель и позиционирование, рынок выдерживает оба продукта.
- Производительность — на первых 100–1000 пользователях текущая архитектура (PostgreSQL + Node) достаточна.
- Усложнение UI от 7 новых направлений — нивелируется режимом «Бизнес» (§4.2) и feature flags (§4.6).

## 6. Операционная модель и первый шаг

### 6.1 Цикл для каждого под-проекта

```
1. brainstorming  — обсуждаем детали, получаем подтверждение
2. writing-plans  — детальный план разбит на PR/задачи
3. executing      — исполняем по плану, каждый PR atomic
4. review         — e2e + dogfooding + баги
5. retro          — что узнали, что поменять в дорожной карте
6. next           — следующий под-проект
```

Между под-проектами можно (и нужно) делать паузы.

### 6.2 Точки повторной ревизии дорожной карты

Обязательная ревизия дорожной карты после завершения каждой фазы (Ф1, Ф2, Ф3, Ф4, Ф5):

- Что узнали из dogfooding?
- Что больше не актуально?
- Какие новые риски появились?
- Нужно ли добавить под-проект, который раньше не виделся?
- Изменился ли план у Fintablo/PlanFact?

Финальная дорожная карта будет отличаться от той, что сегодня. Это нормально.

### 6.3 Технические артефакты

- Этот документ: `docs/superpowers/specs/2026-05-27-fintablo-planfact-parity-roadmap.md`.
- Предыдущая версия v1: `docs/superpowers/specs/2026-05-22-fintablo-parity-roadmap.md` (только Fintablo).
- Каждый под-проект получает собственный спек в той же папке: `2026-XX-XX-<topic>-design.md`.
- После спека — собственный план: `docs/superpowers/plans/2026-XX-XX-<topic>-plan.md`.

### 6.4 Первый шаг

После одобрения этой дорожной карты:

1. Запускаем `superpowers:writing-plans` для существующего draft-спека русификации (`2026-05-21-russian-localization-design.md`).
2. Превращаем 16 шагов спека в детальный план PR-за-PR с конкретными файлами, командами проверки и инструкциями отката.
3. После одобрения плана — `superpowers:executing-plans` либо ручная работа PR-за-PR.

### 6.5 Что НЕ делаем сейчас (явный gate)

- НЕ начинаем кодить sub-project ① прямо сегодня. Сначала writing-plans.
- НЕ пишем детальные спеки для sub-projects ②–⑫, ⑬a–c, ⑭–⑰. Только когда дойдём.
- НЕ ставим календарные даты. Только оценки трудоёмкости.

## 8. Открытые вопросы

Эти вопросы зафиксированы здесь, чтобы не потерялись:

1. **Графический ребрендинг Bigfin** — когда вставить? Кандидат: в Ф1 как ⓞ Sub-project между ① и ②, или после Ф1 целиком. Решение — после первых dogfooding-сессий.
2. **ЭДО (Контур, Диадок)** — не входит в дорожную карту. Решение о включении — после запуска и первых клиентов с потребностью.
3. **Многопользовательский доступ (роли, права)** — есть базовые роли в текущей кодовой базе. Расширение под российские реалии (бухгалтер + директор) — отдельный мини-sub-project, может быть вклинен в Ф3.
4. **Открытый API** — текущая кодовая база уже имеет REST API. Документация на русском и Swagger UI — мини-задача, не отдельный под-проект.
5. **Формулы между сценариями бюджета** (пессимист = реалист × коэффициент). НЕ входят в ⑤. Возвращаемся к вопросу после первого dogfooding на сценариях. ⚡v2
6. **Кастомные ключи автораспределения** (формулы, метаданные сущностей, `floor_area`). НЕ входят в ⑦. Возвращаемся после первого dogfooding. ⚡v2
7. **Двусторонняя CRM-синхронизация** (отправка статусов из Bigfin в Битрикс/amo). НЕ входит в ⑯a/b. Решение — после первой обратной связи с пользователями. ⚡v2
8. **Аудит ролей перед ⑰** — отдельный мини-под-проект между Ф4 и ⑰ (между ⑯c и ⑪? или сразу перед ⑰?). Решение — ближе к концу Ф5. ⚡v2
9. **Темп публикации собственной CRM Bigfin** — если она появится раньше Ф4, может быть нужен интеграционный API в Bigfin **до** ⑯c. Тогда — мини-под-проект «CRM-приёмник» вставляется по необходимости. ⚡v2
10. **SMS/WhatsApp-напоминания дебиторам** — НЕ входят в ⑭. Отдельный мини-под-проект, требует подключения провайдеров (Twilio, smsc.ru). ⚡v2
