## Что сделано в шаге 6.1

Две миграции тенантной схемы:

1. **`legal_entities`** — справочник юрлиц по §6.1: название, форма, ИНН, КПП,
   ОГРН, система налогообложения, НДС, валюта, директор, адреса, банковские
   реквизиты, доля владельца, признак головного, активность.
2. **`legal_entity_id`** — колонка nullable в 13 таблицах из §6.2, с индексами.

Плюс модель `LegalEntity` (тенантная схема) и её регистрация в общем списке
моделей.

### Главная находка: имена таблиц в ТЗ не совпадают со схемой

ТЗ перечисляет таблицы «по смыслу». В базе **пять из тринадцати** называются
иначе:

| В ТЗ | На самом деле |
|---|---|
| `sale_invoices` | `sales_invoices` |
| `sale_estimates` | `sales_estimates` |
| `sale_receipts` | `sales_receipts` |
| `expenses` | `expenses_transactions` |
| `dividends` | `dividend_payouts` |
| `payment_calendar_entries` | `planned_operations` |

Опечатка тут **не падает**. Миграция защищена проверкой «есть ли такая
таблица» — и просто пропустит несуществующую. Разрез по юрлицу в этой таблице
не появится никогда, и ни одной ошибки при этом не будет. Заметили бы через
месяц, когда отчёт по юрлицу оказался бы неполным.

Поэтому список сверяется со **настоящими именами из моделей** отдельной
проверкой (`legalEntityColumns.spec.ts`). Подстановка имени из ТЗ роняет её.

### Урок про сторожа

Первая версия проверки искала модели только в файлах `*.model.ts` и дала
**ложную тревогу** на пяти настоящих таблицах: часть моделей проекта лежит в
файлах вида `Bill.ts`. Соблазн в такой ситуации — «подогнать список под
сторожа», то есть выкинуть из миграции настоящие таблицы: тест стал бы
зелёным, а продукт сломался. Расширил сторожа. После этого он нашёл одну
**настоящую** ошибку — `sale_invoices` вместо `sales_invoices`.

### Что ещё заложено

- **Обе миграции откатываются**, откат не пустой — за этим следит прежний
  сторож `migrationsReversible.spec.ts`.
- **Повторный запуск безопасен**: перед добавлением проверяется, нет ли уже
  колонки. DDL в MySQL необратим, и прогон, упавший на середине списка,
  оставляет часть колонок созданными.
- **У проводок составной индекс** `(legal_entity_id, date)`: отчёты всегда
  спрашивают «юрлицо за период». У остальных таблиц разрез идёт без даты —
  там одиночный индекс.
- **`is_primary` без уникального индекса**: пока юрлицо одно, оно и головное,
  а при переключении головного жёсткий индекс потребовал бы промежуточного
  состояния.

### Чего в шаге нет

**Миграции не запускались ни на одной базе.** Локальная база проекта не
настроена, а гонять схемную миграцию на общем стенде без ведома владельца
нельзя. ТЗ прямо требует бэкап и прогон на тестовом стенде — это решение
владельца, а не моё.

**Прогон:** сервер 2388 тестов / 355 файлов, типы чисты. Витрину этот шаг не
менял.

**Как откатить:** `git revert` коммита шага 6.1; в базе — `pnpm
tenants:migrate:rollback` дважды (миграции две).
