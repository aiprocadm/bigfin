## 1. Приёмка фазы v8 на свежей организации

Фаза проверялась не по коду, а живьём: заведена **новая организация** (как у
настоящего новичка — регистрация, подтверждение почты, создание организации),
в неё приглашён человек с ролью «Сотрудник», и за него прожит обычный рабочий
день.

**Часть первая — работа должна идти.**

| Действие сотрудника | Итог |
|---|---|
| открыть список покупателей | ✅ 200 |
| завести покупателя | ✅ 201 |
| получить подсказку контрагентов | ✅ 200 |
| завести позицию (услугу) | ✅ 201 |
| выписать счёт покупателю на 20 000 ₽ | ✅ 201 |
| принять оплату по счёту | ✅ 201 |
| увидеть свои счета | ✅ 200 |

**Часть вторая — чего роль не давала, должно быть закрыто.** Шестнадцать
действий: банковские операции, правила разбора выписки, склады и их включение,
валюты, статьи учёта, категории товаров, реквизиты организации, шаблоны печати,
импорт, бюджеты, плановые операции, роли, закрытие периода, подписка на
продукт, эквайринг.

**Все шестнадцать отклонены.** Отдельно проверено, что отказ идёт **по праву**,
а не потому, что модуль выключен: владелец включил бюджеты и платёжный
календарь, после чего сотрудник получил «нет права», а не «модуль выключен».
Владелец на тех же ручках доходит до дела.

**Вывод: фаза v8 подтверждена на чистых данных. Новых дефектов приёмка не
нашла.**

## 2. Что дала разведка этой итерации

Шаг П1 закрыл **запись**: из 305 записывающих ручек каждая либо спрашивает
право, либо объявлена открытой с причиной, либо имеет собственную проверку.

Следующий естественный вопрос — **чтение**. Роль «Сотрудник» задумана как
повседневная работа с документами, а не как доступ ко всей финансовой картине
организации. Проверка живьём за приглашённого сотрудника:

| Журнал операций | 🔒 закрыт |
| Дебиторка и кредиторка по срокам | 🔒 закрыты |
| **Оборотно-сальдовая ведомость** | 👀 **видит** |
| **Остатки по покупателям и поставщикам** | 👀 **видит** |
| **Обороты по покупателям и поставщикам** | 👀 **видит** |
| **Продажи по позициям** | 👀 **видит** |

**Семь отчётов из шестнадцати открыты.** Разметка отчётов сделана меньше чем
наполовину: из восемнадцати отчётных контроллеров право спрашивают семь.

Показательнее всего пара «Баланс закрыт — оборотно-сальдовая ведомость

задней.

## 4. Предлагаемая фаза: «Кто что видит»

Смысл фазы — чтобы **приглашённый человек видел ровно то, что ему показали**.
Прямое продолжение: v6 — верить цифрам, v7 — верить факту сохранения, v8 —
верить границам записи, v9 — верить границам показа.

**Рекомендованный порядок:**

1. **В1 — отчёты.** ✅ **Закрыто (#230).** Размечены все одиннадцать отчётов,
   у которых пометки не было: оборотно-сальдовая ведомость, остатки и обороты
   по покупателям и поставщикам, операции по документу, продажи и закупки по
   позициям, оценка склада, движение позиций склада, налог с продаж.

   Два права спрашивались кодом, но **в схеме ролей их не было** — поставить
   галочку было негде, поэтому отчёты и стояли открытыми: «оборотно-сальдовая
   ведомость» и «налог с продаж». Оба добавлены в схему вместе с переводами.

   **Решение по вопросу 11.** Роли «Сотрудник» оставлены отчёты **по
   контрагентам** — остатки и обороты по покупателям и поставщикам: с кем
   сколько наработали и кто сколько должен, это продолжение работы со счетами
   и оплатами. Общая финансовая картина организации остаётся администратору.
   Перенос `20260812160000_staff_can_read_contact_reports` (прогон на живой
   базе up→down→up).

   | Проба на свежей организации | До правки | После правки |
   |---|---|---|
   | сотруднику видно отчётов | **7 из 16**, включая ОСВ, продажи по позициям и оценку склада | **4 из 16** — только по контрагентам |
   | оборотно-сальдовая ведомость у сотрудника | 👀 видел | **403** |
   | владельцу видно | всё | **всё, без изменений** |

   Сторож `Roles/reportsAccessGates.spec.ts` следит за тремя вещами сразу:
   у каждого отчёта стоит пометка и страж; каждое требуемое право объявлено
   в схеме ролей (иначе владелец не сможет его выдать); **ни один отчётный
   контроллер не остался без пометки** — обход всей папки, а не список.
2. **В2 — действие без проверки существования.** ✅ **Закрыто (#231).**
   Пройден весь класс: девять цепочек «ручка → служба → очередь» разобраны
   по отдельности, каждый вывод перепроверен встречным чтением кода.

   **Сломаны были пять** — письма по счёту, чеку, смете и оплате плюс
   напоминание о долге: команда сразу ставила задачу в очередь, а документ
   загружался только внутри неё, где ошибку клиент уже не видит. Лечение
   одно на всех: загрузка документа с «не найдено» **до** постановки в
   очередь. Напоминание о долге шлётся через ту же команду, что письмо по
   счёту, поэтому починка одной точки закрыла две ручки.

   **Целые две**: переотправка приглашения проверяет пользователя первой
   операцией, а восстановление пароля отвечает «успех» для любой почты
   **намеренно** — иначе перебором адресов можно выяснять, кто
   зарегистрирован. Это не дефект, и чинить его на 404 нельзя.

   **Попутная находка серьёзнее самой темы: переотправка приглашения не
   слала письмо вовсе.** Ветка переотправки заводила новый токен, но не
   эмитила событие, которое слушает почтовый подписчик, — владелец жал
   «переотправить», получал успех, письмо не уходило. Починено: событие
   эмитится после вставки токена; вживую очередь писем выросла на одну
   джобу после переотправки (до правки — не росла).

   | Проба на стенде | До правки | После правки |
   |---|---|---|
   | письма по счёту/чеку/смете/оплате-«призраку» | **200 «отправлено»** | **404** |
   | напоминание о долге по счёту-«призраку» | **201 {queued: true}** | **404** |
   | письмо и напоминание по настоящему счёту | 200 / 201 | **без изменений** |
   | переотправка приглашения | успех, письмо не в очереди | успех, **письмо в очереди (+1)** |

   Известное ограничение (унаследованное, не новая регрессия): если у
   переотправляющего нет тенантной записи (рассинхронизированная база),
   письмо соберётся без отправителя и джоба упадёт — ровно так же ведёт
   себя первичное приглашение.

   **Находка владельцу: SMS по смете — ручка-пустышка.** `POST
   /sale-estimates/:id/notify-sms` отвечает 201, но вся служба SMS
   закомментирована целиком — ручка не делает ничего. Решение продуктовое
   (вернуть SMS или убрать ручку), поэтому код не тронут.
3. **В3 — отбор в подсказке.** Небольшая, но честная доводка П1.
4. **В4 и В6** — только после ответов владельца.

**Что НЕ делать сейчас**: тяжёлые банковские интеграции, нативный клиент,
консолидацию мультиюрлица (без изменений с v7 и v8).
