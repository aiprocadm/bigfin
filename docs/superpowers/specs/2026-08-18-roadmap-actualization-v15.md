## 2. Что дала разведка этой итерации

Разведка велась от вопроса: **«что уже построено, но недоступно
пользователю?»** — плюс контрольный заход «что сломается при росте данных».
Четыре линии, всё подтверждено на коде (файлы:строки).

**Линия 1 — телефон (САМАЯ ДЕШЁВАЯ КРУПНАЯ ПОБЕДА).** Приоритет основателя
«мобильность» ни разу не исследовался. Оказалось: **80% фундамента уже
мобильные** — корректный viewport, PWA-манифест с установкой на домашний
экран (`manifest.json`, `sw.js` — рабочий, с тестами), бургер-меню с
выезжающей панелью (`DashboardShell.tsx`), формы V2 mobile-first
(`InvoiceFormHeaderV2.tsx` — `sm:grid-cols-2`), все 42 карточки-шторки
резиновые. **Но приложение физически не открывается на телефоне из-за трёх
строк легаси-CSS:** `App.scss:52` `min-width: 1100px`, `App.scss:48`
`body { overflow: hidden }` (65% интерфейса недостижимо даже скроллом),
`Dashboard.scss:395` `min-width: 850px`. Плюс оверлей глобального поиска
фиксированной ширины 600px уезжает за экран (`Dashboard.scss:~634`).
Из повседневного цикла на легаси-Blueprint осталась только форма расхода
(`routes/dashboard.tsx:533` → `ExpenseFormPage`). Карточных представлений
списков нет нигде.

**Линия 2 — четыре готовых модуля недоступны (ПУСТЫШЕК НЕТ).** Все 28
фичефлагов несут настоящий код (~34 000 строк по модулям). Но: список
модулей в UI (`ModulesPage.tsx:40-59`) и серверный allowlist
(`Features.constants.ts:10`) — два независимых захардкоженных списка без
теста-сверки, и они разошлись. **`telegram_quick_entry`** (крон-обработчик +
205 строк разбора + блок в UI) и **`onec_import`** (страница, роут, меню) —
включить можно только курлом: тумблера в «Модулях» нет. **`payroll_kpi`**
(вкладка KPI, цели, расчёт бонуса) и **`bank_statement_import`** (830 строк
импорта выписок) — включить нельзя вообще: вне allowlist, сервер отвечает
400 (вот почему в приёмках флаг включали прямым SQL). Плюс дыра класса v7:
**`deals` и `deal_stages` — флаги без `@RequireFeature` на контроллерах** —
выключенный модуль прячется только визуально, API отвечает всем.
Три интеграции (эквайринг, маркетплейсы, МойСклад) — честно read-only;
зарплата пишет не в ГК, а в платёжный календарь (задокументировано).

**Линия 3 — мины роста данных (ядро отчётов здорово).** Баланс/ОПиУ/ОСВ/ДДС
агрегируют в SQL — там всё правильно. Но: **Главная книга и Журнал тянут все
проводки периода в память без лимита** (`GeneralLedgerRepository.ts:110-131`,
`JournalSheetRepository.ts:90-118` + все контакты целиком) — при 30–50 тыс.
проводок это десятки секунд и OOM. **`EXPORT_SIZE_LIMIT = 9999999`**
(`Export/constants.ts:1`) — лимита фактически нет, `/export/all` синхронно
собирает всю базу в буфер, а `catch → skipped` проглотит даже таймаут.
**Индексы:** на `accounts_transactions` 13 одиночных и ни одного составного
(`(account_id, date)`, `(reference_type, reference_id)` нет);
`sales_invoices.due_date` не проиндексирован (полный перебор на каждом
календаре/дебиторке); `items_entries.reference_id` — VARCHAR. **Курс валют:**
`ExchangeRates.service.ts:15-36` — без кэша, `OpenExchangeRate.ts:30` — без
таймаута; календарь делает N последовательных внешних HTTP, при недоступности
API виснет навсегда.

**Линия 4 — онбординг говорит неправду (хвосты v14).** Формат `/auth/meta`
разошёлся с фронтом: сервер отдаёт плоский `{signupDisabled}`
(`GetAuthMeta.service.ts:17-21`), фронт читает `meta.signup_disabled` и
`meta.one_click_demo` — из-за этого мертвы сразу три вещи: флаг «регистрация
закрыта» (форма показывается и отказывает после заполнения), кнопка демо и
честность мастера. Серверной части демо-режима нет вовсе (полный one-click —
3–5 дней, не сейчас). Шаг «Подписка» рисуется в степпере даже когда
пропускается; в мастере английские хвосты. **`taxRegime` хранится, но его не
читает никто**; константа ставок-по-режиму — сирота; **ИНН/КПП организации
нельзя задать из UI, хотя печатные формы их печатают**. Мёртвых «Подробнее»
осталось два (ставки, правила банка) — с английскими текстами.

### Чего в списке НЕТ

- **Полный one-click демо-режим** (генератор данных, TTL-тенанты) — 3–5

- **Реквизиты организации в UI + ставка по налоговому режиму** — полезно
  (печатные формы без ИНН!), но средний объём; вопрос 22, кандидат в v16.

  покажет реальное использование телефона.
- **Полная пагинация ГК/Журнала и экспорт через очередь** — в М3 только
  честные потолки; полноценная переделка — следующие фазы.

## 4. Предлагаемая фаза: «Открыть построенное»

1. **М1 — телефон открывается.** ✅ **Сделано.** Три CSS-блокера сняты
   через `@media`: жёсткие ширины 1100px/850px и запрет прокрутки действуют
   теперь только на десктопе (≥769px — там поведение в точности прежнее,
   проверено замером на 1440px), на телефоне их нет. Оверлей поиска не шире
   экрана (`min(600px, calc(100vw - 2rem))`), на десктопе положение прежнее.
   Сторож-тест держит все четыре точки (жёсткая ширина допустима только под
   `@media`). Живая проба Playwright на 390px против собранного фронта и
   живого API: **до** — ширина документа 1100 при экране 390, прокрутка
   запрещена (65% интерфейса недостижимо), **после** — ровно 390, прокрутка
   работает, бургер-меню и кнопки топбара видны, список счетов умещается.
   Грабля сборки: `vite build` на сервере требует `SASS_PATH=.` (иначе
   sass не находит `src/style/_base.scss`).
2. **М2 — все построенные модули доступны.** ✅ **Сделано.** Четыре готовых
   модуля получили тумблер в «Настройки → Модули»: `telegram_quick_entry` и
   `onec_import` (сервер их разрешал и раньше — не хватало только записи в
   интерфейсе), `payroll_kpi` и `bank_statement_import` (вопрос 20 решён по
   умолчанию из карты — открыты: добавлены в серверный allowlist). Все
   четыре с иконками и парой текстов ru/en. Заведён **сторож сверки**:
   серверный `MODULE_ALLOWLIST` обязан совпадать со списком интерфейса, и у
   каждого модуля обязаны быть название и описание в обеих локалях — два
   независимых ручных списка больше не разъедутся молча. Закрыта дыра
   класса v7: на «Сделки» и «Этапы сделки» повешены `@RequireFeature` +
   `FeatureGuard` (в модуль добавлен `FeaturesModule` — иначе краш при
   старте). Прежняя причина исключения («сделка выбирается в формах
   операций») оказалась устаревшей: список сделок запрашивает только сам
   раздел, а синхронизация с CRM ходит в сервисы мимо контроллера. Живая
   проба: два запертых модуля включились (было 400 «не переключаемый
   модуль»), выключенный раздел «Сделки» стал отвечать 403 вместо 200 — и
   на чтение, и на запись, включение возвращает 200.
   **Состязательная проверка правок (17 подтверждённых находок из 37) нашла
   два регресса, которых не увидели ни тесты, ни первая живая проба, — оба
   исправлены здесь же:** (1) включённый «KPI» при выключенной «Зарплате»
   ломал соседний раздел «Сделки» (запрос сотрудников уходил на закрытую
   ручку и давал ложное «нет прав»); теперь дочерний тумблер нельзя включить
   без родителя (подсказка «Сначала включите «Зарплату»»), а запрос
   спрашивает оба флага; (2) ручку сделок дёргает ВТОРОЙ, легаси-хук
   («проект» — прежнее имя сделки) — три места без проверки флага получали
   403 на отчёте о рентабельности и в списке проектов; закрыты, заведён
   сторож на все вызовы этого хука. Попутно: KPI-ручки получили собственный
   замок (пометка теперь умеет требовать пару флагов — свой и родительский,
   иначе пометка на ручке перекрывала родительскую), ручной запуск разбора
   Telegram перестал работать при выключенном модуле, а сторож сверки
   перестал быть ложно-зелёным на закомментированных модулях и проверяет
   ещё иконки, повторы и наличие флага в реестре.
3. **М3 — мины роста обезврежены дёшево.** Идёт по срезам.
   - **Срез 1 — индексы.** ✅ **Сделано.** Одна тенантная миграция: составной
     индекс «счёт + дата» на проводках и индекс срока оплаты у счетов
     покупателей. Живая проба на базе стенда: накат → откат → накат, все три
     прогона чисто, планировщик **выбирает** оба новых индекса (у срока
     оплаты индекса не было вовсе — был полный перебор). **Два индекса из
     карты не поставлены — доказано планировщиком, что пользы не будет:**
     пара «тип документа + номер» проигрывает существующему индексу номера
     (он избирателен сам по себе), а на позициях документов колонка ссылки
     строковая, тогда как код сравнивает её с числами — база приводит тип и
     индекс не применяет вовсе (долг: сначала сменить тип колонки).
     Попутно заведён сторож: у каждой тенантной миграции обязан быть рабочий
     откат — он сразу нашёл две миграции 2022 года с пустым `down()`, обе
     починены. **Грабли стенда, не продукта:** миграция v12 была применена
     руками при давней пробе и не записана в журнал — из-за этого штатный
     прогон падал на «дубле ключа» и откатывал записи всего пакета (сам
     индекс при этом оставался, потому что MySQL фиксирует DDL сразу);
     журнал стенда приведён в соответствие с фактом.
   - **Срез 2 — курс валют.** ✅ **Сделано, но не то, что планировалось.**
     Живая проба на стенде вскрыла, что запрос курса валют **не работал
     вообще**: отвечал 500 на любой вызов, интерфейс эту ошибку молча
     проглатывал, а форма документа подставляла курс **1** — счёт в долларах
     считался один к одному с рублём. Две молчаливые причины: (1) контроллер
     брал организацию из `req.tenantId`, которую в Bigfin никто не заполняет
     (все остальные берут её из контекста запроса), поэтому запрос к базе
     получал пустоту и падал; (2) общий перехватчик переименовывает входящие
     параметры (`from_currency` → `fromCurrency`), а описание запроса было в
     snake_case — валюты выбрасывались как посторонние, курс всегда считался
     «базовая к базовой», а проверка длины кода валюты не срабатывала ни разу.
     Сделано по замыслу карты и сверх него: кэш в памяти (организация + пара
     валют, час жизни, потолок 1000 записей с вытеснением — валюты приходят из
     запроса пользователя), запасной курс с пометкой «несвежий», таймаут 10
     секунд, честные коды вместо сырых сетевых ошибок, убрано молчаливое
     «`|| 1`» у ответа службы и в прогнозе платёжного календаря, базовая
     валюта спрашивается у базы только когда валюта не названа. В интерфейсе:
     отказ показывается словами («впишите курс вручную»), несвежий курс —
     предупреждением, форма больше не подставляет единицу. **Живая проба
     до/после:** было 500 без объяснения → стало 400 с понятным кодом; валюты
     из адреса дошли до сервера; три одинаковых запроса — один поход наружу
     вместо трёх; при поломке службы отвечаем из кэша, а на незнакомую пару —
     честный отказ. **Попутно той же болезнью болел телефон филиала** (поле в
     snake_case — молча не сохранялся); заведён сторож на все входящие
     описания запросов, во всём коде это было единственное такое поле.
   - **Срез 3 — потолок Главной книги и Журнала.** ✅ **Сделано, и снова не
     то, что планировалось.** Живая проба вскрыла, что **оба отчёта вообще не
     открывались**: 500 на любом периоде с проводками. Причина — у шести типов
     операций (дивиденды, выдача и платёж по займу, амортизация и выбытие
     основного средства, перемещение между складами) **не было названий в
     справочнике**; поиск названия возвращал пустоту, а перевод по пустому
     ключу ронял весь отчёт. Названия заведены парно ru/en, а поиск сделан
     устойчивым: новый модуль без названия покажет технический тип, но отчёт
     откроется. Заведён сторож: каждый тип операции, попадающий в проводки,
     обязан иметь название в обеих локалях. **Сам потолок:** оба отчёта
     считают строки ДО выборки (одним дешёвым запросом по новому индексу из
     среза 1) и при переполнении честно отказывают кодом
     `REPORT_ROWS_LIMIT_EXCEEDED` с числами «вышло / предел»; потолок 50 000
     строк, меняется переменной окружения. Молча ничего не режется. **В
     интерфейсе** отказ стало видно: раньше провайдеры отчётов ошибку не
     читали вовсе, а экран лез в пустые данные и падал в общую заглушку
     «Что-то пошло не так»; выгрузка и предпросмотр PDF при отказе крутились
     вечно (ошибка не ловилась, а тело ошибки приходило файлом и не
     разбиралось). Всё это закрыто, сторож держит обе половины. **Живая проба
     до/после:** было 500 на обоих отчётах → стало 200; при потолке 5 строк —
     400 с числами «57 из 5» за 0,12 с (то есть отказ ДО выборки), узкий
     период по-прежнему 200, выгрузка CSV потолок не обходит.
   - **Срез 4 — честный лимит выгрузки.** ✅ **Сделано.** Предела у выгрузки
     не было: в двенадцати местах стояла «бесконечность» `EXPORT_SIZE_LIMIT =
     9999999`, ещё в двух — магическое `pageSize: 12000` (то есть молчаливое
     усечение на 12000-й строке), а в четырёх выгрузках предела не было
     вовсе. Заведён один настоящий потолок на всех — 100 000 строк, меняется
     переменной окружения; все шестнадцать выгрузок переведены на него.
     **Одиночная выгрузка** при переполнении честно отказывает кодом
     `EXPORT_ROWS_LIMIT_EXCEEDED` ещё до сборки книги. **«Выгрузить всё»**
     не роняется из-за одного большого раздела: он пропускается, а в листе
     «Skipped» появилась колонка «Reason» с причиной и числом — раньше там
     было только имя раздела, и «сломалось» было не отличить от «не
     поместилось». Считаем ДО разворота строк документа: разворот ста тысяч
     записей дал бы миллион. **На фронте** отказ стало видно: одиночная
     выгрузка показывала безликое «что-то пошло не так» (ошибку даже не
     принимала в аргумент), а выгрузка PDF молчала вовсе — `.catch` не было.
     Сторожа: ни одна выгрузка не заводит свой размер страницы числом;
     причина отказа видна на экране. **Живая проба:** раздел из одной строки
     по-прежнему выгружается (200), раздел побольше при потолке 1 отвечает
     400 с кодом, «выгрузить всё» собирает книгу из 11 листов вместо 17, а
     шесть пропущенных перечислены в «Skipped» с причиной «Too many rows
     (over 1)».

   Исходный замысел шага: одна миграция составных индексов
   (`(account_id, date)`, `(reference_type, reference_id)`,
   `sales_invoices.due_date`); кэш курса с TTL + `timeout: 5000` + fallback
   на последний известный; честный потолок строк ГК/Журнала («сузьте
   период» вместо 30-секундного ответа); реальный `EXPORT_SIZE_LIMIT` и
   причина пропуска в листе «Skipped».
4. **М4 — онбординг говорит правду.** ✅ **Сделано.**
   - **Формат `/auth/meta` согласован.** Сервер отдаёт поля плоско
     (`{"signup_disabled": false}`), а фронт искал их во вложенном `meta` —
     поле было мёртвым: закрытая регистрация ни на что не влияла. Путь
     выправлен, заведён сторож, сверяющий поля ответа сервера с чтением на
     фронте. Дальше поле стали **использовать**: при закрытой регистрации
     страница показывает «Регистрация закрыта» вместо формы (раньше человек
     заполнял её целиком и только потом получал отказ), а на входе исчезает
     приглашение «Зарегистрируйтесь» — иначе оно ведёт в тупик.
   - **Шаг «Подписка» убран из мастера.** Он выбирался условием «подписка
     неактивна», а у нового пользователя подписки нет никогда — значит это
     был **первый экран для всех**, и на нём показывались долларовые тарифы
     и оплата чужого сервиса с английским текстом. Список шагов вынесен в
     отдельный файл под тестами; сам экран из кода не удалён, только не
     показывается.
   - **Две мёртвые «Подробнее» убраны**, английские тексты этих экранов
     переведены (русские ключи уже лежали в словаре и не были подключены).
     Заведён сторож: на пустых экранах не бывает кнопок в никуда и
     английских строк. Попутно на первом экране мастера убрана ссылка-
     заглушка `href="#"` у выхода.
   - **Живая проба (браузер + API):** сервер отдаёт `signup_disabled: true`
     → страница регистрации показывает «Регистрация закрыта» без формы, на
     входе приглашения нет; вернули `false` → форма и приглашение на месте.
   - **Не тронуто намеренно:** блок `one_click_demo` (кнопка «демо») —
     сервер этих полей не отдаёт вовсе, кнопка не рисуется; это **вопрос 21**
     владельцу. Чтение поля выправлено, чтобы кнопка появилась сразу, как
     только поле появится на сервере.

**Что НЕ делать сейчас**: полный демо-режим, мобильные карточки, пагинация
ГК, экспорт очередью, ядро мультивалюты.
