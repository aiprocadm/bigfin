# ㉙ — Метод начисления: тумблер ОПиУ (кассовый / начисление)

**Дата:** 2026-06-11
**Под-проект роадмапа:** ㉙ (§4.13) — «режим ОПиУ `cash | accrual`: „начисление" — по дате документа (счёт/акт), „кассовый" — по дате оплаты. По умолчанию кассовый (аудитория без бухгалтерского образования)».
**Зависит от:** ④ (отчёты), ㉑ (Budgets — там уже есть понятие «кассово-расчётной» операции для БДДС).
**Флаг:** `Features.ACCRUAL_PNL = 'accrual_pnl'` (по умолчанию **off** — паттерн ⑦b/⑧b/㉗).
**Контекст решений (в рамках делегированного исполнения роадмапа):**
- новый расчётный движок **не пишется** — это представление над существующим леджером (`accounts_transactions`), паттерн `ProfitLossSheet` + Query-DTO;
- баг текущего состояния: радио «кассовый/начисление» в шапке ОПиУ уже есть, сервер принимает `basis` в DTO, но **движок его полностью игнорирует**, а дефолты расходятся (webapp `cash`, сервер `accrual`) — ㉙ закрывает именно это;
- определение «кассовой» операции **переиспользуется из Budgets** (`cashSettledReferenceKeys`): источник (reference) считается оплаченным деньгами, если хотя бы одна его нога легла на денежный счёт (`cash`/`bank`) и это не внутренний перевод (`TransferToAccount`/`TransferFromAccount`) — список не дублируется;
- ручной перенос месяца начисления отдельной операции и раздельные статьи ДДС vs ОПиУ на одной операции — **не входят** (anti-scope роадмапа).

---

## 1. Зачем

Основная аудитория ведёт учёт «по деньгам»: прибыль месяца — это что реально пришло и ушло. Но как только появляются счета покупателям и акты, возникает второй взгляд — «по документам». Сейчас тумблер в ОПиУ есть, но ничего не делает: пользователь щёлкает «кассовый/начисление» и видит одни и те же цифры. ㉙ делает тумблер настоящим: один отчёт, два корректных режима, по умолчанию — кассовый.

## 2. Модель данных

**Нет.** Никаких новых таблиц/колонок/миграций. Оба режима — чтение существующих `accounts_transactions` + `accounts`.

## 3. Логика режимов

### a) `accrual` (начисление) — текущее поведение, без изменений

Все проводки по доходно-расходным счетам за период по дате проводки (= дате документа: счёт, акт, ручная проводка). SQL-агрегация в `ProfitLossSheetRepository` остаётся как есть.

### b) `cash` (кассовый) — только «оплаченные деньгами» источники

1. Берём все проводки периода (с учётом фильтра филиалов).
2. Через `cashSettledReferenceKeys` (Budgets) отбираем источники, у которых есть нога на денежном счёте и которые не являются внутренним переводом.
3. В ОПиУ попадают **только проводки этих источников**; агрегация по счёту (итог) и по счёту+периоду (колонки день/месяц/год) повторяет форму SQL-агрегации — дальше конвейер отчёта (схема, формулы, PP/PY, проценты) не меняется ни строчкой.

Практика для аудитории: операции ДДС с доходной/расходной статьёй, оплаты, расходы с кассы/банка — попадают в кассовый ОПиУ по дате денег; неоплаченный счёт покупателю — не попадает (он появится в режиме «начисление» по дате документа).

**Известное ограничение (осознанно):** оплата счёта покупателя гасит дебиторку, а доходная нога живёт в самом счёте — поэтому доход «счёт + оплата» виден в кассовом режиме не через перепривязку оплаты к счёту (это уже расчётный движок, anti-scope), а через прямые денежные операции. Для дальнейшего сближения есть ㉒/бэклог.

## 4. Поведение флага и дефолты

| | Флаг **off** (сегодняшний прод) | Флаг **on** |
|---|---|---|
| `basis` в движке | игнорируется — цифры байт-в-байт как сегодня | честно применяется (`cash`/`accrual`) |
| Дефолт сервера | `accrual` (как сегодня) | **`cash`** |
| Дефолт webapp | `cash` (уже так) | `cash` |
| Радио в шапке ОПиУ | скрыто (раньше было мёртвым) | видно и работает |

Решение о применении кассового фильтра принимает `ProfitLossSheetService` (один lookup флага на запрос) и передаёт в репозиторий готовый признак `cashBasisActive` — сам репозиторий о флагах не знает.

## 5. API

Без изменений: `GET /reports/profit-loss-sheet?basis=cash|accrual` — параметр уже есть в `ProfitLossSheetQuery.dto.ts`, теперь он влияет на цифры (при включённом флаге).

## 6. Фронт

- Радио `RadiosAccountingBasis` в `ProfitLossSheetHeaderGeneralPane` уже есть и уже переведено («Метод учёта: Кассовый / По начислению») — новые ключи i18n не нужны;
- показывается за `featureCan('accrual_pnl')` (константа `Features.AccrualPnl` в webapp);
- `basis` уже круговым маршрутом ходит в API (`getDefaultProfitLossQuery` → форма шапки → `transformFilterFormToQuery`), дефолт `cash` уже стоит.

## 7. Тесты (Jest, рядом с модулем)

- `ProfitLossSheetCashBasis.spec.ts`: неоплаченный счёт (без ноги на денежном счёте) исключается из кассового режима; денежная операция с расходной ногой включается; внутренний перевод исключается; агрегация итога и периодов (день/месяц/год) считает суммы корректно;
- `ProfitLossSheetRepository.cashBasis.spec.ts` (mock-based): при `cashBasisActive` репозиторий агрегирует только кассовые источники; без него — отдаёт SQL-агрегацию как сегодня (начисление включает неоплаченные счета);
- `FeaturesConfigure.accrualPnl.spec.ts`: флаг есть, дефолт off.

## 8. НЕ входит (явно отложено)

- Ручной перенос месяца начисления отдельной операции;
- Раздельные статьи ДДС vs ОПиУ на одной операции;
- Перепривязка оплат к счетам для кассового дохода (расчётный движок);
- Кассовый режим в балансе / ДДС / GL — только ОПиУ.

## 9. Критерий завершения ㉙

Включить флаг → в ОПиУ тумблер переключает кассовый↔начисление, цифры прибыли корректны для каждого метода, по умолчанию кассовый. `pnpm typecheck`, тесты `FinancialStatements`, `lang-check.js` — зелёные. Флаг off — поведение и цифры как до ㉙.
