### 0.2. Что удалось и что не удалось проверить у конкурента

**Проверено интерактивно [OBSERVED]:**

Показатели (обычные) `/`; Показатели PRO — все семь вкладок (`/dashboard-pro/cashflow`, `/income`, `/project`, `/deal`, `/balance`, `/debts`, `/budgets`); Операции `/transactions` — фильтры, массовое выделение, меню действий, настройка колонок, карточка операции, разбиение суммы, всплывающие подсказки бейджей; Платёжный календарь `/budget/planning` — все режимы отображения и оба источника; БДР `/budget/Bdr` — список и редактор бюджета; Отчёты — ДДС `/reports/cashflow`, ОПУ `/reports/pnl`, Баланс `/balance`, включая раскрытие суммы; Справочники — Учетные статьи `/transaction-categories`, Мои счета `/accounts`, Мои юрлица `/legal-entities`, Контрагенты `/contractors`; Сделки `/deals/selling`, Выставленные счета `/invoice-documents`; Проекты `/projects`; Настройки `/manage/general-settings`, `/notification-settings`; глобальная панель «На счетах», центр уведомлений, меню «Помощь и обучение», страница 404.

**Не удалось проверить — честный список:**

1. **Создание сущностей.** В demo-аккаунте **нет ни одной кнопки создания** — ни «Добавить операцию», ни «Создать бюджет», ни «Новый контрагент». Проверен экран «Операции» (поиск по DOM по словам «Добавить», «Создать», «Новая», «Импорт» дал только заголовок и счётчик). Формы редактирования открываются, но сценарий создания с нуля недоступен. Всё, что сказано ниже о создании, помечено `[INFERRED]`.
2. **Пользователи, роли и права.** Раздел «Настройки» в demo содержит только четыре пункта: Общие настройки, Курсы валют, История действий, Уведомления. Прямые заходы на `/manage/users` и `/manage/integrations` дают страницу 404. **Модель прав ПланФакта не проверена вообще.**
3. **Интеграции и импорт выписок.** Точек входа в demo не обнаружено. Есть ли у ПланФакта банковские коннекторы, импорт 1С, автоправила категоризации — **по demo установить нельзя**. В ТЗ это не используется как аргумент.
4. **Мобильное поведение.** Попытка изменить размер окна браузера до 420 px не подействовала (окно не перерисовалось). Адаптивность ПланФакта **не проверена**. 5. **Графики на вкладках PRO «Проекты» и «Сделки»** отрисованы в canvas — содержимое не читается текстом, описана только обвязка (селекторы и заголовки).

## 1. Executive Summary

### 1.1. Что представляет собой Bigfin сейчас

`[CODE-CONFIRMED]` Bigfin — монорепозиторий на pnpm + lerna: сервер `packages/server` (NestJS 10, Objection + Knex, MySQL/MariaDB, Redis, BullMQ, база на организацию) и витрина `packages/webapp` (React 18, Vite 5, react-router v5, Redux Toolkit + react-query v3). 3267 серверных `.ts`-файлов, 3050 файлов витрины, 586 файлов тестов, ~3438 объявленных проверок.

Продукт вырос из форка Bigcapital и **полностью переработан под российский управленческий учёт**: юрлица с ИНН/КПП/ОГРН и налоговыми режимами, консолидация группы с внутригрупповыми оборотами, статьи управленческого учёта, платёжный календарь с прогнозом кассового разрыва, бюджеты БДР/БДДС со сценариями, шесть печатных форм РФ, сумма прописью, курсы ЦБ РФ, импорт выписок 1С и таблицами, коннекторы Тинькофф и Альфа-Банка, Wildberries и Ozon, МойСклад, ZenMoney, YooKassa, Битрикс24/amoCRM, публичный API с вебхуками, ИИ-аналитик на YandexGPT/GigaChat.

Под всем этим — **настоящая двойная запись**: таблица `accounts_transactions`, предохранитель `assertBalanced()` в `src/modules/Ledger/LedgerStorage.service.ts:68-95`, который отказывается писать журнал при расхождении дебета и кредита больше полукопейки. Это фундамент, которого у ПланФакта, судя по наблюдаемому интерфейсу, нет.

Предыдущее мастер-ТЗ (`docs/tz/MASTER.md`, 15 этапов) закрыто по коду; по `docs/tz/STATE.md` очередь пуста, идёт режим стабилизации, приёмка владельца не выполнена ни по одному этапу.

### 1.2. Какие основные разрывы обнаружены

Разрывы разложены на четыре группы. Внутри каждой — ссылка на раздел 6 с требованиями.

**Группа A. Пользователь не понимает, откуда берутся цифры.**
Статьи управленческого учёта в Bigfin имеют два вида — `income` и `expense` (`packages/server/src/database/tenant/migrations/20260529120000_create_management_articles_table.ts:12`, комментарий в коде: `// 'income' | 'expense'`) `[CODE-CONFIRMED]`. Движения по активам, обязательствам и капиталу статьями не классифицируются — они живут только в плане счетов, то есть в бухгалтерском слое, который целевой пользователь (предприниматель без бухгалтерского образования) не открывает. Схемы, объясняющей связь статей и отчётов, нет. → FIN-001, FIN-002, FIN-003.

**Группа B. Раскрытие суммы есть, но ведёт не туда.**
`GetReportDrillDownService` раскрывает сумму **по счёту** (`accountId`), а не по статье, и возвращает список операций журнала — дата, номер, дебет, кредит `[CODE-CONFIRMED]`, `packages/server/src/modules/FinancialStatements/queries/GetReportDrillDown.service.ts`. Раскрытие есть только в трёх отчётах из девятнадцати `[CODE-CONFIRMED]` (`packages/webapp/src/containers/FinancialStatements/ReportDrillDownPanel.tsx` используется в BalanceSheet, ProfitLossSheet, CashFlowStatement). Передачи в реестр операций с фильтрами нет. → FIN-004, FIN-005.

**Группа C. Деньги не на виду.**
Прогноз кассового разрыва считается (`GetPaymentCalendarForecast.service.ts` + `utils/computeRunningBalance.ts`, возвращает **один** `CashGap{date, amount, daysFromStart}`) `[CODE-CONFIRMED]`, но показывается только на главной, в герое «лента денег». Уйдя с главной, пользователь теряет и остаток, и предупреждение. Разрыва по отдельному счёту нет — хотя сервис уже принимает `accountId` (там же, строки 106–113) `[CODE-CONFIRMED]`. → FIN-006, FIN-007.

**Группа D. Отчёты настраиваются медленно и показывают меньше, чем могут.**
Настройки отчёта спрятаны в шторку `FinancialHeaderDrawer` `[CODE-CONFIRMED]`. ОПиУ строится только по периодам — разреза по проектам и сделкам нет. Ярусов прибыли (EBITDA/EBIT/EBT) нет. Спарклайна в строке нет. Графики есть только в 6 из 19 отчётов; библиотека одна — recharts, используется в пяти файлах `[CODE-CONFIRMED]`. ДДС в `FinancialStatements` считается **косвенным методом** (`modules/CashFlowStatement/schema.ts`) `[CODE-CONFIRMED]`; прямой ДДС по статьям существует отдельно (`src/modules/Budgets/queries/ArticlesCashflowRollup.service.ts`), но у него нет собственного отчёта с таблицей и экспортом. → FIN-008 … FIN-013.

### 1.3. Каким должен стать продукт

Предприниматель открывает Bigfin и за пять секунд видит: сколько денег, на каких счетах, и на каком счёте когда кончатся. За один клик из любой суммы любого отчёта проваливается в операции, из которых она сложилась, и оттуда — в реестр с фильтрами. Справочник статей объясняет ему картинкой, как его «Аренда» превращается в строку ОПиУ и в строку ДДС. Отчёт перестраивается по проектам одним выбором в шапке. Всё это — **на существующей архитектуре**, без единого нового модуля уровня «Зарплата» или «Основные средства».

### 3.2. Модель операции — ядро ПланФакта

`[OBSERVED]` Карточка «Редактирование операции» (боковая панель, открывается кликом по строке реестра):

| Поле | Поведение |

| Счет и юрлицо | один селектор, в подписи показан **текущий остаток счёта**: «Сейф [ИП Алексеенко Михаил Федорович] −178 226 RUB» |

| **Дата начисления** | дата + чекбокс **«Подтвердить начисление»**; ссылки «Автоматизировать» и **«Распределить на период»** |

| Заголовок | «Создана 20 сен '26 в 00:37» |

**Разбиение суммы.** Выпадающий список «Выберите, как разбить сумму…» с пятью вариантами: **Начисление, Контрагент, Статья, Проект, Сделка продажи**. После выбора появляется таблица «Статья | Сумма, RUB | Доля», строки добавляются ссылкой «Добавить строку», внизу «Итого: 0 / 0 %» и **красная строка-подсказка «Распределите еще 198 620 / 100 %»**, которая пересчитывается вживую. Отмена разбиения спрашивает подтверждение: «Подтвердите, что вы хотите отменить разбиение суммы операции. Это приведет к удалению ранее введенных данных» — кнопки «Вернуться» / «Подтвердить».

**Из двух дат выводится всё остальное.** Подтверждено наведением на бейджи в реестре:

- Бейдж **«Д»** (бирюзовый): «Дебиторка (вам должны) — дата начисления уже подтверждена, а дата оплаты еще нет (постоплата)».
- Бейдж **«К»** (фиолетовый): «Кредиторка (вы должны) — дата начисления уже подтверждена, а дата оплаты еще нет (постоплата)».
- Значок **«!»** (оранжевый): «Дата оплаты и дата начисления просрочены».

То есть дебиторка и кредиторка — **не отдельная сущность, а вычисляемое состояние операции**. `[INFERRED]` Аванс (оплата подтверждена, начисление нет) должен давать зеркальные состояния; в demo такой строки найти не удалось.

**Документы начисления.** Типы «Отгрузка» и «Поставка» открывают другую форму — «Редактирование отгрузки»: ссылка на сделку, «Дата отгрузки» + чекбокс «Плановая отгрузка», обязательные Юрлицо и Клиент, Проект, Статья продажи услуг, и **табличная часть «Товары/услуги для отгрузки»**: Наименование, Кол-во, Цена за ед. ₽, Скидка, НДС, Сумма ₽; ссылки «Добавить…» и **«Заполнить позициями из сделки»**, итог «Сумма отгрузки: 600 000 ₽». Внизу «* Обязательные поля».

### 3.5. Платёжный календарь

Селекторы: **«Отображение: По дням / По неделям / По месяцам / По кварталам / По годам»**, **«Источник: Доходы и расходы / Движение денег»**, «Учет: Кассовый метод», меню «…» → «Скачать в Excel». Кнопка **«На сегодня»** прокручивает таблицу к текущей дате.

В режиме «Движение денег / По дням»: строки — Операционный поток (+), Инвестиционный поток (+), Финансовый поток (+), Перемещения (+), Общий итог, **Остатки на счетах (+)**. Колонка сегодняшнего дня разделена на «факт | план», будущие дни — только «план». Выходные дни подсвечены. Раскрытие потока даёт Поступления / Выплаты и далее по статьям. **Клик по сумме не делает ничего — раскрытия до операций нет.**

В режиме «Доходы и расходы / По месяцам»: Доходы (+), Расходы (+), Чистая прибыль, Рентабельность %, Дивиденды, Нераспределенная прибыль; колонка «янв '26–дек '26» разделена на «факт | план».

### 3.6. Бюджеты

Список: Название, Валюта, Юрлицо, Проект, Период, Дата изменения, Кто изменил; фильтры Юрлица, Проекты, поиск по названию. Бюджеты бывают привязаны к проекту либо общими («Общий бюджет компании»).

Редактор бюджета: заголовок + бейджи «БДР | Окт '26 — дек '26 | RUB», кнопка «.xls». Селекторы: «По месяцам», «Кассовый метод», «Показатели прибыли». **Чекбоксы колонок: Факт, Вып. плана %, Откл., Откл. %** — три последних заблокированы, пока не включён «Факт». При включении колонка «Итого» разворачивается в пять подколонок: План | Факт | Вып. плана, % | Откл. | Откл., %. Подсказка при наведении: «Разница между планом и фактом в процентах». Неопределённое отношение печатается как **«н/о»**. Строки: Доходы (+), Расходы (+), Чистая прибыль/убыток, Рентабельность %; план вводится по статье и периоду.

На вкладке PRO «Бюджеты» каждый бюджет показан плиткой: Доходы / Расходы / Чистая прибыль, под каждым «План …» и «Выполнено … %», а рядом — **«Прошло времени 60 %»**. Это и есть честное сравнение: выполнено 56 % плана при прошедших 60 % времени.

### 3.8. Глобальные элементы

**Виджет «На счетах».** В шапке всегда: «На счетах 2 743 652 ₽ ⌄» и второй строкой оранжевым «Разрыв с 21.04.26», рядом — спарклайн динамики остатка. По клику разворачивается панель: крупная сумма, отметка времени «20 Сентября 2026 | 13:45», вкладки **«По группам» / «По юрлицам»**, селектор «Вид», ссылка «Свернуть группы». Ниже — колонки групп счетов («Нераспределенные (6) 2 743 652 ₽», «Депозиты (0) 0 ₽», «Новая группа (0) 0 ₽»), пустые группы приглашают «Переместите счета в эту группу». Внутри группы — счета, у каждого **цветная точка состояния и собственная дата разрыва**: «Альфа банк 909 494 ₽ / Разрыв с 09.11.26», «Сбер 450 067 ₽ / Разрыв с 23.10.26», «Т-Банк 265 254 ₽ / **Разрыв с 15.10.26 по 16.10.26**», «Сейф −178 226 ₽ / Разрыв с 21.04.26». Счета без разрыва — зелёная точка, без подписи.

**Меню «Помощь и обучение».** Три колонки: «Материалы» (Справка и инструкции, Бесплатный курс по финучёту, Обучающие видео, Telegram-канал), «Примеры бизнеса» (одиннадцать отраслевых демо), «Демонстрация» (запись на 15-минутное демо с экспертом).

**Центр уведомлений.** Правая шторка «Уведомления», в demo пустая: иллюстрация + «Здесь пока пусто» + «Новые уведомления появятся в этом окне».

**Страница 404.** «Похоже, такой страницы не существует» + «Вот несколько полезных разделов:» + четыре ссылки (Показатели, Операции, Отчеты, Проекты) + иллюстрация.

**Пустые состояния виджетов.** На обычных «Показателях» каждый виджет при отсутствии данных показывает **правдоподобный демонстрационный график** и поверх него текст: «Наполните ПланФакт платежными операциями, и здесь появится реальный график. При желании вы можете посмотреть на него в Демо-бизнесе». Для конкретных виджетов текст точнее: «Создайте проведенные операции Поступления и вы увидите реальный график», «Объедините несколько операций в Проект, и здесь появится реальный график».

**Настройки отображения.** «Отображать копейки», «Показывать прошлые кассовые разрывы в верхней панели», «Скрыть подсказки-вопросы», «Показывать фильтр "Дата начисления" в разделе "Операции"», «Отображать категорию статей (доходы, расходы и др.) в списке операций», «Показывать номер платежного поручения под статьей», «Подставлять текущую дату при копировании операции».

### 3.10. Сводка решений

**COPY CONCEPT** (концепция верная, реализация своя): виды статей и схема отчётов; бейджи состояния операции; глобальный виджет денег; нижняя сводная строка реестра; группировка реестра по дате; разрез отчёта по проектам/сделкам; ярусы прибыли; спарклайн «Тренд»; два источника платёжного календаря и пять масштабов; колонки план-факта в бюджете и «прошло времени»; Парето по контрагентам; четыре квадранта долгов; контекстная справка; разбиение суммы с живой валидацией; денежная/неденежная задолженность; группы счетов.

**IMPROVE** (функция нужна, но сделать заметно удобнее): раскрытие суммы — по статье **и** по счёту, с переходом в реестр и с сохранением сверки «начало + оборот = конец», которой у конкурента нет; ДДС прямым методом — сделать полноценным отчётом со всеми пятью форматами выгрузки, а не только графиком; настройка отчёта — вынести наружу **частично**, оставив шторку для редких параметров; двухдатная модель — добавить вторую дату денежной операции, **не разрушая двойную запись**; отраслевые демо-данные поверх существующего `OneClickDemo`.

**SKIP** (переносить не стоит): скудные массовые действия; выгрузка только в Excel; отсутствие раскрытия в календаре; пустой раздел Баланса в демо; маркетинговый обвес (курс, вебинары, партнёрская программа).

**BIGFIN ORIGINAL** (своё, чего у конкурента нет, — беречь и развивать): двойная запись с предохранителем сходимости; 19 отчётов; консолидация группы юрлиц с долями владения и внутригрупповыми оборотами; печатные формы РФ и сумма прописью; валидаторы ИНН/КПП/ОГРН/БИК; правила банковской категоризации и импорт выписок; массовая разноска; вердикт словами на главной; блок «Требует внимания»; сценарии бюджета; повторяющиеся плановые операции; права CASL и права по юрлицам; публичный API и вебхуки; поведение затрат (постоянные/переменные) и точка безубыточности; раскрытие суммы **в платёжном календаре** — то, чего у конкурента нет.

## 4. Target Product Architecture

### 4.1. Принцип

Целевая структура Bigfin **не меняется** относительно этапа 1 предыдущего ТЗ: восемь разделов верхнего уровня, глубина не больше двух. Настоящее ТЗ добавляет не разделы, а **входы**: глобальный виджет денег, раскрытие сумм, схему статей, переключатели в шапках отчётов.

### 4.2. Целевой состав

| Раздел | Что отвечает пользователю | Экраны | Состояние |
|---|---|---|---|
| **Главная** | «Сколько у меня денег и что горит» | `/` | есть; дополняется FIN-018 |
| **Операции** | «Что произошло и что произойдёт с деньгами» | `/cashflow-accounts/transactions`, `/cashflow-accounts`, `/bank-rules` | есть; дополняется FIN-008 … FIN-011 |
| **Отчёты** | «Сколько заработал, куда утекло, чем владею» | `/financial-reports` + 19 отчётов + новый `/financial-reports/cash-flow-articles` | есть; дополняется FIN-004 … FIN-007, FIN-012 … FIN-016 |
| **Планирование** | «Хватит ли денег и укладываюсь ли в план» | `/payment-calendar`, `/budgets`, `/payment-requests`, `/financial-model`, `/ai-chat` | есть; дополняется FIN-019 … FIN-022 |

| **Контрагенты** | «Кто нам должен и кому должны мы» | `/customers`, `/vendors` | есть; дополняется FIN-023 |
| **Справочники** | «Как устроен мой учёт» | `/management-articles` (**ядро**), `/legal-entities`, `/directions`, `/items`, `/payroll`, `/fixed-assets`, `/tax-rates`, `/cost-allocation`, `/dividends` + бухгалтерские | есть; `/management-articles` радикально дополняется FIN-001 … FIN-003 |

### 4.3. Сквозные элементы (появляются на всех экранах)

1. **Виджет «Деньги» в шапке** — `Topbar`. Сумма остатка, дата ближайшего разрыва, спарклайн; по клику — панель со счетами и разрывом по каждому. FIN-006, FIN-007.
2. **Кнопка контекстной справки** у заголовка экрана — `PageHeader`. FIN-025.
3. **Единый механизм раскрытия суммы** — компонент и ручка, общие для отчётов, календаря и бюджетов. FIN-004, FIN-005, FIN-020.
4. **Единая панель настройки отчёта** — общая шапка: период, масштаб, способ построения, метод учёта; редкое — в шторке. FIN-012.

### 4.4. Границы

- Новых серверных модулей — **один**: расширение `ManagementArticles`. Всё остальное — доработка существующих модулей и новые query-сервисы внутри них.
- Новых таблиц — **три** (`account_groups`, `article_report_map`, `user_display_preferences`), плюс колонки в двух существующих. Обоснование каждой — в разделе 7.
- Новых маршрутов витрины — **один** (`/financial-reports/cash-flow-articles`). Остальное — изменения существующих экранов.

**Проблема:** `[CODE-CONFIRMED]` `management_articles.kind` принимает только `income` и `expense` (`packages/server/src/database/tenant/migrations/20260529120000_create_management_articles_table.ts:12`). Движение денег, которое не является ни доходом, ни расходом — получение займа, покупка оборудования, возврат аванса, взнос учредителя — статьёй не классифицируется. Пользователь, размечая выписку, упирается в операции, для которых «нет подходящей статьи», и либо ставит неверную, либо бросает разноску.
**Цель:** Любая денежная операция может быть размечена статьёй; статья однозначно определяет, в какой строке какого отчёта сумма окажется.
**User Story:** Как собственник, размечающий выписку, я хочу выбрать для платежа по кредиту статью «Погашение кредита», а не подбирать среди расходов, чтобы прибыль не искажалась телом кредита.
**Текущее состояние Bigfin:** `[CODE-CONFIRMED]` Два вида; поля `cashflow_section` ∈ {operating, investing, financing, null} и `cost_behavior` ∈ {fixed, variable} уже есть; привязка к счетам плана счетов — таблица `management_article_accounts`; дерево строится через `parent_id`. Экран — `packages/webapp/src/containers/ManagementArticles/ManagementArticlesPage.tsx` + `ArticleTree.tsx`.
**Референс из ПланФакта:** `[OBSERVED]` Экран `/transaction-categories` имеет пять вкладок: Доходы, Расходы, Активы, Обязательства, Капитал. Системные статьи помечены замком и не удаляются.
**Предлагаемое решение Bigfin:** Расширить домен `kind` до пяти значений: `income`, `expense`, `asset`, `liability`, `equity`. Сохранить существующую связь `management_article_accounts` — именно она делает вид статьи не декларацией, а фактом: у статьи вида `asset` привязанные счета обязаны иметь корневой тип `asset`. Это **уточнение существующей модели, а не новая сущность**. Дерево статей, разноска, бюджеты и `ArticlesCashflowRollup` продолжают работать без изменений для `income`/`expense`.
**UI/UX:** Пять вкладок над деревом статей — `components/ui/tabs`. Вкладка запоминается в адресной строке (`?kind=asset`), чтобы ссылку можно было переслать. У системных статей — иконка замка и отключённое меню удаления. Счётчик статей на вкладке.
**Frontend:** `containers/ManagementArticles/ManagementArticlesPage.tsx` — вкладки и фильтрация; `ArticleTree.tsx` — без изменений структуры; форма статьи (RHF+Zod) получает поле «Вид статьи» только при создании, при редактировании оно заблокировано с подсказкой «Вид статьи меняет отчёт, в который попадают операции. Создайте новую статью и перенесите операции».
**Backend:** `src/modules/ManagementArticles/` — расширить перечисление, валидацию DTO и сид. Добавить проверку согласованности: при привязке счёта к статье корневой тип счёта обязан соответствовать виду статьи; несоответствие → `ServiceError` с русским текстом.
**API:** `GET /api/management-articles?kind=` — новый необязательный параметр. `POST`/`PUT` принимают расширенный `kind`. Существующее поведение без параметра не меняется.
**Database:** См. раздел 7, изменение D1. Тип колонки не меняется (`string`), меняется домен значений и добавляется CHECK-эквивалент на уровне валидации. Сид `src/database/tenant/seeds/data/managementArticles.ts` дополняется системными статьями видов `asset`, `liability`, `equity`.
**Business rules:**
1. Статьи видов `asset`, `liability`, `equity` **не участвуют** в ОПиУ ни при каком методе учёта.
2. Статьи всех пяти видов участвуют в ДДС по статьям (FIN-013), распределяясь по `cashflow_section`.
3. `cost_behavior` осмыслен только для `expense`; для прочих видов поле скрывается и не сохраняется.
4. Системные статьи (`predefined`) переименовываются, но не удаляются и не меняют вид.

**Validation:** Имя — 1…120 символов, уникально среди сиблингов; `kind` — из перечисления; `parent_id` — статья того же вида (смешанное дерево запрещено); `cashflow_section` обязателен для `asset`/`liability`/`equity`.

5. Существующие организации после миграции сохраняют все статьи с прежним `kind`; ни одна сумма ни в одном отчёте не изменилась — покрыто спекой сходимости «до и после».
6. `pnpm typecheck`, `node packages/webapp/scripts/lang-check.js` и серверные тесты зелёные.

### FIN-002 — Схема «Куда попадает статья»

**Название:** Живая схема участия статьи в трёх отчётах
**Проблема:** Пользователь не понимает связи между тем, что он выбирает при разноске, и тем, что видит в отчётах. Это прямо названо владельцем как главная беда продукта. Экрана, объясняющего связь, нет.
**Цель:** За один взгляд на экран статей человек понимает, в какую строку ДДС, ОПиУ и Баланса попадёт операция с выбранной статьёй.
**User Story:** Как новичок, я хочу увидеть, что статья «Аренда» уходит в «Операционный поток → Выплаты» в ДДС и в «Расходы → Аренда» в ОПиУ, чтобы перестать бояться, что я разношу неправильно.
**Текущее состояние Bigfin:** `[CODE-CONFIRMED]` Нет. Экран `/management-articles` — только дерево статей.
**Референс из ПланФакта:** `[OBSERVED]` Правая половина экрана `/transaction-categories`: три колонки-карточки («Движение денег», «Прибыли и убытки», «Баланс») с полной структурой отчётов, подпись «Эта схема наглядно показывает, как статьи участвуют в формировании отчета Баланс», итоговая строка «АКТИВЫ = ОБЯЗАТЕЛЬСТВА + КАПИТАЛ».
**Предлагаемое решение Bigfin:** `[PROPOSED]` Сделать **лучше, чем у конкурента**: у ПланФакта схема статична и не реагирует на выбор статьи. В Bigfin схема **подсвечивает конкретную строку** при выборе статьи в дереве и показывает рядом сумму за текущий период. То есть схема отвечает не «как устроен продукт вообще», а «где именно окажутся мои деньги».
Три карточки: «Деньги (ДДС)», «Прибыль (ОПиУ)», «Баланс». Структура строится **из данных**, а не из вёрстки: сервер отдаёт карту «вид статьи + раздел ДДС + корневой тип привязанных счетов → адреса строк в трёх отчётах». Выбор статьи подсвечивает соответствующие строки и печатает рядом оборот за выбранный период. Клик по подсвеченной строке открывает соответствующий отчёт с наложенным фильтром по этой статье.
**UI/UX:** Правая половина экрана на широких экранах; на телефоне — вкладка «Куда попадает» рядом с вкладкой «Статьи» (таблица на телефоне не помещается — сторож `tableScrollOnPhone.spec.ts` это проверит). Подсветка — фоном `rgb(var(--c-accent) / 0.15)` плюс левая планка; **не цветом текста**, чтобы не конфликтовать с правилом «расход не красный». Если статья ни в один отчёт не попадает (нет привязанных счетов) — отдельная строка-предупреждение «Статья ни на что не влияет: не привязан ни один счёт» со ссылкой на привязку.
**Frontend:** Новый компонент `containers/ManagementArticles/ArticleReportMap.tsx` + `ArticleReportMapCard.tsx`. Данные — новый хук `hooks/query/managementArticles.ts#useArticleReportMap`.
**Backend:** Новый query-сервис `src/modules/ManagementArticles/queries/GetArticleReportMap.service.ts`. Возвращает структуру трёх отчётов (статические узлы + узлы, порождённые статьями) и, если передан `articleId`, — адреса подсвеченных строк и оборот за период.
**API:** `GET /api/management-articles/report-map?articleId=&from=&to=` → `{ cashFlow: Node[], profitLoss: Node[], balance: Node[], highlights: { report, path[] }[], turnover: { amount, formatted } | null }`, где `Node = { key, title, children?, isHighlighted? }`.
**Database:** Изменение D2 (раздел 7) — таблица `article_report_map` **не создаётся**: карта выводится из `kind` + `cashflow_section` + корневых типов привязанных счетов. Новых таблиц требование не добавляет.
**Business rules:**
1. Статья вида `income`/`expense` подсвечивает строку в ОПиУ и строку в ДДС.
2. Статья вида `asset`/`liability`/`equity` подсвечивает строку в Балансе и строку в ДДС; в ОПиУ — ничего.
3. Оборот считается тем же кодом, что и отчёт, — переиспользуется `ArticlesCashflowRollupService`, а не пишется заново.
**Permissions:** `Preferences: read`.
**Validation:** `articleId` — существующая активная статья; период — не больше 5 лет.
**Error states:** Сбой загрузки карты не ломает дерево статей: карточка показывает состояние «ошибка» с кнопкой «Повторить».
**Empty states:** Статья не выбрана → схема показана без подсветки, с подписью «Выберите статью слева, чтобы увидеть, куда попадают её суммы».
**Acceptance Criteria:**
1. Выбор статьи вида `expense` подсвечивает ровно одну строку в карточке ОПиУ и ровно одну — в карточке ДДС; в карточке Баланса подсветки нет.
2. Выбор статьи вида `liability` подсвечивает строку в Балансе и строку в ДДС; в ОПиУ подсветки нет.
3. Сумма, напечатанная рядом с подсвеченной строкой, совпадает до копейки с суммой той же статьи за тот же период в отчёте «Деньги (ДДС по статьям)» — покрыто Jest-спекой сходимости.
4. Клик по подсвеченной строке открывает соответствующий отчёт с фильтром по этой статье в адресной строке.
5. Статья без привязанных счетов показывает предупреждение и не подсвечивает ничего.
6. На ширине 390 px схема доступна отдельной вкладкой и не создаёт горизонтальной прокрутки страницы.
**Dependencies:** FIN-001 (пять видов), FIN-013 (отчёт ДДС по статьям — для перехода и для сверки сумм).
**Priority:** **P0**

### FIN-003 — Состояние операции: дебиторка, кредиторка, просрочка

**Название:** Вычисляемые бейджи состояния денежной операции
**Проблема:** `[CODE-CONFIRMED]` В Bigfin дебиторка и кредиторка существуют только как остатки по документам (`sales_invoices.balance`, `bills.balance`) и видны в отчётах старения. В реестре операций, где пользователь проводит большую часть времени, состояние «нам должны» / «мы должны» / «просрочено» не видно никак.
**Цель:** Человек, глядя на список операций, сразу видит, какие из них ещё не закрыты деньгами и какие просрочены, — и понимает, почему.
**User Story:** Как собственник, я хочу видеть в списке операций пометку «нам должны» на отгрузке, которую ещё не оплатили, чтобы не открывать отдельный отчёт.
**Текущее состояние Bigfin:** `[CODE-CONFIRMED]` Колонки реестра — `packages/webapp/src/containers/CashFlow/AllTransactions/useAllTransactionsColumns.tsx`: Дата, Контрагент, Примечание, Тип, Счёт, Сумма. Бейджей состояния нет.
**Референс из ПланФакта:** `[OBSERVED]` Бейдж «Д» — «Дебиторка (вам должны) — дата начисления уже подтверждена, а дата оплаты еще нет (постоплата)»; бейдж «К» — «Кредиторка (вы должны) …»; значок «!» — «Дата оплаты и дата начисления просрочены».
**Предлагаемое решение Bigfin:** Не копировать двухдатную модель (это разрушило бы двойную запись), а **вывести те же состояния из того, что уже есть**:
- **«Нам должны»** — у строки реестра есть связанный документ `SaleInvoice` с `balance > 0`.
- **«Мы должны»** — связанный `Bill` с `balance > 0`.
- **«Просрочено»** — `due_date` связанного документа раньше сегодняшней даты при `balance > 0`, либо плановая операция (`planned_operations`) со статусом `planned` и `planned_date` в прошлом.
- **«План»** — строка порождена плановой операцией и ещё не материализована.
Подписи бейджей — словами, не буквами: «нам должны», «мы должны», «просрочено», «план». Буквенные «Д»/«К» — решение конкурента, требующее заучивания; Bigfin пишет по-русски. Подсказка при наведении объясняет состояние полной фразой и даёт ссылку на документ.
**UI/UX:** Бейджи — `components/ui/badge`, в колонке «Сумма» слева от числа, максимум два на строку. Цвет: «просрочено» — `danger` (это и есть беда, красный уместен); «нам должны» / «мы должны» / «план» — нейтральный контур, **не зелёный и не красный**. На телефоне бейдж переезжает во вторую строку карточки (`TransactionMobileRow.tsx`).
**Frontend:** `useAllTransactionsColumns.tsx` — новая ячейка `TransactionStateBadges.tsx`; `TransactionMobileRow.tsx` — вторая строка.
**Backend:** `src/modules/BankingTransactions/` — обогащение ответа списка полем `state: { kind, dueDate, documentId, documentType }[]`. Вычисление — новый `utils/resolveTransactionState.ts` со своей Jest-спекой. Никаких новых таблиц.
**API:** `GET /api/banking/transactions` — ответ дополняется полем `states`. Обратная совместимость сохраняется (поле необязательное).
**Database:** Изменений нет.
**Business rules:**
1. Состояния вычисляются на сервере, а не на витрине: правило одно и то же для реестра, отчётов и публичного API.
2. Документ в статусе «черновик» состояний не порождает.
3. Частично оплаченный документ даёт состояние «нам должны» с остатком, а не полной суммой.
**Permissions:** Наследуются от чтения операций.
**Validation:** Не применимо (только чтение).
**Error states:** Если связанный документ недоступен по правам, бейдж показывается без ссылки.
**Empty states:** Не применимо.
**Acceptance Criteria:**
1. Операция, связанная со счётом покупателю с `balance > 0` и `due_date` в будущем, получает ровно один бейдж «нам должны».
2. Та же операция при `due_date` в прошлом получает два бейджа: «нам должны» и «просрочено».
3. Полностью оплаченный счёт не даёт ни одного бейджа.
4. Подсказка при наведении содержит полную фразу и дату срока.
5. На ширине 390 px бейджи не выталкивают сумму за край — покрыто `containers/tableScrollOnPhone.spec.ts`.
6. Jest-спека `resolveTransactionState.spec.ts` покрывает все шесть комбинаций (черновик, частичная оплата, полная оплата, просрочка, план, материализованный план).
**Dependencies:** нет.

### FIN-004 — Раскрытие суммы по статье

**Название:** Раскрытие суммы отчёта до операций в разрезе статьи
**Проблема:** `[CODE-CONFIRMED]` `GetReportDrillDownService` раскрывает сумму **по счёту** (`accountId`) и возвращает строки журнала с дебетом и кредитом (`packages/server/src/modules/FinancialStatements/queries/GetReportDrillDown.service.ts`). Пользователь, который кликает по строке «Аренда» в ДДС по статьям, ждёт список платежей за аренду, а не выписку по бухгалтерскому счёту.
**Цель:** Клик по любой сумме в любом отчёте открывает именно те операции, из которых она сложилась, на языке пользователя.
**User Story:** Как собственник, я хочу кликнуть по «Аренда 391 282 ₽» и увидеть шесть платежей с датами, контрагентами и назначением, чтобы понять, откуда столько.
**Текущее состояние Bigfin:** `[CODE-CONFIRMED]` Раскрытие по счёту, в трёх отчётах, панелью `ReportDrillDownPanel.tsx` с двумя режимами (`turnover` и `balance`, последний показывает цепочку «остаток на начало + оборот = остаток на конец»). Лимит строк — 200 (`DRILL_DOWN_LIMIT`).
**Референс из ПланФакта:** `[OBSERVED]` Модальное окно «Операции по статье "Доходы"» с шапкой «Период отчета» и «Сумма операций», таблицей и ссылкой «Открыть в разделе Операции».
**Предлагаемое решение Bigfin:** Расширить существующий сервис вторым измерением, **не ломая первое**. Ручка принимает либо `accountId`, либо `articleId`, либо оба (пересечение). Ответ сохраняет все нынешние поля, включая `openingBalance`/`closingBalance` — это преимущество Bigfin над конкурентом, и его нельзя потерять. Добавляются поля строки: `accountName`, `articleName`, `projectName`, `dealName`, чтобы таблица была читаемой без справочников.
**UI/UX:** Панель остаётся панелью (`ReportDrillDownPanel.tsx`), а не превращается в модальное окно: панель не перекрывает отчёт, и пользователь видит, откуда пришёл. Шапка панели: название строки, период, итог, и **строка сверки** «Остаток на начало 120 000 + оборот 391 282 = остаток на конец 511 282», когда режим `balance`. Внизу — кнопка «Открыть в Операциях» (FIN-005) и, при обрезке, честная строка «Показаны первые 200 из 431 операций».

### FIN-023 — Денежная и неденежная задолженность

**Название:** Разделение долга на «должны деньги» и «должны товар/услугу»
**Проблема:** Аванс, полученный от клиента, и отгрузка без оплаты — принципиально разные обязательства, но в отчётах старения они сливаются в одно сальдо.
**Цель:** Видно, где ждём денег, а где — поставки.
**User Story:** Как собственник, я хочу отличать «клиент должен 500 000 ₽» от «мы взяли аванс 500 000 ₽ и должны сделать работу».
**Текущее состояние Bigfin:** `[CODE-CONFIRMED]` `contacts.balance`, отчёты `ARAgingSummary` и `APAgingSummary` по типу контакта. Разделения по природе долга нет.
**Референс из ПланФакта:** `[OBSERVED]` Фильтры на экране контрагентов: «Дебиторка: Денежная / Неденежная / Без дебиторки», «Кредиторка: Денежная / Неденежная / Без кредиторки». На вкладке PRO «Долги» — четыре блока: дебиторка с клиентами, дебиторка с поставщиками, кредиторка с клиентами, кредиторка с поставщиками.
**Предлагаемое решение Bigfin:** Вычисляемая классификация на основе уже существующих данных: если по контрагенту сумма подтверждённых отгрузок/актов превышает полученные деньги — это **денежная дебиторка** (нам должны деньги); если деньги получены вперёд — **неденежная кредиторка** (мы должны исполнение). Зеркально для поставщиков. Новых сущностей не требуется.
**UI/UX:** Колонки «Дебиторка» и «Кредиторка» на экранах клиентов и поставщиков, каждая с двумя подколонками «деньги» и «исполнение»; фильтр в панели. На главной блок «Деньги» дополняется строкой «авансы получены / авансы выданы».
**Frontend:** `containers/Customers/CustomersLanding/v2/`, `Vendors/…`, `containers/Homepage/MoneySummarySection.tsx`.
**Backend:** Новый `src/modules/Contacts/queries/GetContactDebtBreakdown.service.ts`.
**API:** `GET /api/contacts/debt-breakdown?contactIds=&asDate=`; параметры фильтра в списках клиентов и поставщиков.
**Database:** Изменений нет.
**Business rules:** Классификация считается по одному контрагенту в целом, а не по документу: зачёт аванса против отгрузки выполняется до классификации. Черновики не учитываются.
**Acceptance Criteria:** (1) Сумма денежной и неденежной дебиторки равна нынешнему сальдо дебиторки — спека; (2) контрагент с авансом и отгрузкой на равные суммы показывает нули в обеих колонках; (3) фильтр «Без дебиторки» исключает контрагентов с ненулевой дебиторкой любой природы; (4) отчёты старения не изменились.
**Dependencies:** нет.
**Priority:** **P1**

### FIN-024 — «Оплачено, %» и «Отгружено, %» в сделках

**Название:** Прогресс сделки по деньгам и по исполнению
**Проблема:** Сделка показывает сумму и прибыль, но не показывает, насколько она закрыта.
**Цель:** Видно, где деньги пришли, а работа не сделана, и наоборот.
**Текущее состояние Bigfin:** `[CODE-CONFIRMED]` `containers/Deals/DealsPage.tsx` (228 строк): вкладки статусов, сводка, `DealProfitability`, стадии.
**Референс из ПланФакта:** `[OBSERVED]` Колонки «Поступило %» и «Отгружено %» в списке сделок.
**Предлагаемое решение Bigfin:** Две колонки-прогресса в списке сделок и два индикатора в карточке сделки. Отличие: при расхождении больше 20 процентных пунктов рядом появляется пометка «работа впереди денег» или «деньги впереди работы» — прямое указание на риск.
**UI/UX:** Тонкая полоска прогресса с числом справа; пометка — `badge` нейтрального тона.
**Frontend:** `containers/Deals/` — колонки и карточка.
**Backend:** `src/modules/Deals/queries/` — поля `paidRatio`, `shippedRatio` в ответе списка.
**API:** Расширение `GET /api/deals`.
**Business rules:** «Оплачено» = поступления по сделке / сумма сделки; «Отгружено» = сумма подтверждённых отгрузок/актов / сумма сделки. Обе доли ограничены сверху 999 %, при превышении 100 % — пометка «переплата»/«перепоставка».
**Acceptance Criteria:** (1) Доли считаются от суммы сделки и отображаются целым процентом; (2) при нулевой сумме сделки — «н/о»; (3) пометка расхождения появляется ровно при разнице > 20 п.п.; (4) `@RequireFeature(Features.DEALS)`.
**Dependencies:** нет.
**Priority:** **P2**

### FIN-027 — Отраслевые демо-данные

**Название:** Выбор отрасли при создании демо-организации

## 7. Database Changes

Изменений **минимум**: три новые таблицы и одно расширение домена. Каждое обосновано тем, что существующая схема задачу не решает.

### D1 — Расширение домена `management_articles.kind`

**Таблица существует**, новая не нужна.

| | |
|---|---|
| Файл | `packages/server/src/database/tenant/migrations/2026MMDDHHMMSS_extend_management_articles_kind.ts` |
| Схема | **tenant** (статьи принадлежат организации) |
| Изменение | Домен `kind` расширяется с `{income, expense}` до `{income, expense, asset, liability, equity}` |
| Тип колонки | `string` — **не меняется**, меняется только валидация в коде и сид |
| Индексы | существующий индекс по `kind` сохраняется |
| Constraints | в MySQL CHECK-ограничения ненадёжны — домен закрывается `class-validator` в DTO плюс Jest-спекой, проверяющей, что в сиде нет посторонних значений |
| Данные | существующие строки не трогаются |
| `down()` | обратная миграция переводит статьи новых видов в `expense` и пишет предупреждение в лог; **разрушение данных документируется в комментарии миграции** |
| Влияние | нулевое для существующих организаций до тех пор, пока пользователь не создаст статью нового вида |

Дополнительно — **догоняющая миграция сида**: `2026MMDDHHMMSS_seed_balance_articles.ts` добавляет в существующие организации системные статьи видов `asset`, `liability`, `equity` (получение и погашение кредита, покупка и продажа основных средств, взнос и изъятие собственника, выданные и полученные займы). Миграция идемпотентна: проверяет наличие статьи по устойчивому ключу, а не по имени.

⚠️ **Обязательно** использовать помощник `schemaAnyCase` при проверке существования таблиц и колонок — прямые `hasTable`/`hasColumn` в этом проекте уже приводили к молча не сработавшей миграции (карта `2026-09-19-finish-the-product.md`, дефект П3), и это закреплено сторожем `noRawSchemaExistenceChecks.spec.ts`.

### D2 — Карта отчётов: новой таблицы НЕ создаём

Рассмотрено и **отклонено**: таблица `article_report_map` со строками «статья → строка отчёта». Причина отказа: карта полностью выводится из `kind`, `cashflow_section` и корневых типов счетов, привязанных через `management_article_accounts`. Хранить производное — значит завести второй источник правды и гарантированно получить расхождение схемы с отчётом. Карта считается на лету и кэшируется в Redis на время жизни запроса.

Не миграция, а данные ролей: новое значение `ReportsAction.READ_CASHFLOW_ARTICLES` добавляется в `src/modules/FinancialStatements/types/Report.types.ts` и в `src/modules/Roles/AbilitySchema.ts` с парными i18n-ключами. ```

Комментарий в миграции обязан объяснить, какой запрос он ускоряет и на каком объёме замерено. Существующий файл `20260818200000_hot_query_composite_indexes.ts` задаёт образец такого комментария.

### D7 — Чего мы НЕ делаем

- **Не добавляем вторую дату в денежную операцию.** Разбор в FIN-003: двойная запись привязана к одной дате проводки; вторая дата потребовала бы либо двух проводок, либо даты «вне журнала», и то и другое ломает сходимость.
- **Не заводим таблицу дебиторки/кредиторки.** Это производное от документов (FIN-023).
- **Не заводим таблицу разрывов.** Прогноз считается на лету и кэшируется (FIN-007).
- **Не трогаем `parent_account_id`** — группы счетов идут отдельной колонкой (D4).

### 10.2. Правила для новых элементов

**Спарклайн (`components/ui/sparkline.tsx`).** Размер по умолчанию 88×20, линия 1.5 px, цвет `rgb(var(--c-action))`, без заливки, без точек. Нулевая линия не рисуется. Подсказка при наведении — `tooltip` с минимумом и максимумом и их месяцами. Рендер — inline-SVG; **библиотека графиков для спарклайнов не используется** (300 строк × recharts недопустимо по скорости).

**Бейджи состояния (`badge`).** Четыре варианта: «просрочено» — `danger` (заливка 10 %, текст `--c-danger`); «нам должны», «мы должны», «план» — контурные, текст `--c-muted`, граница `--c-border`. Высота 20 px, радиус 6 px, 12/500, без иконок. Максимум два бейджа в строке; третий сворачивается в «+1» с подсказкой.

**Точка состояния счёта.** Круг 8 px: `success` — разрыва нет; `warning` — разрыв дальше 14 дней; `danger` — ближе или уже начался. Точка **никогда не единственный носитель смысла** — рядом всегда есть текст или подсказка (требование доступности; аддон a11y в Storybook включён).

**Подсветка в схеме статей.** Фон `rgb(var(--c-accent) / 0.15)` плюс левая планка 3 px цветом `--c-accent`. **Не менять цвет текста** — жёлтый бренд на тексте нечитаем, а красный/зелёный конфликтуют с правилом «расход не красный».

**Полоски прогресса (бюджет, сделки).** Высота 6 px, радиус 3 px, фон `--c-muted-surface`, заливка `--c-action`; полоска времени — `--c-border`. Число процентов справа, `tabular-nums`, 13/500.

## 11. Financial Logic

Формулы и правила для всех показателей, затронутых настоящим ТЗ. Формат: **Название → Формула → Источники данных → Период → Фильтры → Edge cases → Drill-down.**

Общие соглашения:

- Валюта расчёта — валюта учёта организации (`organization.base_currency`, по умолчанию `RUB`). Пересчёт — `ExchangeRatesService`, курс на дату операции; при отсутствии курса строка попадает в «не пересчитано» и показывается отдельно, **никогда не отбрасывается молча**.
- Денежные счета — типы из `CASH_ACCOUNT_TYPES` (`src/modules/Budgets/constants.ts`).
- Допуск сходимости — 0.005 (полкопейки), как в `Ledger.ts:57-59`. Расхождение больше — ошибка расчёта, а не округление.
- «Рассчитано деньгами» — документ, чьи проводки затрагивают денежный счёт; список ключей — `src/modules/Budgets/utils/cashSettledReferenceKeys.ts`.

### 11.1. Остаток на счетах

**Формула.**
```
Остаток(счёт, дата) = Σ по accounts_transactions(account_id = счёт, date ≤ дата) от
                      ( debit − credit ),      если нормаль счёта = debit
                      ( credit − debit ),      если нормаль счёта = credit
Остаток(организация, дата) = Σ Остаток(счёт, дата) × курс(валюта счёта, дата)
                             по всем счетам денежных типов
```
**Источники.** `accounts_transactions`, `accounts.account_type`, `ACCOUNT_NORMAL` из `src/constants/accounts.ts`, `exchange_rates`.
**Период.** Точка, не интервал: остаток на дату.
**Фильтры.** Юрлицо (`legal_entity_id`), группа счетов, тип счёта, отделение.
**Edge cases.** Счёт в валюте, отличной от базовой, — `getForeignClosingBalance()` (`LedgetAccountStorage.service.ts:113-139`). Счёт без операций — ноль, не пусто. Отрицательный остаток допустим (овердрафт, касса «в минусе» из-за ошибки разноски) и печатается красным.
**Drill-down.** По счёту, режим `balance`: «остаток на начало + оборот = остаток на конец».

### 11.2. Чистый денежный поток и ДДС прямым методом (FIN-013)

**Формула.**
```
Поток(статья, период) = Σ ( сумма проводки ) по операциям, где:
    – проводка затрагивает денежный счёт,
    – документ входит в cashSettledReferenceKeys,
    – счёт второй стороны привязан к статье через management_article_accounts,
    – операция не является переводом между своими счетами,
    – (в сводном режиме) операция не помечена is_intercompany

Поступления(раздел, период) = Σ Поток(статья, период) по статьям раздела, где сумма > 0
Выплаты(раздел, период)     = Σ |Поток(статья, период)| по статьям раздела, где сумма < 0
Поток(раздел)               = Поступления(раздел) − Выплаты(раздел)
Чистый поток                = Поток(operating) + Поток(investing) + Поток(financing)

Остаток на конец = Остаток на начало + Чистый поток
```
Раздел определяется полем `management_articles.cashflow_section`.
**Источники.** `ArticlesCashflowRollupService`, `accounts_transactions`, `management_article_accounts`, `management_articles`.
**Период.** Интервал; масштаб день / неделя / месяц / квартал / год / итого.
**Фильтры.** Юрлица, направления, отделения, контрагенты, счета.
**Edge cases.**
- **Переводы между своими счетами** дают две проводки с противоположными знаками; оба вычитаются из потоков и показываются отдельным блоком с нулевым итогом. Если итог блока не ноль — это дефект разноски, и блок это показывает.
- **Статья не назначена** — сумма попадает в строку «Без статьи»; строка **обязана быть видимой**, иначе итог не сойдётся с остатком.
- **Операция в валюте** пересчитывается по курсу даты; строка «не пересчитано» показывается отдельно.
- **Внутригрупповые обороты** исключаются только в сводном режиме (`legalEntityIds` пуст); при выборе одного юрлица они остаются, иначе баланс этого юрлица не сойдётся.
**Drill-down.** По статье (FIN-004); итог списка = значение строки.

### 11.3. Прибыль и рентабельность (ОПиУ)

**Формула (метод начисления).**
```
Выручка            = Σ оборотов по счетам с корневым типом income, привязанным
                     к статьям вида income, за период
Основные расходы   = Σ оборотов по счетам expense, привязанным к статьям
                     вида expense с cost_behavior = variable ∪ прямым расходам
Операционная прибыль          = Выручка − Основные расходы − Операционные расходы
Операционная рентабельность,% = Операционная прибыль / Выручка × 100

EBITDA  = Операционная прибыль + Амортизация
EBIT    = EBITDA − Амортизация                       (= Операционная прибыль)
EBT     = EBIT + Прочие доходы − Прочие расходы − Проценты по кредитам
Чистая прибыль = EBT − Налог на прибыль
Рентабельность чистой прибыли, % = Чистая прибыль / Выручка × 100
Нераспределённая прибыль = Чистая прибыль − Дивиденды
```
**Формула (кассовый метод).** Те же строки, но в основу берутся только проводки документов, рассчитанных деньгами (существующий `ProfitLossSheetCashBasis`). Переключение — параметр `basis`.
**Источники.** `accounts_transactions`, план счетов, `management_articles`, `dividend_payouts`, `fixed_asset_depreciation_entries`.
**Период.** Интервал; колонки — периоды, направления или сделки (FIN-014).
**Фильтры.** Юрлица, направления, сделки, отделения, метод учёта.
**Edge cases.**
- **Выручка = 0** → все рентабельности печатаются как **«н/о»**, не «0 %» и не «∞». Это прямое наблюдение у конкурента `[OBSERVED]` и правильное решение.
- **Отрицательная выручка** (возвраты превысили продажи) → рентабельность считается, но помечается подсказкой «выручка отрицательна, показатель трудно интерпретировать».
- **Нет статей амортизации** → EBITDA равна операционной прибыли, рядом подсказка «амортизация не учитывается: нет операций этого вида».
- **Разрез по направлениям:** операции без направления собираются в колонку «Без направления»; сумма колонок = «Итого».
**Drill-down.** По строке отчёта: по статье (если строка — статья) или по счёту (если строка — группа плана счетов).

### 11.4. Кассовый разрыв (FIN-007)

**Формула.**
```
Для счёта A и горизонта H дней:
  B[0]   = Остаток(A, сегодня)
  B[d]   = B[d−1] + Σ Приток(A, день d) − Σ Отток(A, день d),  d = 1..H

  где приток/отток дня d складывается из:
    – плановых операций (planned_operations) со status ∈ {planned, confirmed}
      и planned_date = d, account_id = A, развёрнутых по recurrence;
    – неоплаченных счетов покупателям (sales_invoices.balance > 0)
      с due_date = d — как приток;
    – неоплаченных счетов поставщиков (bills.balance > 0)
      с due_date = d — как отток.

  Разрыв = максимальный по включению интервал [from..to], в котором B[d] < 0
  from = первый день интервала
  to   = последний день интервала (null, если B не вернулся в ≥ 0 до конца H)
  deepestAmount = |min B[d]| внутри интервала
  deepestDate   = день, где достигнут минимум
```
**Источники.** `accounts_transactions` (для `B[0]`), `planned_operations`, `sales_invoices`, `bills`, `exchange_rates`.
**Период.** Горизонт H, по умолчанию 90 дней, максимум 365.
**Фильтры.** Счёт, юрлицо.
**Edge cases.**
- **Плановая операция без счёта** не участвует в разрезе по счетам; их число возвращается полем `unassignedPlannedCount`, и интерфейс об этом сообщает.
- **Разрыв уже начался** (`B[0] < 0`) — `from` в прошлом; показывается, только если включена настройка «показывать прошедшие разрывы» (по умолчанию включена).
- **Несколько провалов** — возвращаются все интервалы; в шапке показывается ближайший.
- **Повторяющаяся операция** разворачивается `expandRecurrence.ts`; разворот ограничен горизонтом H.
- **Валюта счёта ≠ валюты учёта** — прогноз строится в валюте счёта, а в виджет отдаётся пересчёт на сегодня; при отсутствии курса — «прогноз недоступен: нет курса на дату».
**Drill-down.** День разрыва → операции дня (FIN-020).

### 11.5. Состояние операции (FIN-003)

**Правила.**
```
нам должны  ⟺ есть связанный SaleInvoice со status ≠ draft и balance > 0
мы должны   ⟺ есть связанный Bill со status ≠ draft и balance > 0
просрочено  ⟺ (нам должны ∨ мы должны) ∧ due_date < сегодня
            ∨ (source = planned ∧ status = planned ∧ planned_date < сегодня)
план        ⟺ source = planned ∧ ещё не материализована
```
**Источники.** `sales_invoices`, `bills`, `planned_operations`.
**Edge cases.** Частичная оплата — состояние «нам должны» с остатком, а не полной суммой. Черновик состояний не порождает. Материализованная плановая операция теряет состояние «план».

### 11.6. Денежная и неденежная задолженность (FIN-023)

**Формула.**
```
Для контрагента C на дату D:
  ОтгруженоПодтв  = Σ сумм подтверждённых отгрузок/актов/счетов (не черновики)
  ПолученоДенег   = Σ поступлений от C
  ОплаченоНами    = Σ выплат в адрес C
  ПолученоТоваров = Σ сумм подтверждённых поставок/актов от C

  Дебиторка денежная   = max(0, ОтгруженоПодтв − ПолученоДенег)
  Кредиторка товарная  = max(0, ПолученоДенег − ОтгруженоПодтв)   // аванс от клиента
  Кредиторка денежная  = max(0, ПолученоТоваров − ОплаченоНами)
  Дебиторка товарная   = max(0, ОплаченоНами − ПолученоТоваров)   // аванс поставщику
```
**Edge cases.** Контрагент одновременно клиент и поставщик — считаются обе пары независимо, зачёт между ними **не выполняется** (это разные договоры). Равные аванс и отгрузка дают нули во всех четырёх колонках.

### 11.7. План-факт и «прошло времени» (FIN-021, FIN-022)

**Формула.**
```
План(статья, период, сценарий) = Σ budget_lines.planned_amount
Факт(статья, период)           = ArticlesPlRollup   (для БДР)
                               | ArticlesCashflowRollup (для БДДС)

Выполнение, %       = Факт / План × 100                     (План = 0 → «н/о»)
Отклонение (доход)  = Факт − План
Отклонение (расход) = План − Факт
Отклонение, %       = Отклонение / |План| × 100             (План = 0 → «н/о»)

Прошло времени, %   = (min(сегодня, конец) − начало) / (конец − начало) × 100
                      в календарных днях; период завершён → 100 %
```
**Edge cases.** План задан и на группу статей, и на дочернюю — двойной счёт исключается существующей защитой в `GetReportPlanFact.service.ts`. План отрицателен (редко, но возможно для статей вида «возврат») — знаменатель берётся по модулю.
**Вывод словами.** Если |Выполнение − Прошло времени| ≤ 5 п.п. — «идём по плану». Для расходов при Выполнение > Прошло времени + 5 — «тратим быстрее плана». Для доходов при Выполнение < Прошло времени − 5 — «отстаём от плана».

### 11.8. Парето по контрагентам (FIN-018)

**Формула.**
```
Выручка(контрагент, период) — тем же методом учёта, что и ОПиУ
Сортировка по убыванию; топ-10 + строка «Остальные»
Накопительная доля[i] = Σ(j ≤ i) Выручка[j] / Σ Выручка × 100
Порог концентрации: k = минимальное i, при котором Накопительная доля[i] ≥ 80
Вывод словами:
  k ≤ 3           → «Более 80 % выручки дают {k} клиентов — высокая зависимость»
  4 ≤ k ≤ 8       → «Более 80 % выручки дают {k} клиентов»
  k > 8           → «Выручка распределена равномерно»
```
**Edge cases.** Нулевая выручка за период — блок не показывается. Один контрагент — вывод «Вся выручка от одного клиента».

---

### 11.9. Прогресс сделки (FIN-024)

```
Оплачено, %  = Σ поступлений по сделке / Сумма сделки × 100
Отгружено, % = Σ подтверждённых отгрузок по сделке / Сумма сделки × 100
Сумма сделки = 0 → обе доли «н/о»
Доля > 100 % → пометка «переплата» / «перепоставка», значение показывается как есть
|Оплачено − Отгружено| > 20 п.п. → пометка «деньги впереди работы» либо «работа впереди денег»
```

---

### 11.10. Инварианты, обязательные к проверке тестами

1. `Остаток на начало + Чистый поток = Остаток на конец` — ДДС по статьям.
2. `Активы = Обязательства + Капитал` — Баланс (существующая проверка сохраняется).
3. `Итог раскрытия = Сумма в отчёте`, допуск 0.005 — для любой раскрываемой строки любого отчёта.
4. `Σ колонок по направлениям = колонка «Итого»`, включая «Без направления».
5. `Σ inflow − Σ outflow = net` — сводная строка реестра.
6. `Σ остатков по группам счетов = общий остаток` — виджет денег.
7. `Дебиторка денежная + Дебиторка товарная` не противоречит нынешнему сальдо контрагента.
8. Сумма строки статьи в отчёте = сумме той же статьи в схеме FIN-002 за тот же период.
9. Итог блока «Переводы между своими счетами» = 0.
10. Сводный режим по группе юрлиц = Σ по юрлицам − внутригрупповые обороты.

## 12. Implementation Plan

- Миграции — с рабочим `down()`, проверенным циклом `latest → rollback → latest` на живой базе стенда.

## 14. Testing Strategy

Проект держится на 586 файлах спек и ~3438 проверках, из которых заметная часть — **сторожевые спеки**, проверяющие инварианты кода, а не поведение. Это сильная сторона, и новая работа должна её продолжать, а не размывать. Одновременно проект уже получил урок: живой проход нашёл пять дефектов, которых не видели все эти тесты (`docs/design/2026-09-19-ux-redesign-plan.md`). Поэтому стратегия двухслойная: машина проверяет сходимость и инварианты, человек — понятность.

### 14.2. Financial calculation tests — отдельный обязательный набор

Это главный слой. Каждый из **десяти инвариантов раздела 11.10** получает спеку в `src/modules/FinancialStatements/convergence/`, прогоняемую на трёх подготовленных наборах данных:

- **Набор А — одно юрлицо, одна валюта, без проектов.** Базовая сходимость.
- **Набор Б — два юрлица с внутригрупповыми оборотами, направления, переводы между счетами.** Консолидация и исключения.
- **Набор В — две валюты, один курс отсутствует, часть операций без статьи и без направления.** Граничные случаи и «не пересчитано».

Требования к набору: фиксированные данные в фикстурах, **фиксированная «сегодняшняя» дата** (иначе спеки про разрывы и «прошло времени» станут плавающими), суммы с копейками, чтобы ловить ошибки округления.

Правило: расхождение больше 0.005 — **падение теста**, а не предупреждение. Расхождение меньше — тоже проверяется: инвариант «ровно ноль» (блок переводов) сравнивается с нулём точно.

## Рекомендуемый порядок реализации

Последовательность выстроена по техническим зависимостям: **данные → расчёт → ручка → экран**. Интерфейс не делается раньше модели, которая его кормит. Номера задач — из раздела 13.

### Волна 1 — фундамент (ничего не видно пользователю, всё зависит от этого)

```
T-01  SDK перегенерирован
  └→ T-02  ArticlesCashflowRollup / ArticlesPlRollup переехали в ManagementArticles
T-03  computeRunningBalance → массив интервалов разрыва
T-04  примитив sparkline
```
Почему первым: T-02 нужен этапу ДДС, T-03 — виджету денег, T-01 — вообще всему, что трогает API. T-03 и T-04 независимы и делаются параллельно с T-01/T-02.

### Волна 2 — статьи (модель, без которой не существует ни отчёта, ни схемы)

```
T-05  миграция домена kind
  ├→ T-06  догоняющий сид балансовых статей
  ├→ T-07  валидация совместимости счёта и вида
  ├→ T-08  вкладки и форма статьи
  └→ T-09  балансовые статьи не попадают в ОПиУ
```
Почему до отчёта: отчёт ДДС по статьям группирует по виду статьи. Сделать отчёт раньше — значит переписать его после.

### Волна 3 — главный отчёт (первая видимая ценность)

```
T-10  подмодуль CashFlowArticles (сервер, 5 форматов)
  ├→ T-11  право read-cashflow-articles
  ├→ T-12  экран отчёта
  │    └→ T-13  пункты меню и витрины отчётов
  └→ T-14  согласовать график и таблицу
```
Почему здесь: это первый этап, после которого владелец видит результат и может дать обратную связь до того, как в ту же логику вложено ещё шесть этапов.

### Волна 4 — раскрытие (то, без чего отчёту не верят)

```
T-15  articleId в GetReportDrillDown
  ├→ T-16  колонки статьи/направления/сделки в панели
  └→ T-17  фильтры articleId/projectId/legalEntityIds в реестре
        └→ T-18  «Открыть в Операциях» + строка контекста
```
Почему после отчёта: раскрытие нужно проверять на реальных строках нового отчёта; итог обязан совпадать, и проверить это можно только когда есть с чем совпадать.

### Волна 5 — схема статей (объяснение)

```
T-19  GetArticleReportMap (сервер)
  └→ T-20  три карточки схемы
        └→ T-21  вкладка «Куда попадает» на телефоне
```
Почему после раскрытия: клик по подсвеченной строке схемы уводит в отчёт с фильтром — механизм из волны 4.

### Волна 6 — деньги на виду

```
T-22  GetMoneyWidget + кэш          ─┐
T-24  GetAccountsCashGaps            ├→ T-23  виджет в шапке
                                     │     └→ T-25  строки счетов с датой разрыва
                                     │           └→ T-26  группы счетов (миграции + CRUD)
                                     │                 └→ T-27  вкладки «По группам»/«По юрлицам»
```
Почему не раньше: T-22 и T-24 опираются на T-03 из волны 1. Группы счетов идут последними в волне, потому что без виджета их негде показывать.

### Волна 7 — реестр операций

```
T-28  resolveTransactionState
  ├→ T-29  бейджи в таблице и карточке
  ├→ T-32  фильтр по состоянию + счётчик фильтров
  └→ T-33  группировка «Будущие/Сегодня/Ранее» + планы
T-30  ручка transactions/summary
  └→ T-31  нижняя сводная строка
```
Почему после волны 4: фильтр по статье в реестре (T-17) — предпосылка для осмысленной работы с реестром.

### Волна 8 — отчёты вглубь

```
T-35  ReportControlBar (единая шапка)
  ├→ T-36  разрез по направлениям и сделкам
  │     └→ T-39  замер и, при нужде, индекс (project_id, date)
  ├→ T-37  ярусы прибыли
  └→ T-38  колонка «Тренд»            (требует T-04)
```
Почему T-35 первым в волне: три остальных вешаются на эту шапку. Сделать их до неё — значит трижды переставить органы управления.

### Волна 9 — планирование

```
T-40  масштабы и источники календаря   (требует T-35 для единого вида шапки)
  ├→ T-41  «На сегодня»
  └→ T-42  раскрытие клетки            (требует T-15)
T-45  таблица и раздел личных настроек
  ├→ T-34  настройка колонок реестра
  └→ T-43  чекбоксы колонок план-факта
        └→ T-44  «Прошло времени, %»
```
T-45 идёт раньше своих зависимых, хотя сам помечен P2: без него настройки некуда сохранять.

### Волна 10 — аналитика и понятность

```
T-46  Парето по контрагентам   ─┐
T-47  прибыльность направлений  ├→ T-48  оба блока в одном запросе overview
T-49  GetContactDebtBreakdown
  └→ T-50  колонки и фильтр в списках контрагентов
T-51  прогресс сделки
T-52  ScreenHelp + словарь + сторож
```
Волна независима от предыдущих и может идти параллельно волнам 8–9, если работают два исполнителя.

### Волна 11 — обучение и приёмка

```
T-53  три отраслевых демо-набора   (требует T-05)
  └→ T-54  вопрос об отрасли в мастере
T-55  расширить e2e и testMatch
T-56  набор спек сходимости         (требует T-10, T-15)
T-57  регрессия «золотых» ответов   (требует T-15, T-17)
T-58  ключи en+ru для всего нового
```
T-56 и T-57 формально идут последними в списке, но **пишутся вместе с соответствующими волнами**, а не откладываются: спека сходимости для ДДС пишется в волне 3, для раскрытия — в волне 4. В этой волне они только сводятся в единый прогон.

### Что можно делать параллельно

При двух исполнителях:

| Поток A (модель и отчёты) | Поток B (интерфейс и аналитика) |
|---|---|
| Волна 1 (T-01, T-02) | Волна 1 (T-03, T-04) |
| Волна 2 (статьи) | Волна 6 (виджет денег — зависит только от T-03) |
| Волна 3 (отчёт ДДС) | Волна 6 (группы счетов) |
| Волна 4 (раскрытие) | Волна 7 (реестр) |
| Волна 5 (схема) | Волна 10 (Парето, задолженность, справка) |
| Волна 8 (отчёты вглубь) | Волна 9 (планирование, настройки) |
| Волна 11 (сведение тестов) | Волна 11 (демо-наборы) |

### Чего нельзя делать в другом порядке

1. **Экран раньше ручки.** Ни один из перечисленных экранов не делается «на моках» — в проекте есть сторож `hooks/query/apiPathsExistOnServer.spec.ts`, и он покраснеет.
2. **Отчёт раньше статей.** ДДС по статьям группирует по `kind`; без пяти видов он соберётся неправильно и будет переписан.
3. **Раскрытие раньше отчёта.** Инвариант «итог = сумме в отчёте» непроверяем, пока отчёта нет.
4. **Группы счетов раньше виджета.** Показывать группы негде.
5. **Колонки и ярусы раньше личных настроек (T-45).** Выбор будет некуда сохранять, и придётся делать дважды.
6. **Единая шапка после разрезов и трендов.** Органы управления придётся переставлять трижды.

## Приложение А. Чего в этом ТЗ сознательно нет

Список отклонённых идей — чтобы к ним не возвращались.

1. **Вторая дата у денежной операции.** Решение ПланФакта элегантно, но у него нет двойной записи. В Bigfin проводка привязана к одной дате; вторая дата потребовала бы либо двух проводок, либо даты вне журнала — и то и другое ломает сходимость, которую охраняет `assertBalanced()`. Те же пользовательские задачи решены через FIN-003 (состояние из документов) и FIN-010 (планы в реестре).
2. **Отдельная таблица дебиторки и кредиторки.** Производное от документов; хранить — значит завести второй источник правды.
3. **Таблица «статья → строка отчёта».** То же самое: карта выводится из вида статьи, раздела ДДС и типов привязанных счетов (D2).
4. **Массовая миграция Blueprint → shadcn.** Прямой запрет ЧАСТИ G прежнего ТЗ; граница закрыта сторожем и может только уменьшаться.
5. **Одиннадцать отраслевых демо сразу.** Три набора закрывают большинство случаев; остальные — по спросу.
6. **Курс по финучёту, вебинары, партнёрская программа.** Это маркетинг, а не продукт.
7. **Новые разделы меню.** Восемь пунктов остаются восемью.
8. **ИИ сверх уже существующего.** `AiAnalyst` и `AiChat` в проекте есть, за выключенным флагом, с жёсткими ограничениями §13.1 прежнего ТЗ (модель не считает цифры; сырые операции, реквизиты и ФИО наружу не уходят). Настоящее ТЗ к ним не прикасается: продукту сейчас не хватает не ИИ, а входа в то, что уже есть.

## Приложение Б. Что исполнитель обязан проверить сам перед работой

Помечено в тексте как «требует проверки». Собрано в одном месте:

1. **Гранулярность платёжного календаря.** По коду виден дневной вид (`DayRow.tsx`); поддерживаются ли недели, месяцы, кварталы и годы — проверить перед FIN-019, чтобы не делать заново сделанное.
2. **Измерения в `transaction_splits`.** По каким именно измерениям сейчас разбивается операция — проверить перед оценкой объёма FIN-008-подобной задачи (в настоящем ТЗ разбиение вынесено за скобки как уже существующее).
3. **Архивные признаки справочников.** Есть ли `active` у направлений, контрагентов, статей — перед FIN-023 и фильтрами архива.
4. **Текущее поведение `ReportDrillDownPanel`** в каждом из трёх отчётов, где он подключён, — чтобы расширение не изменило поведение двух остальных.
5. **Наличие индекса по `project_id`** в `accounts_transactions` — перед FIN-014; при отсутствии сначала замер, потом решение об индексе (D6).
6. **Актуальность `docs/tz/STATE.md`** — шаг 0 из `docs/tz/CONTINUE.md`: `git fetch --all --prune`, `gh pr list --state all`, чтение STATE целиком. Без этого отчёт о состоянии будет фантазией.
