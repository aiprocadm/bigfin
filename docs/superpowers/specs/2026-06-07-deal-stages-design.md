# ㉘ — Этапы сделки (поэтапное признание прибыли)

**Дата:** 2026-06-07
**Под-проект роадмапа:** ㉘ (Ф3a), §126 «Этапы сделки».
**Зависит от:** ⑦a Сделки (смержено, PR #57), `ArticlesPlRollupService`, `computeDealMargin`, измерение `projectId`.
**Флаг:** `Features.DEAL_STAGES` (по умолчанию **off**, отдельно от `deals`).
**Подход (одобрен основателем 2026-06-07):** признание по **плановой сумме этапа** на стороне отчёта; масштаб v1 — **в карточке сделки** (Подход 3: узко сейчас, с заделом на режим в общем ОПиУ позже без переделок).

---

## 1. Зачем (проблема)

Сегодня выручка/расходы сделки (`GetDealProfitabilityService` + `computeDealMargin`) = свёртка ОПиУ по статьям, отфильтрованная по `projectId` сделки и просуммированная **по дате операции** за период. То есть прибыль «появляется» в момент проводки (счёт/расход).

Для длинных сделок (ремонт, внедрение, стройка) предпринимателю нужно видеть прибыль **поэтапно — по факту закрытия этапа**, а не всей сделкой целиком и не по дате денег. Пример: ремонт 500 000 ₽ = «Проект» (100 000) + «Стройка» (400 000); «Проект» закрыт в марте, хотя клиент платит в мае — 100 000 должны «признаться» в марте.

㉘ это закрывает: сделка делится на этапы с плановыми суммами; закрытие этапа признаёт его план в месяце закрытия; виден прогресс и план/факт.

## 2. Ключевой принцип — признание на стороне отчёта

Признание **считается при построении отчёта, проводок в книгу не пишется** (зеркалит ⑦b и тумблер метода ⑤/㉙). Следствия:
- Флаг/этап можно выключить — отчёт мгновенно «как было», без миграции данных.
- Журнал/книга бухгалтера не трогаются — фактические операции остаются исходными.
- Прямо снижает риск «неожиданных цифр» (риск №15 роадмапа): признание по этапам — отдельный управленческий взгляд, а не подмена факта.

## 3. Объём первой версии

**Входит:**
- Тенантная таблица `deal_stages` (этапы сделки).
- У этапа: **плановая выручка** и **плановые прямые расходы** (задаёт пользователь), статус `open`/`closed`, дата закрытия, порядок.
- CRUD этапов + действие «закрыть этап» (статус + дата) за флагом `DEAL_STAGES`.
- Чистая функция признания: закрытые этапы → признанные суммы по месяцам.
- По сделке: **план** (Σ всех этапов), **признано** (Σ закрытых), **прогресс** (% по плановой выручке), **план/факт** (план этапов vs фактические операции сделки из ⑦a).
- Фронт: секция «Этапы» на странице сделки (список, добавить/изменить/удалить/закрыть, прогресс, «признано по этапам», план/факт).

**НЕ входит (явно отложено):**
- Признание по **проценту готовности от затрат** (percentage-of-completion) — v2.
- **Шаблоны этапов** по типам сделок — v2.
- Привязка конкретных операций к конкретным этапам — факт берётся по сделке целиком (per-stage факт — v2).
- Режим «по признанию этапов» в **общем ОПиУ** компании — НЕ строим в v1, но модель данных и чистая функция признания проектируются так, чтобы добавить его позже без переделок (задел Подхода 3).
- История версий/аудит изменений этапа; переоткрытие разрешено (статус → `open`), но без журнала изменений.

## 4. Модель данных — тенантная таблица `deal_stages`

Миграция в `packages/server/src/database/tenant/migrations/` (стиль `exports.up/down`, как `cost_allocation_rules`/`payment_requests`). **Additive.**

| Колонка | Тип | Назначение |
|---|---|---|
| `id` | increments | PK |
| `deal_id` | int unsigned, FK → `projects.id`, index | Сделка (модель `Deal` живёт на таблице `projects`) |
| `name` | string | Название этапа, напр. «Проект» |
| `sort_order` | int, default 0 | Ручной порядок этапов |
| `planned_revenue` | decimal(15,2), default 0 | Плановая выручка этапа |
| `planned_cost` | decimal(15,2), default 0 | Плановые прямые расходы этапа |
| `status` | string, default `'open'` | `'open'` \| `'closed'` |
| `closed_date` | date, nullable | Дата закрытия (период признания) |
| `created_at`/`updated_at` | timestamps | — |

Модель `DealStage` (objection, наследует `TenantBaseModel`, `tableName = 'deal_stages'`), зарегистрировать в `Tenancy.module.ts` (как `Deal`/`CostAllocationRule`). Модификатор `closed(query)` → `where('status','closed')`.

## 5. Логика признания (чистые функции, тестируемые)

`modules/Deals/utils/recognizeStages.ts` (чистые, без зависимостей → юнит-тесты, как `computeDealMargin`/`allocatePool`):

```
recognizeStagesByPeriod(stages): Record<period 'YYYY-MM', { revenue, cost, profit }>
```
- Берёт только `status === 'closed'` с непустой `closed_date`; группирует по месяцу `closed_date`; суммирует `planned_revenue`/`planned_cost`; `profit = revenue − cost`.

```
summarizeDealStages(stages, actual): DealStagesSummary
```
- `planned` = Σ всех этапов (`revenue`, `cost`, `profit`).
- `recognized` = Σ закрытых этапов.
- `progress` = `planned.revenue > 0 ? recognized.revenue / planned.revenue : 0` (доля 0..1, по плановой выручке).
- `byPeriod` = из `recognizeStagesByPeriod`.
- `planVsFact` = `{ planned, fact: actual }`, где `actual` — фактическая маржа сделки из `computeDealMargin` (передаётся аргументом; функция не лезет в БД).
- Край-кейсы: нет этапов → нулевая сводка, `progress = 0`; все открыты → `recognized` нулевой; переоткрытый этап (status `open`) в признание не входит.

**Задел (Подход 3):** `recognizeStagesByPeriod` принимает массив этапов и ничего не знает о конкретной сделке/странице, поэтому будущий режим «по признанию этапов» в общем ОПиУ сможет вызвать её по всем сделкам без переделки.

## 6. Серверная часть — внутри модуля `Deals`

Этапы тесно связаны со сделкой → не отдельный модуль, а файлы в `modules/Deals/`:

- `models/DealStage.model.ts`.
- `dtos/DealStage.dto.ts` (Create/Edit), `dtos/CloseStage.dto.ts` (или статус через Edit).
- `commands/CommandDealStageValidator.service.ts` (+ spec), `commands/{CreateDealStage,EditDealStage,DeleteDealStage}.service.ts`.
- `queries/GetDealStages.service.ts` — список этапов сделки + сводка (`summarizeDealStages`, переиспользует существующую фактическую маржу сделки).
- `utils/recognizeStages.ts` (+ spec).
- Контроллер: маршруты под сделкой — `GET/POST /deals/:dealId/stages`, `PUT/DELETE /deals/:dealId/stages/:stageId`. Расширить `DealsApplication`/`DealsController` (или новый под-контроллер) — зеркалить существующий стиль `Deals.controller.ts`.

**Валидатор** (`CommandDealStageValidator`):
- сделка (`deal_id`) существует;
- `name` непустое;
- `planned_revenue ≥ 0`, `planned_cost ≥ 0`;
- при закрытии (`status = 'closed'`) обязательна `closed_date`.

**Доступ:** изменение этапов = **как редактирование сделки** (этапы — операционные данные сделки, не финансовая настройка). Зеркалить guard/декоратор create/edit в `Deals.controller.ts` (подтвердить точный декоратор в плане), а не админ-онли `manage all` (это было для правил ⑦b).

## 12. Принятые решения и задел

**Решено (зафиксировано с основателем 2026-06-07):**
- Признание = **плановая сумма этапа** на стороне отчёта (не факт по операциям, не % готовности).
- Масштаб v1 = **карточка сделки**; общий ОПиУ не трогаем (Подход 3 — задел на будущее).
- **Прогресс** — по плановой выручке (не по числу этапов).
- Права на этапы = **как на сделку** (не админ-онли).
- **Отдельный флаг** `deal_stages`.
- Привязка операций к этапам — **не входит** (факт по сделке целиком).

**Задел Подхода 3:** чистая `recognizeStagesByPeriod` независима от сделки/страницы → будущий режим «по признанию этапов» в общем ОПиУ переиспользует её без переделок.

**Детали к уточнению в плане (не блокеры дизайна):**
- Точный декоратор прав create/edit в `Deals.controller.ts` (подтвердить, зеркалить для этапов).
- Точное место секции «Этапы» на странице сделки в вебаппе (найти контейнер сделки D-redesign).
