# ⑧a — Зарплаты и налоги на ФОТ: ядро (без KPI)

**Дата:** 2026-06-10
**Под-проект роадмапа:** ⑧ (Ф3a), разбит на ⑧a (это ядро) и ⑧b (KPI/бонусы — отдельный цикл, как ⑦a/⑦b).
**Зависит от:** ⑥ Платёжный календарь (`planned_operations`, смержен), модуль `Settings` (generic group/key/value), `ManagementArticles` (статьи для плановых операций — опционально).
**Флаг:** `Features.PAYROLL = 'payroll'` (по умолчанию **off**).
**Контекст решений (одобрены основателем 2026-06-10):**
- ⑬a/⑬b (мобильное) отложены — PWA не реализован, ⑧ идёт следующим;
- формы занятости v1: **штатные + ГПХ + самозанятые + ИП-подрядчики**;
- налоги **упрощённо + настройка** (без годовых накопленных баз);
- подход **A «Расчёт + календарь»** — без проводок в леджере.

---

## 1. Зачем (проблема)

ФОТ — обычно крупнейшая статья расходов малого бизнеса, но сегодня в Bigfin он существует только как ручные операции. Предприниматель не видит: сколько стоит сотрудник целиком (на руки + НДФЛ + взносы), сколько налогов с ФОТ платить в следующем месяце и когда. PlanFact/Fintablo закрывают это модулем «Зарплата».

⑧a даёт: справочник сотрудников, месячные начисления с авторасчётом НДФЛ/взносов, плановые оттоки в платёжном календаре (выплата + налоги) и сводку «Налоги к уплате».

## 2. Ключевой принцип — расчёт без проводок

Начисление **не пишет проводок в книгу** (зеркалит ⑦b/㉘): суммы налогов фиксируются в строках начисления, плановые оттоки попадают в платёжный календарь через `planned_operations` (механизм ㉔), а в ОПиУ расход появляется по факту оплаты — кассовый метод, дефолт продукта. Следствия:

- Выключение флага мгновенно убирает модуль, данные не мигрируются.
- Бухгалтерская книга не затронута — нулевой риск для существующих отчётов.
- Тумблер «метод начисления» (㉙) при появлении сможет опереться на даты начислений — задел, не работа v1.

## 3. Объём первой версии

**Входит:**
- Тенантные таблицы `employees`, `payroll_runs`, `payroll_run_lines`.
- Справочник сотрудников: ФИО, должность, тип занятости (`staff`/`gph`/`npd`/`ip`), оклад по умолчанию, активность.
- Начисление за месяц (один документ на месяц): строки по активным сотрудникам, оклад + премия − удержание → авторасчёт НДФЛ, взносов, «на руки», полной стоимости. Статусы `draft` → `approved` (и обратно).
- Чистые функции расчёта по типам занятости (включая режим МСП по взносам).
- Проведение → 3 плановых оттока в платёжном календаре (выплата / НДФЛ / взносы); возврат в черновик → их удаление.
- Сводка «Налоги к уплате» по месяцам года (из проведённых начислений).
- Настройки ставок в Settings group `payroll` (редактируемые, не хардкод — риск №3 роадмапа).
- Фронт: страница `/payroll` (вкладки «Начисления», «Сотрудники»), диалоги, настройки ставок.

**НЕ входит (явно отложено):**
- KPI/бонусы от показателей, план продаж менеджера, «ответственный менеджер» на сделке — **⑧b**.
- Годовые накопленные базы: прогрессивная шкала НДФЛ, предельная база взносов — v2 (решение «упрощённо»).
- Платёжная ведомость и РКО как печатные формы — позже, рядом с ②c.
- Травматизм отдельной ставкой (можно учесть, подняв общую ставку взносов в настройках).
- Аванс/две выплаты в месяц — одна дата выплаты на начисление; отчёты в ФНС/СФР — никогда (anti-scope ⑧).
- Проводки обязательств в Балансе (вариант B — отвергнут).

## 4. Модель данных — три тенантные таблицы

Миграции в `packages/server/src/database/tenant/migrations/` (стиль `payment_requests`/`deal_stages`), **additive**, с рабочим `down()`.

|---|---|---|

| `default_salary` | decimal(13,3), default 0 | Оклад/ставка по умолчанию |
| `active` | boolean, default true | Архивация вместо удаления при наличии строк |

| Колонка | Тип | Назначение |
|---|---|---|

| `period_month` | date, **unique** | Первое число месяца начисления |
| `pay_date` | date | Дата выплаты «на руки» |

### `payroll_run_lines`

| Колонка | Тип | Назначение |
|---|---|---|
| `id` | increments | PK |
| `run_id` | int unsigned, FK → `payroll_runs.id`, index, CASCADE | Начисление |
| `employee_id` | int unsigned, FK → `employees.id`, index | Сотрудник |
| `employment_type` | string | **Снапшот** типа на момент расчёта |
| `base_amount` | decimal(13,3), default 0 | Оклад |
| `bonus_amount` | decimal(13,3), default 0 | Премия |
| `deduction_amount` | decimal(13,3), default 0 | Удержание |
| `ndfl_amount` | decimal(13,3), default 0 | **Снапшот** расчёта НДФЛ |
| `contributions_amount` | decimal(13,3), default 0 | **Снапшот** взносов |
| `net_amount` | decimal(13,3), default 0 | «На руки» |

Принцип снапшота: налоги фиксируются в строке при сохранении; изменение ставок в настройках влияет только на последующие расчёты, история не «плывёт». Уникальность `(run_id, employee_id)` — один сотрудник один раз в начислении.

Модели objection (`Employee`, `PayrollRun`, `PayrollRunLine` ← `TenantBaseModel`) регистрируются в `Tenancy.module.ts`.

## 5. Расчёт (чистые функции `utils/`)

`computePayrollLine({ employmentType, base, bonus, deduction }, settings)`:

```
gross = base + bonus                          // налоговая база
staff | gph:
  ndfl          = round2(gross × ndflRate)            // удерживается ИЗ gross
  contributions = standard: round2(gross × contribRate)
                  msp:      round2(min(gross, mspThreshold) × contribRate
                                   + max(0, gross − mspThreshold) × mspRate)
npd | ip:
  ndfl = 0; contributions = 0
net       = gross − ndfl − deduction          // удержание после налогов
totalCost = gross + contributions
```

NaN-safe (паттерн ㉘): нечисловые входы → 0. Округление до копеек (2 знака). Отрицательные `net` допускаются (удержание больше начисления — пользователь увидит и поправит), но валидатор предупреждает.

`summarizeRun(lines)` → `{ totalGross, totalNdfl, totalContributions, totalNet, totalCost }`.

## 6. Настройки — Settings group `payroll`

Через существующий generic `PUT/GET /settings` (метабельное хранилище group/key/value), **новых эндпоинтов и таблиц не нужно**. Ключи и дефолты (применяются в коде при отсутствии ключа):

| Ключ | Дефолт | Смысл |
|---|---|---|
| `ndflRate` | `13` | Ставка НДФЛ, % |
| `contribMode` | `'standard'` | `'standard'` \| `'msp'` |
| `contribRate` | `30` | Базовая ставка взносов, % |
| `mspRate` | `15` | Ставка МСП на часть сверх порога, % |
| `mspThreshold` | `27093 × 1.5` | Порог МСП, ₽/мес (1,5×МРОТ 2026; редактируемый) |
| `payrollArticleId` | null | Статья для плановой выплаты (опционально) |
| `taxesArticleId` | null | Статья для плановых налогов (опционально) |

UI настроек — диалог «Ставки и взносы» на странице `/payroll` (не в глобальных Preferences — ближе к месту использования; права на запись настроек — стандартный `Preferences/Mutate`).

## 7. Связь с платёжным календарём

`ApprovePayrollRun` (транзакционно): статус → `approved` + создание до 3 плановых операций (`direction='outflow'`, `status='planned'`, `sourceType='payroll_run'`, `sourceId=run.id`, валюта базовая):

1. **Выплата сотрудникам** — `totalNet`, дата = `pay_date`, статья = `payrollArticleId`;
2. **НДФЛ** — `totalNdfl`, дата = 28-е месяца, следующего за `period_month` (ЕНП), статья = `taxesArticleId`;
3. **Взносы** — `totalContributions`, та же дата, та же статья.

Операции с нулевой суммой не создаются. `UnapprovePayrollRun`: статус → `draft` + удаление плановых операций по `sourceType+sourceId` (паттерн отвязки как в ㉔). Редактирование/удаление допустимо только в `draft`; удаление run каскадно удаляет строки.

## 8. API — модуль `Payroll`

По образцу `Debts`/`PaymentRequests`: `Payroll.module.ts`, application-фасад, контроллер(ы), commands/queries, DTO со swagger-аннотациями. Все эндпоинты за `AuthorizationGuard + PermissionGuard`; **запись — админ** (`@RequirePermission('manage', 'all')`, как ㉔/⑦b), чтение — авторизованный пользователь.

```
GET    /payroll/employees            ?activeOnly=
POST   /payroll/employees
PUT    /payroll/employees/:id
DELETE /payroll/employees/:id        // запрещено при наличии строк → архивация
GET    /payroll/runs                 ?year=
GET    /payroll/runs/:id             // с строками и итогами
POST   /payroll/runs                 // создаёт run + строки-заготовки по активным сотрудникам
PUT    /payroll/runs/:id             // pay_date, note, строки (только draft)
DELETE /payroll/runs/:id             // только draft
POST   /payroll/runs/:id/approve
POST   /payroll/runs/:id/unapprove
GET    /payroll/taxes-summary        ?year= // по месяцам: НДФЛ, взносы, итого (approved)
```

`CreatePayrollRun` пре-заполняет строки: активные сотрудники, `base = default_salary`, расчёт по текущим настройкам. Сервер **пересчитывает налоги сам** при каждом сохранении строк (клиентские суммы налогов не доверяются).

Серверная проверка флага не ставится на чтение (паттерн ⑦b — флаг гейтит UI); мутации тоже без проверки флага, безопасность обеспечивают права админа.

## 9. Фронт

- Роут `/payroll` в `routes/dashboard.tsx` за флагом `PAYROLL` (как `/debts`, `/payment-requests`).
- Страница `PayrollPage` (shadcn, как `PaymentRequestsPage`): вкладки **«Начисления»** и **«Сотрудники»** + кнопка «Ставки и взносы».
- «Начисления»: список по году (месяц, статус, итоги: на руки / НДФЛ / взносы / всего), действия: открыть, провести/в черновик, удалить (draft).
- Карточка начисления: таблица строк (сотрудник, оклад, премия, удержание → НДФЛ, взносы, на руки, стоимость — серые вычисленные колонки), итоги, дата выплаты. Редактирование только в draft.
- «Сотрудники»: список (ФИО, должность, тип занятости, оклад, статус), диалог создания/редактирования (React Hook Form + Zod, как `RepaymentPlanDialog`).
- Блок «Налоги к уплате» на вкладке «Начисления»: текущий год по месяцам.
- Хуки `hooks/query/payroll.tsx` (react-query, инвалидация по образцу `paymentRequests.tsx`).
- i18n: ключи `payroll.*` парно en+ru, `node packages/webapp/scripts/lang-check.js` после правок. Термины: «начисление», «на руки», «взносы», «удержание» (не кальки).

## 10. Ошибки и валидация

- `CommandEmployeeValidator`: `full_name` непустое; `default_salary ≥ 0`; тип из enum; удаление при наличии строк → 400 `EMPLOYEE_HAS_PAYROLL_LINES` (фронт предлагает архивировать).
- `CommandPayrollRunValidator`: `period_month` уникален → 400 `PAYROLL_RUN_MONTH_EXISTS`; `pay_date` — валидная ISO-дата; суммы строк `≥ 0` и NaN-safe; мутации `approved` → 400 `PAYROLL_RUN_NOT_DRAFT`; повторный approve → 400; сотрудник в строках без дублей.
- 404 на несуществующие run/employee (паттерн ㉘ GetDealStages).
- Ошибки локализуются на фронте конкретикой: «Начисление за этот месяц уже существует», «Не удалось провести начисление».

## 11. Тесты (Jest, рядом с модулем)

- `computePayrollLine.spec.ts`: staff standard / staff msp ниже и выше порога / gph / npd / ip / удержание / NaN-входы / округление копеек.
- `summarizeRun.spec.ts`: итоги, пустой список.
- `CommandPayrollRunValidator.service.spec.ts`: дубль месяца, мутация approved, отрицательные суммы.
- `ApprovePayrollRun.service.spec.ts`: создаёт ≤3 плановых операции с верными суммами/датами/source; нулевые суммы пропускаются; unapprove удаляет.
- `FeaturesConfigure.payroll.spec.ts`: флаг присутствует, дефолт off (паттерн ㉘).

## 12. Риски

| Риск | Митигация |
|---|---|
| Упрощённые налоги разойдутся с реальной платёжкой бухгалтера | Ставки редактируемы; суммы в календаре — плановые, факт вводится фактом; в UI подпись «оценка для управленческого учёта» |
| Смена ставок «поплывёт» по истории | Снапшоты сумм в строках; пересчёт только при явном сохранении draft-строк |
| Дата налогов (28-е) не совпадёт с реальностью пользователя | Плановую операцию можно перенести прямо в календаре — связь по source сохраняется |
| Удаление сотрудника сломает историю | Запрет удаления при наличии строк, архивация `active=false` |

## 13. Критерий завершения ⑧a

Завести сотрудника (любого из 4 типов) → создать начисление за месяц (строки заполнились сами) → увидеть НДФЛ/взносы/на руки/полную стоимость → провести → в платёжном календаре появились выплата и налоги с верными датами → сводка «Налоги к уплате» показывает месяц. `pnpm typecheck`, серверные тесты модуля, `lang-check.js` — зелёные. Миграции `latest → rollback → latest` проходят.
