## 1. Контекст и цели

### Что строим

Прогноз остатка денег на каждый день вперёд и заблаговременную подсветку **кассовых разрывов** (день, когда денег не хватит на запланированный платёж). Это слой планирования поверх существующего фактического учёта.

### Целевая аудитория

Предприниматели без бухгалтерского образования. Им важен один вопрос: «хватит ли мне денег в ближайшие недели и когда будет напряжённо». Календарь отвечает на него визуально.

### Критерий успеха

В режиме «Бизнес» пользователь видит ленту по дням на месяц вперёд с прогнозным остатком, может добавить ручную и повторяющуюся плановую операцию, и при риске кассового разрыва видит баннер «через N дней разрыв на X ₽». Прогноз сходится с отчётом по дебиторке (одни и те же запросы открытых обязательств).

### Что в коде уже есть (фундамент — подтверждено разведкой 2026-05-31)

- **Неоплаченные счета покупателям** — таблица `sales_invoices`: `due_date` (date), общая сумма `balance` (decimal 13,3), к доплате = `balance − payment_amount − written_off_amount − credited_amount`, `currency_code`, `exchange_rate`, `delivered_at` (null = черновик). Готовые модификаторы модели: `dueInvoicesFromDate`, `overdueInvoicesFromDate`.
- **Неоплаченные счета поставщикам** — таблица `bills`: `due_date`, сумма `amount`, к оплате = `amount − payment_amount − credited_amount`, `currency_code`, `exchange_rate`, `opened_at` (null = черновик). Модификаторы: `dueBillsFromDate`, `overdueBillsFromDate`.
- **Денежные счета** — таблица `accounts`, `account_type ∈ ('cash','bank')`; текущий баланс в колонке `amount` (decimal 15,5); `currency_code`.
- **Базовая валюта организации** — `tenants_metadata.base_currency`, достаётся через `tenancyContext.getTenantMetadata().baseCurrency`.
- **Конвертация валют** — `ExchangeRatesService.latest(tenantId, dto)`.
- **Образцовые репозитории для переиспользования** — `ARAgingSummaryRepository` (дебиторка по сроку) и `APAgingSummaryRepository` (кредиторка по сроку): уже делают ровно «открытые обязательства по дате + фильтр по направлению».
- **Статьи учёта** — `management_articles` (+ свёртка «счёт→статья») из Этапа 0.

### Чего в коде нет (строим)

- Таблицы плановых/будущих операций (`planned_operations`).
- Движка прогноза остатка по дням и детекции кассового разрыва.
- Развёртки повторяющихся операций.

## 2. Объём v1

### Входит (4 источника строк календаря — решение основателя 2026-05-31: все три типа сразу)

1. **Ожидаемые поступления** — неоплаченные `sales_invoices` по `due_date` (сумма = остаток к доплате).
2. **Ожидаемые выплаты** — неоплаченные `bills` по `due_date`.
3. **Ручные плановые операции** — пользователь добавляет разовую операцию.
4. **Повторяющиеся операции** — аренда/зарплата по правилу повтора, разворачиваются на горизонт.

Плюс: расчёт бегущего остатка, детекция кассового разрыва, лента по дням, добавление/правка плановых операций, фильтры, горизонт неделя/месяц/квартал.

### НЕ входит (anti-scope)

- Автоматическая отправка платежей в банк (требует ЭКО-сертификации).
- Полноценный модуль «Долги» (старение по корзинам, напоминания) — это ⑭. Календарь только **читает** открытые обязательства.
- Автогенерация строк `planned_operations` из счетов (материализация) — v1 читает обязательства «на лету»; см. Открытый вопрос №1.
- Сценарии (опт./пес.) — это бюджеты, Этап 2.
- Правила автораспределения расходов — это ⑦ Сделки.

## 3. UX

### Формат: лента по дням (а не сетка-календарь)

Решение основателя 2026-05-31. Причины: мобильность (одна колонка, вертикальная прокрутка — приоритет dogfooding), прогноз естественно ложится на «бегущий остаток по дням», нет потребности в стороннем календарном компоненте.

```
┌───────────────────────────────────────────────┐
│ ⚠ Через 6 дней кассовый разрыв: −48 200 ₽      │  ← баннер сверху (липкий)
├───────────────────────────────────────────────┤
│ [Неделя][Месяц][Квартал]     Счёт: Все ▾       │  ← горизонт + фильтры
├───────────────────────────────────────────────┤
│ Сегодня, 31 мая          Остаток: 312 000 ₽    │
│    +200 000  Счёт №12 от ООО «Ромашка»         │
│    −150 000  Аренда (повтор)                   │
│ ──────────────────────────────────────────────│
│ 1 июня                   Остаток: 362 000 ₽    │
│ …                                              │
│ 6 июня          🔴 Остаток: −48 200 ₽          │  ← разрыв красным
│    −410 200  Зарплата (повтор)                 │
└───────────────────────────────────────────────┘
```

### Элементы

- **Строка дня** = дата + прогнозный остаток на конец дня. Раскрытие → «из чего сложилось»: приходы (зелёным) и расходы (красным) с источником (счёт №, контрагент, «повтор», «вручную»). День с остатком < 0 — красный.
- **Баннер кассового разрыва** — сверху, липкий: «через N дней кассовый разрыв: X ₽». Скрыт, если разрыва на горизонте нет.
- **Кнопка «+» → модалка** добавления плановой операции (новый стек: React Hook Form + Zod, shadcn `components/ui`): приход/расход, сумма, дата, статья, счёт, контрагент (опц.), заметка; галочка «Повторять» → частота (день/неделя/месяц), интервал, дата окончания.
- **Горизонт:** по умолчанию месяц вперёд; переключатель неделя/месяц/квартал.
- **Фильтры:** денежный счёт, направление (`branch_id`), приход/расход.
- **Мобильный:** та же лента в одну колонку; баннер-разрыв липкий сверху.

### Переиспользование UI

Те же примитивы, что на странице статей (Этап 0) и в новом auth-флоу: shadcn `components/ui` + RHF + Zod + Tailwind. Новый календарный npm-пакет **не вводим** (роадмап §4.7).

## 4. Модель данных

Одна новая таблица в **tenant**-схему. Таблицы `sales_invoices` / `bills` / `accounts` / `management_articles` **не трогаем — только читаем**. Всё additive, рабочий `down()`.

### `planned_operations`

| Колонка | Тип | Назначение |
|---|---|---|
| `id` | increments | PK |
| `direction` | string | `inflow` / `outflow` |
| `amount` | decimal(13,3) | сумма (формат как у счетов) |
| `currency_code` | string(3) | валюта (по умолчанию базовая орг.) |
| `planned_date` | date, index | когда ожидается |
| `article_id` | integer nullable → `management_articles.id` | статья учёта (Этап 0) |
| `account_id` | integer nullable → `accounts.id` | денежный счёт (cash/bank) |
| `branch_id` | integer nullable | направление |
| `project_id` | integer nullable | проект |
| `contact_id` | integer nullable → `contacts.id` | контрагент |
| `status` | string | `planned` / `confirmed` / `done` / `cancelled` |
| `source_type` | string nullable | тип источника (резерв на будущее) |
| `source_id` | integer nullable | id источника (резерв на будущее) |
| `recurrence` | jsonb nullable | правило повтора (см. §5.3) |
| `description` | string nullable | заметка |
| `created_at` / `updated_at` | timestamps | |

В прогноз попадают операции в статусах `planned` и `confirmed`. `done` (факт уже случился) и `cancelled` — не попадают.

`source_type`/`source_id` в v1 заполняются только если когда-то понадобится «переопределить» ожидаемую дату конкретного счёта (Открытый вопрос №1). В v1 обязательства читаются напрямую из `sales_invoices`/`bills`, поэтому для них строки `planned_operations` не создаются.

## 5. Движок прогноза

### 5.1 Алгоритм (считается «на лету», ничего не материализуется)

1. **Начальный остаток.** Сумма колонки `amount` по счетам `account_type ∈ ('cash','bank')`, приведённая к **базовой валюте** организации (`tenants_metadata.base_currency`). Счёт в другой валюте конвертируется по последнему курсу (`ExchangeRatesService.latest`). Если задан фильтр по счёту — берём только его.
2. **Сбор строк на горизонт `[fromDate, toDate]`:**
   - **Приходы (обязательства):** неоплаченные `sales_invoices` через модификатор `dueInvoicesFromDate` (переиспользуем паттерн `ARAgingSummaryRepository`), сумма = остаток к доплате, дата = `due_date`, валюта → база по `exchange_rate` счёта-фактуры.
   - **Выплаты (обязательства):** неоплаченные `bills` через `dueBillsFromDate` (паттерн `APAgingSummaryRepository`).
   - **Ручные плановые операции:** `planned_operations` со `status ∈ (planned,confirmed)` и `recurrence IS NULL`, по `planned_date`.
   - **Повторяющиеся:** `planned_operations` с `recurrence`, развёрнутые в виртуальные вхождения на горизонте (§5.3).
3. **Бегущий остаток по дням:** `остаток[d] = остаток[d−1] + Σ приходы[d] − Σ выплаты[d]`, начиная с начального остатка.
4. **Кассовый разрыв:** первый день `d`, где `остаток[d] < 0`. В ответ — флаг разрыва, дата, сумма (`|остаток[d]|`), дней до него. Если такого дня нет — разрыва нет.

### 5.2 Валюта

Прогноз — в базовой валюте организации. Для счетов/биллов конвертация по их зафиксированному `exchange_rate` (чтобы цифры сходились с aging-отчётами). Для ручных операций в другой валюте — по последнему курсу. (Открытый вопрос №2 — зафиксировано это решение.)

### 5.3 Развёртка повторяющихся (`recurrence`)

Форма правила (jsonb):

```json
{ "frequency": "monthly", "interval": 1, "day_of_month": 5, "end_date": "2026-12-31" }
```

- `frequency`: `daily` / `weekly` / `monthly`.
- `interval`: каждые N единиц частоты.
- `day_of_month` (для monthly) / `weekday` (для weekly) — опционально.
- `end_date`: дата окончания (или `null` = бессрочно, разворачивается до конца горизонта).

Развёртка — **чистая функция** `expandRecurrence(rule, fromDate, toDate)`, возвращает список дат; ничего не пишет в БД. Бегущий остаток и детекция разрыва — тоже чистая функция `computeRunningBalance(openingBalance, dailyFlows)`.

## 7. Сквозные решения

- **Миграции:** одна additive-таблица в tenant-схему, рабочий `down()`, прогон `latest → rollback → latest`. Через скилл `make-migration`.
- **Feature flag:** `payment_calendar`, по умолчанию `false`. Откат модуля = выключить флаг.
- **Режим:** платёжный календарь — фича режима «Бизнес».
- **i18n:** все строки через `intl.get` / `<T id=.../>`; сообщения Zod — тоже через i18n; парность EN↔RU; после правок — `node packages/webapp/scripts/lang-check.js`. Скилл `i18n-add-string`.
- **Валюта:** прогноз в базовой валюте; мультивалюта конвертируется (§5.2).
- **Зависимости:** переиспользуем существующий стек; новый календарный npm-пакет не вводим.
- **Копирайт:** © 2026 Bigfin, проприетарная лицензия.
- **Старт реализации:** после Ф1 роадмапа (① русификация, ③ режимы), как и весь управленческий каркас.

## 8. Тестирование

- **Unit (Jest), критично:** `expandRecurrence` (повтор с датой конца, бессрочный, день месяца за пределами короткого месяца) и `computeRunningBalance` (разрыв в первый день, разрыв в середине, отсутствие разрыва, мультивалютные потоки). Это сердце фичи — ошибка = ложная тревога или пропуск разрыва.
- **Unit:** валидатор плановой операции; сервис прогноза с замоканными репозиториями обязательств.
- **Регрессия согласованности:** сумма ожидаемых поступлений календаря на дату == дебиторка из aging-отчёта на ту же дату.
- **Миграция:** прогон `latest → rollback → latest`.
- **e2e (Playwright) на `en`** — зелёный (обязательное условие мерджа).
- **Ручная проверка на `ru`** — чек-лист в PR; **dogfooding** — основатель проверяет на своём бизнесе.

## 10. Критерии приёмки

1. В режиме «Бизнес» открывается лента по дням на месяц вперёд с прогнозным остатком на конец каждого дня.
2. В прогнозе учитываются все 4 источника: неоплаченные счета покупателям, неоплаченные счета поставщикам, ручные и повторяющиеся плановые операции.
3. Можно создать/изменить/удалить ручную плановую операцию и повторяющуюся (с правилом повтора).
4. При риске отрицательного остатка виден баннер «через N дней кассовый разрыв на X ₽», день подсвечен красным.
5. Сумма ожидаемых поступлений календаря сходится с отчётом по дебиторке на ту же дату.
6. Прогноз отображается в базовой валюте; мультивалютные обязательства корректно сконвертированы.
7. Новая таблица — additive tenant-миграция с рабочим `down()`; `lang:check` = 0; e2e на `en` зелёные; флаг `payment_calendar` по умолчанию выключен.

## 11. Открытые вопросы

1. **Материализовать обязательства в `planned_operations` или читать «на лету»?** v1 — читаем напрямую из `sales_invoices`/`bills`. Если пользователю понадобится переопределять ожидаемую дату конкретного счёта, вводим override-строку через `source_type`/`source_id`. Решение на будущее, не блокирует v1.
2. **Курс конвертации.** Зафиксировано: счета/биллы — по их `exchange_rate`; ручные операции — по последнему курсу. Пересмотреть после dogfooding, если будут расхождения.
