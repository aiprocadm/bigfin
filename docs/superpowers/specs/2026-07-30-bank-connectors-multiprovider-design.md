# ⑨c Банковские API: мультипровайдерность и коннектор Альфа-Банка — дизайн

Дата: 2026-07-30. Пункт дорожной карты v5 §5 п. 4 (после ⑬a PWA).

## 1. Что есть сейчас

Модуль `BankApiSync` (флаг `bank_api_sync`) работает с одним банком, и имя
банка вшито во все слои:

- `BankApiSyncSettings` — методы `getTinkoffToken/setTinkoffToken/clearTinkoffToken`,
  ключ настройки `tinkoff_token`.
- `BankApiSyncApplication` — `connectTinkoff/disconnectTinkoff/importTinkoffStatement`,
  статус `{ tinkoffConnected }`.
- Контроллер — роуты `/bank-api-sync/tinkoff/{connect,disconnect,import}`.
- Фронт — хуки `useConnectTinkoff/...` и страница с одной карточкой.

Коннектор как таковой уже отделён (`connectors/tinkoff/`: тонкий
API-клиент + чистый маппер операции в каноническую запись), и импорт
переиспользует конвейер «Разбор» ⑨. Расширяемая часть — только эта.

## 2. Ограничение, определяющее объём

Спецификация Alfa API (developers.alfabank.ru) из рабочей сети недоступна:
портал отдаёт самоподписанный сертификат через локальный прокси, а поиск даёт
лишь общие сведения — OAuth 2.0 (Authorization Code Flow), `Authorization:
Bearer <access-token>`, наличие методов выписки. **Точные пути, имена полей
операций и параметры запроса неизвестны, и проверить их без реального
доступа (client_id/secret от банка) невозможно.**

Отсюда честное разделение:

- **Срез 1 (этот дизайн)** — то, что проверяемо здесь и сейчас: перевод
  модуля на мультипровайдерную архитектуру, Тинькофф как первый провайдер,
  Альфа как второй провайдер с контрактом, вынесенным в один файл-адаптер.
- **Срез 2 (после получения доступа)** — сверка адаптера Альфы с реальным
  API: пути, поля, OAuth-регистрация приложения, живой прогон. Правки
  ожидаются только внутри адаптера.

Писать «настоящий» коннектор вслепую нельзя — это код, который почти
наверняка разойдётся с реальным API. Поэтому адаптер Альфы строится так,
чтобы расхождение чинилось в одном месте, а не по всему модулю.

## 3. Архитектура: провайдер как значение

### 3.1 Реестр провайдеров

`connectors/BankProvider.types.ts`:

```ts
export type BankProviderId = 'tinkoff' | 'alfa';

export interface BankConnector {
  readonly id: BankProviderId;
  /** Проверка учётных данных; бросает ServiceError при неверных. */
  ping(credentials: BankCredentials): Promise<void>;
  /** Операции за период в канонической форме. */
  fetchOperations(
    credentials: BankCredentials,
    accountNumber: string,
    from: string,
    to: string,
  ): Promise<BankApiOperation[]>;
}
```

`BankCredentials` — размеченное объединение: `{ kind: 'token', token }`
(Тинькофф) либо `{ kind: 'oauth', clientId, clientSecret, refreshToken }`
(Альфа). Каноническая запись `BankApiOperation` уже существует
(`connectors/tinkoff/mapTinkoff.ts`) и переезжает в общий файл без изменений
полей — от неё зависит импорт в «Разбор».

Коннекторы регистрируются в `BankConnectorsRegistry` (обычный provider
NestJS с картой `id → BankConnector`); прикладной слой знает только про
реестр.

### 3.2 Настройки

`BankApiSyncSettings` переходит на ключи вида `<provider>_credentials`
(JSON): `getCredentials(providerId)`, `setCredentials(providerId, creds)`,
`clearCredentials(providerId)`, `listConnected()`.

**Совместимость:** существующий ключ `tinkoff_token` читается как запасной
вариант, если нового ключа нет (тенанты с подключённым Тинькоффом не должны
отвалиться после обновления). При первом сохранении пишется уже новый формат.
Миграция данных не нужна — настройки лежат в общем key-value.

### 3.3 Прикладной слой и роуты

- `status()` → `{ connected: { tinkoff: boolean, alfa: boolean } }`;
  прежнее поле `tinkoffConnected` сохраняется в ответе как алиас, чтобы не
  ломать уже задеплоенный фронт до его обновления.
- Роуты становятся параметрическими:
  `POST /bank-api-sync/:provider/{connect,disconnect,import}`,
  где `:provider` валидируется по списку. Старые пути `/tinkoff/*`
  продолжают работать: они и есть частный случай параметрического роута.

Тело `connect` — объединение по провайдеру: `{ token }` для Тинькоффа,
`{ clientId, clientSecret, refreshToken }` для Альфы. Валидация — вручную в
прикладном слое (DTO с опциональными полями + проверка по провайдеру),
чтобы не плодить классы.

### 3.4 Адаптер Альфы

`connectors/alfa/AlfaApi.service.ts` — единственное место, где живут
предположения о внешнем контракте:

- `TOKEN_URL`, `BASE_URL`, путь выписки и имена параметров вынесены в
  константы с комментарием «сверить с документацией банка при подключении»;
- обмен `refresh_token` → `access_token` (OAuth 2.0, `grant_type=refresh_token`),
  токен кэшируется в памяти до истечения `expires_in`;
- 401/403 → `ALFA_INVALID_CREDENTIALS`, прочее → `ALFA_API_ERROR`
  (по образцу Тинькоффа).

`connectors/alfa/mapAlfa.ts` — маппер операции в `BankApiOperation`;
`externalId` — `alfa:<id операции>`. Имена полей источника собраны в
таблицу соответствия в начале файла, чтобы правка была точечной.

## 4. Фронт

`hooks/query/bankApiSync.tsx` — хуки становятся параметрическими:
`useConnectBank(provider)`, `useDisconnectBank(provider)`,
`useImportBankStatement(provider)`; `useBankApiStatus` отдаёт карту
подключений.

Страница `/bank-api-sync` — по карточке на банк: Тинькофф (поле токена) и
Альфа-Банк (три поля OAuth + подпись «требуется регистрация приложения в
банке»). Форма импорта общая, банк выбирается переключателем. Строки — через
`intl.get`, ключи `bank_api.*` парно en/ru.

## 5. Тестирование

- Юнит: реестр отдаёт коннектор по id и падает на неизвестном; настройки —
  чтение/запись/очистка по провайдеру и чтение легаси-ключа `tinkoff_token`;
  маппер Альфы (приход/расход, знак, `externalId`, пустые поля); клиент
  Альфы на моке axios — обновление токена, кэш токена, 401 → доменная ошибка.
- Существующие тесты Тинькоффа (`mapTinkoff.spec.ts`) остаются зелёными без
  правок — признак того, что канонический формат не поехал.
- Живая проверка Тинькоффа/Альфы невозможна без реальных учёток; в PR это
  указывается явно, а не маскируется.

## 6. Порядок работ

1. Общие типы + реестр + настройки по провайдеру (с легаси-чтением).
2. Перевод Тинькоффа на интерфейс коннектора, параметрические роуты и
   прикладной слой.
3. Адаптер Альфы (клиент + маппер) с тестами.
4. Фронт: параметрические хуки, вторая карточка, i18n.
