# ⑧b — KPI/бонусы менеджеров (переменная часть ФОТ)

**Дата:** 2026-06-10
**Под-проект роадмапа:** ⑧ (Ф3a), вторая половина после ⑧a (ядро зарплат, PR #64).
**Зависит от:** ⑧a (`employees`, `payroll_runs/lines`, настройки payroll), ⑦a Сделки (`projects`, прибыльность через свёртку статей), ⑦b/㉘ (паттерны NaN-safe расчётов и снапшотов).
**Флаг:** `Features.PAYROLL_KPI = 'payroll_kpi'` (по умолчанию **off**, независим от `payroll` — гейтит только UI, по паттерну ⑦b).
**Контекст решений (в рамках делегированного исполнения роадмапа, зеркалит одобренные решения ⑧a):**
- метрики v1: **выручка или прибыль** по сделкам менеджера (средний чек — отложен, нет очевидной пользы при малом числе сделок);
- бонус = **процент от факта** показателя, с опцией «только при выполнении плана»;
- факт считается из **сделок с ответственным менеджером** через существующую свёртку статей (как `GetDealsSummary`), без новых механизмов признания;
- подход без проводок (как ⑧a): KPI не пишет в книгу, бонус попадает в начисление как обычная премия.

---

## 1. Зачем

Роадмап v2 для ⑧: «план продаж на менеджера, расчёт переменной части ФОТ от показателя (выручка/маржа), привязка сделок к ответственному менеджеру». Сейчас премия в начислении вводится руками «из головы». ⑧b даёт: поле «ответственный» у сделки → план на месяц по менеджеру → автоматический факт из сделок → расчёт бонуса → автоподстановка бонуса в начисление зарплаты.

## 2. Модель данных (tenant, additive, рабочий `down()`)

### `projects` — новая колонка

| Колонка | Тип | Назначение |
|---|---|---|
| `manager_id` | integer unsigned, nullable, index | Ответственный менеджер (id из `employees`). **Без FK** — зеркалит `contact_id` (plain integer), модули остаются слабо связанными |

### Новая таблица `employee_kpi_targets`

| Колонка | Тип | Назначение |
|---|---|---|
| `id` | increments | PK |
| `employee_id` | int unsigned, FK → `employees.id`, index | Менеджер |
| `period_month` | date | Первое число месяца |
| `metric` | string, default `'revenue'` | `'revenue'` \| `'profit'` |
| `target_amount` | decimal(13,3), default 0 | План на месяц |
| `bonus_rate` | decimal(8,4), default 0 | % от факта показателя |
| `only_if_achieved` | boolean, default false | Бонус только при факте ≥ плана |
| `note` | text, nullable | — |
| `created_at`/`updated_at` | timestamps | — |

Уникальность `(employee_id, period_month)` — один план на менеджера на месяц. Модель `EmployeeKpiTarget` ← `TenantBaseModel`, регистрация в `Tenancy.module.ts`.

## 3. Расчёт (чистая функция)

`computeKpiBonus({ metric, targetAmount, bonusRate, onlyIfAchieved }, fact)`:

```
achievementPct = targetAmount > 0 ? fact / targetAmount × 100 : null
bonus          = round2(max(0, fact) × bonusRate / 100)
onlyIfAchieved && fact < targetAmount → bonus = 0
```

NaN-safe (паттерн ⑧a `payrollMath`): нечисловые входы → 0. Отрицательный факт (убыточный месяц по прибыли) → бонус 0.

**Факт по менеджеру за месяц:** сделки с `manager_id = employee_id` → свёртка статей по каждой (`ArticlesPlRollupService.getRollup({projectId, fromDate, toDate})` + `computeDealMargin`) → сумма `revenue` или `profit`. Период — календарный месяц плана. Паттерн скопирован с `DealsRevenueService`/`GetDealsSummary`.

## 4. API — расширение модуля Payroll (+ Deals)

### Deals (модификация)

`managerId?: number | null` в `CreateDealDto`/`EditDealDto`, модели `Deal`, ответах. Валидатор: если задан — сотрудник существует (404-стиль ошибки как `contactId`). UI-поле гейтится флагом, сервер принимает всегда (паттерн ⑦b).

### Payroll (новые эндпоинты, тот же контроллер/application)

```
GET    /payroll/kpi/targets        ?year=          // планы за год (с ФИО менеджера)
POST   /payroll/kpi/targets                        // admin
PUT    /payroll/kpi/targets/:id                    // admin
DELETE /payroll/kpi/targets/:id                    // admin
GET    /payroll/kpi/summary        ?month=YYYY-MM  // по менеджерам: план, факт, %, бонус
```

Запись — `@RequirePermission('manage', 'all')` (как ⑧a), чтение — авторизованный пользователь. `summary` считает факт on-the-fly (без кэш-таблиц — мало сделок, paттерн `GetDealsSummary`).

### Интеграция с начислением

`CreatePayrollRun` (⑧a) при пре-заполнении строк: для каждого активного сотрудника, у которого есть KPI-план на `period_month`, `bonus_amount` = рассчитанный бонус (вместо 0). Без плана — поведение ⑧a не меняется (бонус 0), поэтому изменение безопасно и без проверки флага. Бонус остаётся редактируемым в draft — KPI лишь даёт стартовое значение (снапшот-принцип ⑧a: дальнейшие изменения сделок не «двигают» начисление).

## 5. Ошибки и валидация

- `KPI_TARGET_MONTH_EXISTS` (400) — дубль (менеджер, месяц);
- `targetAmount ≥ 0`, `bonusRate 0–100`, metric из enum, `periodMonth` — валидная дата (нормализуется к первому числу);
- `EMPLOYEE_NOT_FOUND` (404) — несуществующий менеджер в target или в `managerId` сделки;
- удаление сотрудника: запрет уже стоит при наличии строк начислений (⑧a); наличие KPI-планов также блокирует удаление (`EMPLOYEE_HAS_KPI_TARGETS`) — предлагается архивация.

## 6. Фронт

- **Сделки:** в `DealDialog` select «Ответственный» (активные сотрудники, `useEmployees`), виден при `featureCan('payroll_kpi')`; колонка/строка «Ответственный» в развёрнутой карточке сделки.
- **Зарплаты:** третья вкладка **«KPI»** на `/payroll` (видна при `featureCan('payroll_kpi')`):
  - селектор месяца (как год в «Начислениях»);
  - таблица: менеджер · метрика · план · факт · % выполнения · бонус (паттерн план/факт из `BudgetPlanFact`: подсветка недовыполнения);
  - CRUD диалог плана (React Hook Form + Zod, как `EmployeeDialog`): менеджер, месяц, метрика, план, % бонуса, «только при выполнении»;
  - подпись «оценка для управленческого учёта» (риск-митигация ⑧a).
- Хуки в `hooks/query/payroll.tsx` (+ ключи `PAYROLL_KPI_TARGETS`, `PAYROLL_KPI_SUMMARY`; инвалидация бонусов → также `PAYROLL_RUNS`).
- i18n: `payroll.kpi.*`, `deal.manager.*` парно en+ru; термины: «план продаж», «выполнение», «бонус», «ответственный» (не кальки).

## 7. Тесты (Jest, рядом с модулем)

- `computeKpiBonus.spec.ts`: процент от факта / only_if_achieved ниже и выше плана / нулевой план / отрицательный факт / NaN / округление;
- `CommandKpiTargetValidator.service.spec.ts`: дубль месяца, диапазон ставки, несуществующий сотрудник;
- `GetPayrollKpiSummary.service.spec.ts`: агрегация факта по менеджерам, менеджер без сделок, сделки без менеджера не считаются;
- `CreatePayrollRun` (расширение спека): бонус подставляется из KPI-плана, без плана — 0;
- `FeaturesConfigure.payrollKpi.spec.ts`: флаг есть, дефолт off.

## 8. НЕ входит (явно отложено)

- Средний чек и количество сделок как метрики — v2;
- Несколько планов/метрик на менеджера в месяц; командные планы;
- «Воронка» продаж как отдельная визуализация (v1 — таблица план/факт);
- Ретроспективный пересчёт бонуса в проведённых начислениях (снапшот);
- Какие-либо проводки в книгу.

## 9. Критерий завершения ⑧b

Назначить сделке ответственного → задать менеджеру план по выручке на месяц → вкладка KPI показывает план/факт/%/бонус → создать начисление за этот месяц → премия менеджера заполнилась бонусом автоматически. `pnpm typecheck`, серверные тесты модуля, `lang-check.js` — зелёные; миграции `latest → rollback → latest` проходят.
